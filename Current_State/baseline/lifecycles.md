## Plan lifecycle

1. Configuration names a default plan and policy. Program workflow/executors call `PlanService` to ensure a plan, register a request and its work items, and translate item dependencies. The plan stores relationships; actual request/item records live in separate collections. ## Ordering and ownership limits

Run-event and plan-journal sequence domains are per object. File locks serialize individual writes; the PlanService's reentrant queue serializes local service mutations. No one transaction spans a request, work item, plan document, journal, artifact and run event. Same-process notification listeners do not observe another process's append. Local workspace checkout is separate from run/claim fencing. These are source-backed boundaries, not claims of an observed race.
