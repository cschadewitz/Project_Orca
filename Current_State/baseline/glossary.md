## Status vocabularies are projections, not synonyms

Implemented: core run statuses are `created`, `running`, `waiting`, `paused`, `completed`, `failed`, `cancelled`; step statuses include `scheduled` and `skipped`. Run outcome (`success`, `failure`, `cancelled`) carries a separate result dimension. [`export const RunStatusSchema`](../../packages/core/src/model/run.ts#L10) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/core/src/model/run.ts#L10))

Implemented: the protocol/design vocabulary is `running`, `waiting`, `succeeded`, `failed`, `cancelled`, `blocked`, `held`, `stale`. Display folding combines core state, wait reason, plan state and lease liveness. `held` can describe undispatched planning work; `stale` is a read-time ownership observation, not a stored terminal event. Thus “eight run statuses” refers to presentation vocabulary, not the core enum. [`export const DISPLAY_STATUSES`](../../packages/protocol/src/status.ts#L19) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/protocol/src/status.ts#L19)), [`export class ReadModel`](../../packages/daemon/src/read-model.ts#L387) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/daemon/src/read-model.ts#L387))

Implemented: `agent.changed` reports configured-agent health, `agent.update` is run/step output; `event.appended` carries a persisted run event; `plan.changed` invalidates plan projections. These names have different keys and replay behavior. ## Actors and boundaries

Human contributors author configuration, workflow graphs and templates; operators start daemon/CLI and control releases; upstream ACP clients submit requests; desktop users inspect/answer/control runs; downstream ACP agents run tools and produce files. The implementation divides these through CLI/integration entry points and the daemon bridge, not through authenticated user accounts. [`export async function bootstrap`](../../packages/cli/src/bootstrap.ts#L176) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/cli/src/bootstrap.ts#L176)), [`export async function startDaemon`](../../packages/daemon/src/server.ts#L96) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/daemon/src/server.ts#L96)), [`export async function dispatch`](../../packages/daemon/src/server.ts#L66) ([pinned](https://github.com/cschadewitz/Project_Orca/blob/09f32690ffca5d9c79f6d8702481f6efe30a4cf3/packages/daemon/src/server.ts#L66))

The engine owns orchestration; stores own persistence primitives; core owns reusable models and pure interpretation/planning; daemon owns protocol projections/control adaptation; Electron main owns desktop process/network access; renderer owns interaction and displayed state. The package and process maps are deliberately distinct: daemon models and engine normally share a Node process while renderer/main do not. Configured executables, ESM plugins, workflow/template authors and writable store/config files are trusted inputs at different boundaries. ACP permission callbacks and file-path checks limit cooperating agent operations; they are not OS sandboxing of arbitrary configured subprocesses.
