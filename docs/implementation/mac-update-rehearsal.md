## Composition and evidence

[The fixture](../../packages/app/test/mac-update-rehearsal-fixture.ts) composes the real
`MacUpdates`, strict `delivery-v1` manifest reader and `downloadMacCandidate`,
`MacUpdateWindows`, actual sandboxed preload source, `NonceDraftGuard` through
`MacUpdateGuards`, `Workspace` target capture and authenticated runtime proof client.
The unchanged daemon `runtimeMaintenanceFixture` supplies the production bootstrap,
serving runtime, orchestrator, live inputs, credential/ownership stores and all three
admission models. Requests cross actual loopback HTTP and the actual
`maintenance.runtime` handler. Positive runtime proofs are generated by that serving
runtime, not fabricated by the fixture.

The lifecycle binds an exact manifest digest, channel and compatibility/recovery
references to a process-local offer and approval. Downloaded bytes stay owned while
busy runtime work prevents admission. Known busy/refused drafts restore the native
window states, including a previously disabled second window. Once work settles,
`reconsider` reuses the same owned bytes and approval, freezes both windows, acquires
an exact workspace/instance/PID-bound runtime lease and enters final revalidation.
The fence refuses new RPC work and direct producer entry, connection changes remain
reserved and new window requests remain deferred. Revalidation deliberately returns
`unknown` because recovery/native activation are absent. The coordinator seals in
`recovery-required` with both guards retained. This is an exercised pre-restart
checkpoint, not an assertion of complete update readiness.

[The 16 pre-restart cases](../../packages/app/test/mac-update-rehearsal.test.ts) also cover:

- An actual pending live callback plus a synchronous dispatch reservation prevents
  readiness. The updater never cancels or answers the callback; its disposable source
  ends it before reconsideration. New dispatch work entering after window ACKs and
  immediately before the maintenance request blocks acquisition.
- Duplicate and stale approval, exact owned manifest bytes, safe defer/disposal followed
  by a fresh offer/approval and new download/inspection. The real candidate session
  separately rejects reapproval of its disposed ID and seals malformed native proof.
- Stale nonce, phase, generation and main-frame ACKs cannot advance preparation.
  Cancellation while awaiting a real preload ACK releases known window ownership before
  any maintenance request. Lost prepare or release ACKs use the existing 5-second guard
  deadlines under fake timers and retain the window boundary. Late ACKs cannot retry the
  sealed coordinator. No timeout or production guard is enlarged.
- Document replacement during actual runtime acquisition invalidates the draft lease;
  even the replacement's ACK cannot restore ownership. The authentic remote fence and
  local target reservation remain held, with no revalidation or wrong-target cleanup.
- Response loss after actual acquisition, legacy/malformed proof, wrong PID/instance and
  contradictory held-with-active-work proof seal the composed coordinator. No release
  or retry is sent for uncertain acquisition.
- Cancellation after actual acquisition attempts exactly one release. An injected
  transport failure **before resume dispatch** retains remote admission, local target
  and windows. This is release uncertainty, not a claim of a received/lost resume
  acknowledgement. The fixture intentionally never sends a successful resume.
- Draft refusal and broken downloaded bytes prevent later guards; stalled transport
  cancellation awaits real file cleanup and cancels a late response body before it can
  write or freeze windows.

Every case checks that activation and managed-process stop were not called, then
compares synthetic retained state, draft, preferences and workflow bytes before
removing owned downloads. Cleanup closes only the owned disposable in-process or fresh-child daemon
and removes its temporary roots; it never resumes admission or stops/kills a host app.
The preserved sentinel files are cleanup evidence, not a complete protected-state
inventory, snapshot consistency or recovery proof.

## Reviewed restart extension

The existing four-file scope now also consumes the real `MacUpdateOwnedStop` and
`MacRestartVerification`, using the unchanged
[restartFixture](../../packages/app/test/mac-restart-fixture.ts) and its compiled
[fresh-process source daemon](../../packages/app/test/fixtures/mac-restart-daemon.ts).
No new fixture path or competing restart API is needed. The optional process fixture
composition routes the same candidate/download/coordinator/window/admission path to
that fixture's actual old child, authenticated token file and canonical workspace.
The manifest bytes and candidate references are exactly the restart fixture's,
including its inspected/emitted daemon hash, and the owned downloaded manifest is
compared byte-for-byte with them.

After actual approval/download and both real leases reach the revalidation checkpoint,
a surviving test supervisor invokes the reviewed stop with the captured child and
fresh runtime-v1 proof using the coordinator's actual admission owner token. Local
ownership checks include the held draft boundary, unchanged target/epoch, positive
lease acquisition and the fixture's existing reservation. Concurrent stop controllers
share one proof, one SIGTERM, one clean close and the same private receipt.
The reviewed verifier consumes that receipt once and starts a fresh child from the
exact resource daemon bytes. Initial/final image, authenticated hello, store and
bootstrap-fence observations must match the same approved candidate/workspace while
PID and boot UUID differ from the stopped target.

The positive terminal restart result is **`verified-closed`, `scope: startup-only`**.
Actual RPC admission is refused immediately after verification and after fresh
recheck; receipt replay cannot start another process. No fixture `simulateReopen`
call is used. Native activation and full-state recovery are still absent: the
coordinator's unavailable revalidation gate is settled as unknown during test
completion, leaving its conservative recovery-required state and guard ownership.
A positive restart receipt is never fed back as a valid whole-state/native update
receipt. This tests coherent component composition under a surviving supervisor;
production coordinator activation, UI/app replacement and reconnect wiring remain
separate missing seams.

Eight additional integration schedules cover:

- The positive shared-stop/one-receipt/fresh-identity/verified-closed lifecycle.
- Document replacement after admission makes the stop refuse without signalling;
  the old authentic fence stays held.
- Lost actual same-owner stop proof seals all controllers without a signal or launch.
- Cancellation after one SIGTERM to an ignoring disposable child cannot mint a receipt,
  retry or force-kill; bounded owned IPC cleanup later closes only that fixture child.
- Changed synthetic app bytes and mismatching actual hello PID produce known startup
  refusals. Lost final authenticated hello and a lost response after actual closed
  launch produce unknown. Recheck/verify cannot return cached success or relaunch,
  and the replacement remains closed in every case.

The restart fixture's whole-app comparison, sealed identity/resource witnesses and
store-epoch/work classification are synthetic supported-owner ports, as documented
in [its handoff](mac-update-restart.md). They are not a signed Mac image, native
acceptance, a production epoch reader or full-state restoration. Actual startup
uses the existing legacy initial-maintenance token before server admission; runtime-v1
adoption and production fence acknowledgements are still missing source seams.
Only these owned disposable children receive SIGTERM/cleanup IPC. No installed app,
host daemon, host credential, provider, admission reopening or recovery contract is touched.

## Visible integration gap and mocked boundaries

`MacCandidateSession` deliberately constructs hard-blocked preparation adapters and
exposes no injection seam for the reviewed guards. Therefore the end-to-end portion
composes its real underlying manifest/download path with `MacUpdates` in a test-only
fixture; a separate case runs the actual session's disposal/proof behavior and
confirms `blocked/candidate`. This does **not** prove that production candidate sessions
are wired to the guards. The next owner must design/review that composition before
any production offer or approval IPC. No private fields are patched and no substitute
candidate, restart or recovery API is introduced. No production correctness defect
was found by these schedules.

The Electron OS objects and renderer readiness callback are synthetic; the actual
preload and main window boundary execute unchanged. React `UpdateControl`, real DOM
inert behavior, physical BrowserWindow input/navigation and native lifecycle are not
executed in this Node rehearsal. Existing window and renderer tests remain separate
source evidence. Catalog policy, candidate transport and native inspection are injected
synthetic ports; unchanged #402 fixture payloads are made candidate-shaped only in
memory. They prove neither provenance nor signatures, notarization or a real candidate.
The compatibility/recovery plan IDs are references only, never simulated whole-state
recovery receipts. Revalidation is an explicit unavailable gate; activation is a trap.

`Workspace.captureMacUpdateTarget` deliberately builds a fresh authenticated client
with global `fetch`. The test scopes response corruption/loss and release failure at
that transport boundary and restores it on cleanup. Ordinary traffic uses the real
loopback transport. Only the existing disposable fixture's in-memory synthetic token
and private token file are used; no host credentials or policy are read/selected.
No external candidate download, provider execution or admission reopening occurs.
