# Integrations: Kepler, T3 Code, SSH agents

ORCA is deliberately **standalone**: it is an ACP *client* to the coding agents
below it and an ACP *agent* to the tools above it. That lets it work inside or
in front of existing products without forking them (ADR 0005).

## GitKraken Kepler

Kepler organises work as **Tasks**: a task directory holding one git worktree per
repository, shared context files (`AGENTS.md` / `CLAUDE.md`, generated by Kepler),
agent sessions, and an MCP server (`kepler-workspace`) that agents use to read task
context, attach links, add notes and manage worktrees. Kepler talks to agents over
ACP and supports any ACP agent (Claude Code, Codex, Gemini, Copilot, OpenCode, …).

### Mode A — ORCA as an agent inside Kepler (proxy mode, recommended)

Register ORCA as an agent in Kepler using the command `orca acp` (after `pnpm run build`
and `pnpm link --global`, or `node <repo>/packages/cli/dist/main.js acp --config <orca.config.yaml>`).
A Kepler session then drives ORCA like any agent:

- the prompt becomes a **Request** (first line = title) — or `/run ai-sdlc key=value` to
  run a single workflow in the session's cwd, or `/status` to list the session's runs;
- ORCA decomposes it and launches the real agents (from `orca.config.yaml`) on the task's
  worktrees, locally or over SSH;
- progress streams back as ACP updates: the root workflow and child runs appear as a flat
  **plan** (one entry per node, live status; child entries are prefixed with the workflow
  chain, e.g. `[program › ai-sdlc]`), agent output as message chunks (with the same prefix,
  and each child node start as a `▶ <node>` line),
  every recorded artifact as a completed **tool call** with the file location;
- gates and `ask` permissions are forwarded upstream as `session/request_permission`, so
  Kepler's normal approval UI is the human gate. Questions are routed by the run that raised
  them (child runs resolve to the session that started their root run), so concurrent
  sessions each see only their own gates;
- `session/cancel` cancels the whole run tree.

Implementation: `packages/integrations/src/acp-facade/`. Workspace selection:
`workspace: { provider: kepler }` in `orca.config.yaml` makes ORCA use the task's worktrees
(`KeplerTaskWorkspaceProvider` scans the task dir for `*/.git`, picks by work item `repo`,
else the worktree the parent workspace already sits in, else the first worktree, else the
parent workspace or the task directory itself). Sub‑agents launched by ORCA can still be given Kepler's MCP server
via `agents[].mcpServers` so they keep the task's resource list honest.

### Mode B — ORCA beside Kepler (side‑car)

From a shell inside a task folder: `orca kepler` shows what ORCA sees (task id, title/body
from `AGENTS.md`, worktrees); `orca submit "$(head -1 AGENTS.md)" --body-file AGENTS.md`
drives the task through the program workflow using the task's worktrees.

### What Kepler does not expose (yet)

Kepler has no public API to create sessions or tasks from outside; the ACP‑agent route
is the supported way in. Kepler's remote‑agent support is "in development"; ORCA's SSH
host covers that gap today.

## T3 Code (groundwork — neither direction works yet)

[T3 Code](https://github.com/pingdotgg/t3code) is an open‑source, TypeScript control plane
for coding agents: a Node **WebSocket server** wraps provider CLIs (Codex app‑server,
Claude Code SDK, Cursor, OpenCode, …) behind an **event‑sourced orchestration model**
(`packages/contracts/src/orchestration.ts`: projects → threads → turns → checkpoints;
commands like `thread.create`, `thread.turn.start`, `thread.turn.interrupt`,
`thread.approval.respond`; events like `thread.message-sent`, `thread.activity-appended`,
`thread.session-set`). It is *not* an ACP client or agent.

ORCA's adapter (`packages/integrations/src/t3code/`) therefore maps ORCA's
`AgentSession` onto a **T3 thread**. The mapping is written; the transport under it
is not, so nothing below runs today:

| ORCA | T3 Code |
| --- | --- |
| `openSession` | `orchestration.dispatchCommand` → `thread.create` (project, model selection, runtime mode) |
| `prompt()` | `thread.turn.start`; resolves when `thread.session-set` reports no active turn or `thread.turn-diff-completed` reports the turn `completed` / `error` / `interrupted` |
| updates | `orchestration.subscribeThread` events mapped to `AgentUpdateSummary` |
| `cancel()` | `thread.turn.interrupt` |
| `close()` | `thread.session.stop` |

Once a transport exists, wire it in via `Orchestrator.sessionFactory` (route agents with
e.g. `hostId: t3code` or an `env.ORCA_T3_PROJECT` marker to `openT3CodeSession`, everything
else to `openAcpSession`). Artifact pickup keeps working because T3 threads run in local
worktrees the host FS can read. Until then a t3code session factory fails on first use:
the only shipped `T3CodeRpc` is `UnimplementedT3CodeRpc`, whose `call` and `subscribe`
both throw `NOT_SUPPORTED`.

**Left open on purpose:** the concrete WebSocket transport. T3 Code uses Effect RPC over
`/ws` with typed request/success/error envelopes and streaming subscriptions; `T3CodeRpc`
is the two‑method interface to implement (`call`, `subscribe`) once the envelope is pinned
to a version. `UnimplementedT3CodeRpc` documents the gap. T3's own contracts package
(`@t3tools/contracts` in the monorepo) is the right thing to depend on when publishing.

The other direction is equally unavailable: T3 Code cannot drive ORCA either, because it
has no ACP client. If T3 ever adds ACP agents as a provider, `orca acp` plugs in unchanged
— no work needed on ORCA's side.

## Remote agents over SSH

`hosts[]` entries of `type: ssh` run agents on another machine:

```yaml
hosts:
  - id: buildbox
    type: ssh
    host: build.internal
    user: ci
    identityFile: ~/.ssh/orca
    sshArgs: ["-o", "ProxyJump=bastion"]
    workspaceRoot: /srv/work
agents:
  - id: claude-remote
    command: claude-code-acp      # must be on PATH for a login shell on buildbox
    hostId: buildbox
    roles: [builder, tester]
```

How it works: ORCA spawns `ssh -T -o BatchMode=yes -o ConnectTimeout=20 [sshArgs…] [-p port]
[-i identityFile] ci@build.internal -- bash -lc 'cd <cwd> && exec [env K=V …] claude-code-acp'`
(`bash -lc` is the default `remoteShell`); the child's stdin/stdout carry ACP's
newline‑delimited JSON‑RPC, so the
remote agent is indistinguishable from a local one. File access for artifact pickup and
`fs/*` requests goes through short `ssh … cat|test|mkdir` commands (`SshFileSystem`); the
`git-worktree` workspace provider runs `git worktree add` on the remote via `exec`.

Requirements: key‑based auth (no prompts), the agent binary on the remote login‑shell PATH,
and the repository present on the remote (clone it there, or use a shared filesystem; ORCA
does not sync code). Verify with `orca ping claude-remote`.

## Other ACP clients (Zed, JetBrains, …)

Anything that can launch an ACP agent can launch `orca acp`. The facade advertises
`loadSession: false` and prompt capabilities `embeddedContext: true` (so file context can be
attached to requests).

Plain-text submissions settle their Request from the final program outcome, just as CLI
submissions do: a failure outcome is failed even when interpretation completed, cancellation
is cancelled, and a paused run leaves the Request decomposing. Direct `/run` commands do not
create a Request. Plan updates suppress identical snapshots and label failed, cancelled and
skipped steps explicitly (ACP has no separate failed plan-entry status). Child-run nodes are
flattened beneath their owning container entry and carry their workflow-chain prefix.
