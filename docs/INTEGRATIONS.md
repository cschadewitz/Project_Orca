# Integrations: Kepler, T3 Code, SSH agents, JEV

ORCA is deliberately **standalone**: it is an ACP *client* to the coding agents
below it and an ACP *agent* to the tools above it. That lets it work inside or
in front of existing products without forking them (ADR 0005).

## GitKraken Kepler

Kepler organises work as **Tasks**: a task directory holding one git worktree per
repository, shared context files (`AGENTS.md` / `CLAUDE.md`, generated by Kepler),
agent sessions, and an MCP server (`kepler-workspace`) that agents use to read task
context, attach links, add notes and manage worktrees. Kepler talks to agents over
ACP and supports any ACP agent (Claude Code, Codex, Gemini, Copilot, OpenCode, …).

### Mode A — ORCA as an agent inside Kepler (proxy mode, recommended)

Register ORCA as an agent in Kepler using the command `orca acp` (after `pnpm run build`
and `pnpm link --global`, or `node <repo>/packages/cli/dist/main.js acp --config <orca.config.yaml>`).
A Kepler session then drives ORCA like any agent:

- the prompt becomes a **Request** (first line = title) — or `/run ai-sdlc key=value` to
  run a single workflow in the session's cwd, or `/status` to list the session's runs.
  The facade advertises both to the client as ACP `available_commands_update` right after
  `session/new`, so Kepler renders them as real slash commands with an input hint (the
  hint names the selected workflow once one is chosen); an unknown `/command`, or `/run`
  with no workflow, answers with the command list instead of being submitted as a Request;
- ORCA decomposes it and launches the real agents (from `orca.config.yaml`) on the task's
  worktrees, locally or over SSH;
- progress streams back as ACP updates: the root workflow and child runs appear as a flat
  **plan** (one entry per node, live status; child entries are prefixed with the workflow
  chain, e.g. `[program › ai-sdlc]`), agent output as message chunks (with the same prefix,
  and each child node start as a `▶ <node>` line),
  every recorded artifact as a completed **tool call** with the file location;
- gates and `ask` permissions are forwarded upstream as `session/request_permission`, so
  Kepler's normal approval UI is the human gate. Questions are routed by the run that raised
  them (child runs resolve to the session that started their root run), so concurrent
  sessions each see only their own gates;
- `session/cancel` cancels the whole run tree.

**Session config options.** Kepler's Mode / Model dropdowns are ACP *session config
options*, and the facade advertises the following in `session/new` and handles
`session/set_config_option` (#188). Every option has a default meaning "what the
configuration says", so a client that never sets one gets exactly the behaviour above. A
value set while a run is in flight applies to the **next** run; each option's description
says so.

| Option | Category | Default | Other values | Becomes |
| --- | --- | --- | --- | --- |
| `orca/workflow` | `mode` | `orca:request` (submit a Request) | a workflow id | a direct run of that workflow with the prompt as `vars.prompt`; also `/run`'s default |
| `orca/item-workflow` | `_workflow` | `orca:default` | workflow ids | `overrides.itemWorkflow` |
| `orca/agent.<role>` (one per role) | `_agent` | `orca:default` | agent ids, grouped by host when they span hosts | `overrides.roles` |
| `orca/model` | `model` | `orca:default` (agent default) | `<agentId>/<modelId>`, grouped by agent when several offer models | `overrides.model` as `{ agentId: modelId }` |
| `orca/template-pack` | `_template_pack` | `orca:default` | pack ids | `overrides.templatePack` |
| `orca/use-client-cwd` | `_workspace` | the facade's `useClientCwd` | boolean | run in the session's cwd, or through ORCA's workspace provider |
| `orca/<agentId>/<configId>` | `mode`, `model_config`, `thought_level` | the agent's | the agent's | recorded on the session, **not yet applied** to a run |

Boolean options (`orca/use-client-cwd`) are offered only when the client advertised
`clientCapabilities.session.configOptions.boolean`. Changing `orca/workflow` re-sends
`available_commands_update` so the `/run` hint names the chosen workflow.

**Models are discovered lazily (#189).** `orca/model` starts from each agent's declared
`AgentSpec.models` (or the single "Agent default"); when an agent's first downstream session
opens, the options that session advertised replace the declaration and every open facade
session receives a `config_option_update`. The result is cached per agent for the facade
process's life, so a second session does not re-probe. The engine exposes this moment as
`Orchestrator.onAgentSessionOpened(listener)`, an in-process hook that hands over the live
session (the persisted `agent.session.opened` event carries no session). Downstream options
in the other reserved categories are proxied as `orca/<agentId>/<configId>`; they are
recorded on the session, but the run's override record has no field for them yet, so
choosing one changes nothing downstream in this release.

**How a selected model reaches the agent (#187).** Whatever surface chose it — `orca/model`
here, `--model` on the CLI — the run records it as `overrides.model`, and the engine applies it
right after `session/new` and before any turn: through the session's `category: "model"`
config option when the agent offers one, or, for an agent that offers none, only if the id is
in the agent's declared `models` (there is nothing to set, so it is recorded as declared). An
id in neither place fails the step with `AGENT_MODEL_NOT_FOUND`, listing what is available, and
is not retried. With `sessionMode: per-run`, a pooled session whose model has drifted from the
run's selection (the agent switched it itself) is **re‑applied** with `session/set_config_option`
before the next step and the re‑apply is logged as an agent update; if the agent refuses, ORCA
closes the pooled session and opens a fresh one. T3 Code threads offer no config options, so a
model override on a T3‑backed agent passes only when it is declared in `models`. The model a
step ran on is on `agent.session.opened`, in `orca status` and in the daemon's step view.

Implementation: `packages/integrations/src/acp-facade/`. Workspace selection:
`workspace: { provider: kepler }` in `orca.config.yaml` makes ORCA use the task's worktrees
(`KeplerTaskWorkspaceProvider` scans the task dir for `*/.git`, picks by work item `repo`,
else the worktree the parent workspace already sits in, else the first worktree, else the
parent workspace or the task directory itself). Sub‑agents launched by ORCA can still be given Kepler's MCP server
via `agents[].mcpServers` so they keep the task's resource list honest.

### Mode B — ORCA beside Kepler (side‑car)

From a shell inside a task folder: `orca kepler` shows what ORCA sees (task id, title/body
from `AGENTS.md`, worktrees); `orca submit "$(head -1 AGENTS.md)" --body-file AGENTS.md`
drives the task through the program workflow using the task's worktrees.

The same selections a Kepler session makes through config options are flags here, so a
script and a person drive one mechanism: `orca run <wf> --agent <role>=<agentId>
--model <agentId>=<modelId>` (both repeatable; `--model <modelId>` alone when exactly one
agent is in play, otherwise the run is refused naming the agents), `--item-workflow <id>` on
`submit` and `plan dispatch`, and `--template-pack <name>` on all three. They become the
run's selection record (#186), and an unknown role, agent, model or workflow fails with the
known set before the run starts. `orca agents` lists each agent's declared models with the
default marked; models a running daemon has discovered are shown when `agents.list` carries
them, otherwise the line reads "not probed", because that command never spawns an agent.

### What Kepler does not expose (yet)

Kepler has no public API to create sessions or tasks from outside; the ACP‑agent route
is the supported way in. Kepler's remote‑agent support is "in development"; ORCA's SSH
host covers that gap today.

## T3 Code (groundwork — neither direction works yet)

[T3 Code](https://github.com/pingdotgg/t3code) is an open‑source, TypeScript control plane
for coding agents: a Node **WebSocket server** wraps provider CLIs (Codex app‑server,
Claude Code SDK, Cursor, OpenCode, …) behind an **event‑sourced orchestration model**
(`packages/contracts/src/orchestration.ts`: projects → threads → turns → checkpoints;
commands like `thread.create`, `thread.turn.start`, `thread.turn.interrupt`,
`thread.approval.respond`; events like `thread.message-sent`, `thread.activity-appended`,
`thread.session-set`). It is *not* an ACP client or agent.

ORCA's adapter (`packages/integrations/src/t3code/`) therefore maps ORCA's
`AgentSession` onto a **T3 thread**. The mapping is written; the transport under it
is not, so nothing below runs today:

| ORCA | T3 Code |
| --- | --- |
| `openSession` | `orchestration.dispatchCommand` → `thread.create` (project, model selection, runtime mode) |
| `prompt()` | `thread.turn.start`; resolves when `thread.session-set` reports no active turn or `thread.turn-diff-completed` reports the turn `completed` / `error` / `interrupted` |
| updates | `orchestration.subscribeThread` events mapped to `AgentUpdateSummary` |
| `cancel()` | `thread.turn.interrupt` |
| `close()` | `thread.session.stop` |

Once a transport exists, wire it in via `Orchestrator.sessionFactory` (route agents with
e.g. `hostId: t3code` or an `env.ORCA_T3_PROJECT` marker to `openT3CodeSession`, everything
else to `openAcpSession`). Artifact pickup keeps working because T3 threads run in local
worktrees the host FS can read. Until then a t3code session factory fails on first use:
the only shipped `T3CodeRpc` is `UnimplementedT3CodeRpc`, whose `call` and `subscribe`
both throw `NOT_SUPPORTED`.

**Left open on purpose:** the concrete WebSocket transport. T3 Code uses Effect RPC over
`/ws` with typed request/success/error envelopes and streaming subscriptions; `T3CodeRpc`
is the two‑method interface to implement (`call`, `subscribe`) once the envelope is pinned
to a version. `UnimplementedT3CodeRpc` documents the gap. T3's own contracts package
(`@t3tools/contracts` in the monorepo) is the right thing to depend on when publishing.

The other direction is equally unavailable: T3 Code cannot drive ORCA either, because it
has no ACP client. If T3 ever adds ACP agents as a provider, `orca acp` plugs in unchanged
— no work needed on ORCA's side.

## Remote agents over SSH

`hosts[]` entries of `type: ssh` run agents on another machine:

```yaml
hosts:
  - id: buildbox
    type: ssh
    host: build.internal
    user: ci
    identityFile: ~/.ssh/orca
    sshArgs: ["-o", "ProxyJump=bastion"]
    workspaceRoot: /srv/work
agents:
  - id: claude-remote
    command: claude-code-acp      # must be on PATH for a login shell on buildbox
    hostId: buildbox
    roles: [builder, tester]
```

How it works: ORCA spawns `ssh -T -o BatchMode=yes -o ConnectTimeout=20 [sshArgs…] [-p port]
[-i identityFile] ci@build.internal -- bash -lc 'cd <cwd> && exec [env K=V …] claude-code-acp'`
(`bash -lc` is the default `remoteShell`); the child's stdin/stdout carry ACP's
newline‑delimited JSON‑RPC, so the
remote agent is indistinguishable from a local one. File access for artifact pickup and
`fs/*` requests goes through short `ssh … cat|test|mkdir` commands (`SshFileSystem`); the
`git-worktree` workspace provider runs `git worktree add` on the remote via `exec`.

Requirements: key‑based auth (no prompts), the agent binary on the remote login‑shell PATH,
and the repository present on the remote (clone it there, or use a shared filesystem; ORCA
does not sync code). Verify with `orca ping claude-remote`.

## Other ACP clients (Zed, JetBrains, …)

Anything that can launch an ACP agent can launch `orca acp`. The facade advertises
`loadSession: false` and prompt capabilities `embeddedContext: true` (so file context can be
attached to requests).

Plain-text submissions settle their Request from the final program outcome, just as CLI
submissions do: a failure outcome is failed even when interpretation completed, cancellation
is cancelled, and a paused run leaves the Request decomposing. Direct `/run` commands do not
create a Request. Plan updates suppress identical snapshots and label failed, cancelled and
skipped steps explicitly (ACP has no separate failed plan-entry status). Child-run nodes are
flattened beneath their owning container entry and carry their workflow-chain prefix.

## TypeSafe JEV evaluation (`custom:jev-eval`, proof of concept)

[JEV](https://docs.typesafe.ai/introduction) answers typed questions about a piece of text
without generating any: a **Choice** among fixed options, a **Score** on an ordered rubric,
or a **Noul** (the probability a proposition holds), each with the model's distribution over
the outcomes. ORCA already separates the artifact an agent produces from the decision made
about it, so a narrow semantic judgment can sit in that seam without opening an agent
session: an artifact-producing step, an optional `custom:jev-eval` node, a durable
`evaluation` artifact, and then an ordinary `decision` node. The pilot and its boundaries
are issue #286; this node is the proof of concept (#296).

The node ships as a plugin in `@orca/integrations`, so a workflow that never mentions it is
untouched and a configuration without it loads exactly as before.

### Setup

```yaml
# orca.config.yaml
plugins: ["@orca/integrations/jev-eval"] # from source: "./packages/integrations/src/jev/plugin.ts"
```

```sh
export TYPESAFE_API_KEY=...        # required to evaluate; loading the plugin needs nothing
export ORCA_JEV_MODEL=jev-1.13.0   # optional default; a node's `model:` wins
export TYPESAFE_BASE_URL=...       # optional; the API's origin, for a proxy or a fake
```

The key is read when a node runs, goes into the request's `Authorization` header, and is
written nowhere: not the artifact, not the step result, not the event log, not an error
message. A test asserts that. `createJevEvalPlugin({ apiKey, model, baseUrl, provider })`
does the same from code, and `provider` replaces the HTTP client with anything that
implements `JevProvider` — the scripted one the tests use, for instance.

### The node

```yaml
  coverageCheck: # expressions read it as `steps.coverageCheck.…` (a hyphenated id needs `steps['coverage-check']`)
    type: "custom:jev-eval"
    model: jev-1.13.0 # a version, never `jev-latest`
    inputs: # explicit refs, resolved like an agent node's; each becomes state.artifacts.<alias>
      - { kind: implementation }
      - { name: testReport, as: report }
      - { kind: review, required: false } # a missing optional input is recorded as missing
    context: # extra state.context.<key> sections, each a template
      acceptance: "{{#each workItem.acceptanceCriteria as c}}- {{ c }}\n{{/each}}"
    rubric: { id: sdlc/coverage, version: 3 } # the questions' identity, recorded with every answer
    questions:
      addressed:
        type: score
        instructions: "How many acceptance criteria does the implementation summary explicitly address?"
        criteria: ["None", "Some; at least one is not mentioned", "All of them"] # 2..10 levels, low to high
      conflict:
        type: choice
        instructions: "Do the summary and the test report agree about what was verified?"
        criteria: # 2..255 options; ids become `choice == '<id>'` edge tests downstream
          consistent: "They describe the same verification."
          contradiction: "One names a test as passing that the other reports failed."
      cites_evidence:
        type: noul
        instructions: "Does the review cite specific files, lines or test results?"
        criteria: { true: "Names locations it checked", false: "Paraphrases the summary" }
    maxStateChars: 96000 # default; over it the step fails, nothing is truncated
    timeoutMs: 60000 # default
    onError: fail # default; `record` is for shadow mode (below)
    produces: { kind: evaluation, name: coverageCheck } # defaults: kind evaluation, name = node id
```

The executor validates these fields with zod twice: when the workflows are loaded, so
`orca validate` and bootstrap report a missing `rubric:` or a `model: jev-latest` under the
node's path before any agent has run (#308), and again at the top of `execute`, where a node
that arrived unvalidated fails with `WORKFLOW_INVALID` before calling anyone. It then
resolves the inputs, renders the context, builds
`{ artifacts: { <alias>: <content> }, context: { <key>: <text> } }`, and refuses to send it if
the JSON is over `maxStateChars`. Every field of the response is checked against the
questions: the answer ids must be exactly the question ids, a choice must be an offered
option, a score must lie in `[0, levels - 1]`, every probability and confidence must be a
finite number in `[0, 1]`, and a distribution must cover exactly the options and sum to 1.
Anything else is `JEV_RESPONSE_INVALID`, not retryable, and no artifact is recorded. A
response from a model other than the one pinned is `JEV_MODEL_MISMATCH`.

### The artifact, and what downstream reads

A successful node records one `evaluation` artifact whose `parents` are the inputs it
judged and whose front matter is the whole record: `rubric`, `questions` as sent,
`model: { requested, resolved }`, `inputs` (alias, artifact id, name, kind, version, content
hash, byte size), `missingInputs`, `stateChars`, `answers`, `usage` (input and output tokens)
and `evaluatedAt`. The body is a table for a person. The judged content is referenced by
id and hash, not copied, so the artifact stays small.

The same record is the step's `result.data`, plus `artifactId`, which is what expressions and
decision nodes read. A decision on one answer names the artifact and a dotted path into it,
which ties the decision to the evaluation rather than to the node that produced it (#309);
an expression is for arithmetic over an answer:

```yaml
  route:
    type: decision
    source: { kind: artifact, artifact: coverageCheck, field: answers.conflict.choice }
    options: [consistent, contradiction]
  cited:
    type: decision
    source: { kind: expression, expr: "steps.coverageCheck.result.data.answers.cites_evidence.noul >= 0.9 ? 'yes' : 'no'" }
    options: [yes, no]
```

An answer is `{ type: "noul", noul }`, `{ type: "choice", choice, probabilities, confidence }`
or `{ type: "score", score, probabilities, confidence, levels, normalized, legend? }`.
`levels` and `normalized` (`score / (levels - 1)`) are ORCA's arithmetic, added so scores on
different rubrics compare on one scale; every other field is the provider's. The threshold,
the comparison and the edge are the workflow's, in a decision node, where they are
deterministic and reviewable. The model never picks an edge.

### Shadow mode: `onError: record`

The pilot runs *beside* the existing reviewer, not instead of it, and a pilot must not fail
the run it is observing. With `onError: record`, a provider error, an over-sized state, a
missing required input or an invalid response completes the step with
`data.status: "failed"`, `data.error: { code, message }`, **no** `answers`, and an
`evaluation` artifact saying the same. A decision that reads a missing answer falls to its
`defaultOption` (and fails without one), which is the intended behaviour: an unanswered
question is never an approval. `examples/jev/` is the worked version — the shipped
`ai-sdlc` with a `jevShadow` node between `review` and `review-verdict`, the verdict still
the reviewer's, and the answers lifted into `vars.jevShadow` for a summary to read:

```sh
export TYPESAFE_API_KEY=...
pnpm run orca --config examples/jev/orca.config.yaml validate
pnpm run orca --config examples/jev/orca.config.yaml run ai-sdlc-jev-shadow --var workItem='{"id":"wi_1","slug":"x","title":"…","acceptanceCriteria":["…"]}'
```

Under `onError: fail` (the default), `maxAttempts:` on the node retries what the API says
to retry — 429, 529, 5xx, a network error, a timeout — and nothing else.

### Bounded input, and what the model is not for

`docs.typesafe.ai/models` gives 64k tokens per request and 32k for the state plus the longest
question; the node's `maxStateChars` default of 96,000 characters sits under that for prose.
The bound is a failure, not a truncation, because a judgment over half an artifact is a
judgment over something nobody wrote. Select the artifacts a question is about — a
summary, a report, a review — rather than a diff or a transcript, and keep the questions
one dimension each: the model reads instructions literally, treats irrelevant state as a
distractor, and is not a calculator or a date parser
([known limitations for jev-1.13](https://docs.typesafe.ai/model-jaggedness/jev-1.13)).
Per #286, do not ask it what authoritative data already answers (whether tests passed is
in the test report's front matter; whether a dependency is satisfied is in the plan), do
not let it stand in for repository review, and treat a judgment over an agent's summary as
a judgment of what the summary *claims*.

### Two confidences

Two things in ORCA are called confidence and they are not the same quantity:

- **Model confidence** (`answers.<id>.confidence`, on a choice or a score) is a statistic of
  the returned distribution — 1 when all the probability sits on one outcome, 0 when it is
  flat. A noul has no separate confidence; its single value *is* the probability. Neither is an
  accuracy rate: a confidently wrong answer reads exactly like a confidently right one until
  calibration (#299) says how often each happens on ORCA's own evidence.
- **Decision-matrix ranking confidence** (`steps.<matrix-node>.result.data.confidence`,
  `docs/PLANNING.md`) is `clear`, `close` or `tie` from the *margin* between the top two
  weighted sums — arithmetic over scores people or agents wrote, with no model involved.

A gate can route on either. It should not treat one as the other.

### Known limitations of the proof of concept

- One request per node, no batching across nodes, no caching of identical questions.
- Retries are the interpreter's `maxAttempts`; there is no backoff schedule of its own, and a
  resumed run re-asks rather than reusing an in-flight answer (#297).
- Questions are literal YAML on the node; there is no shared rubric registry, no authoring
  aid and no inspection surface in the app (#298).
- No thresholds are recommended. Every one is per question, per model version and per
  consequence, and none has been measured on ORCA workloads yet (#299).

### Live smoke

The test suite never touches the network. To prove a real answer lands as a real artifact:

```sh
export TYPESAFE_API_KEY=...
ORCA_JEV_LIVE=1 pnpm exec vitest run packages/integrations/test/jev-eval.live.test.ts
```

It runs the same seeded workflow the scripted tests use against the API (one request of
about 500 input tokens), asserts an `evaluation` artifact with the pinned model, a choice
from the offered options, a three-level score and a noul, and prints the answers. Without
both variables the file reports as skipped.
