# Synthetic fixtures and their expected results

Every value here is invented. Fixed UUIDs, versions and metadata make exact-byte review
repeatable; they are not a captured report, random-generator test or candidate identity.
No real secret, project path, host, account or user data is included. Reserved `.invalid`
names and `192.0.2.42` are synthetic negative inputs, never allowed output.

## Invalid complete candidates and parser inputs

Every file in [invalid](invalid) must be rejected. Unknown fields are rejected, not silently
removed. Rejection diagnostics are fixed categories and must not echo the unsafe value.

| Files | Expected rejection |
| --- | --- |
| `unsupported-version`, `unknown-field`, `nested-field` | `schema`: no version fallback or nested extra keys |
| `path-in-enum`, `version-content`, `error-object` | `schema`: no content-bearing value in a safe slot |
| `missing-required`, `null-unknown`, `boolean-number`, `one-shot-window`, `phase-code` | `schema`: exact types, unknown semantics, limits and phase/code pairs |
| `dangling-alias` | `dangling_alias`: no unresolved alias |
| `outside-window` | `event_order_or_window`: event outside represented time |
| `duplicate-alias` | `duplicate_alias`: alias uniqueness across entity kinds |
| `store-format-without-handshake`, `protected-state-without-handshake`, `protected-observation-without-handshake` | `unobserved_claim`: store facts/observation require handshake evidence |
| `unobserved-claim` | `unobserved_claim`: known admission without observation |
| `reused-identifier` | `identifier_reuse`: report/session IDs must differ |
| `duplicate-key` | `duplicate_key`: parser ambiguity fails even when duplicate values agree |
| `nonfinite` | `non_integer_number`: parser rejects NaN, not a JSON value |

The last two files use `.txt` because they intentionally contain duplicate keys/nonstandard
JSON. Do not run a formatter that repairs or rewrites negative fixture bytes. A local
Prettier override preserves exact valid fixture bytes using its `json-stringify` parser.
Other invalid candidates use
readable object ordering; schema/semantic rejection happens before canonical-byte checks.

[privacy-cases.json](privacy-cases.json) supplies 15 schema-injection recipes: nested,
base64, percent-encoded, Unicode-escaped and fragmented synthetic secrets; POSIX, Windows
and UNC paths; URLs/headers; nested error/cause/stack objects; ciphertext; private title;
predictable-ID hash; IP; and huge newline-free data generated by bounded repetition.
The 14 bounded cases reject as `schema`; huge input rejects as `byte_limit` before decode.
They inject into a would-be output slot, not into any real collector. Future producer
expectation for every case: **exclude source without reading it**, regardless of scanning.

Six pipeline design cases additionally require no export/raw fallback on sanitizer or
scan throw/hang, reject a projection with unknown fields, and preserve missing safe evidence
as unknown with omission accounting. All six remain `runtimeStatus: not_run`; the checker
only verifies their declarations, not timeout handling, sanitization or source exclusion.

Dynamic checker tests exercise byte ceilings at 262,144 and 262,145 bytes (whitespace at
the exact ceiling still fails canonical form), invalid UTF-8, excessive nesting, exponent/
fraction representations, trailing JSON, maximum and overflow event/alias counts, reversed
time order, trailing-newline regex attacks, unknown fields at every object level and
unobserved daemon facts. There is no multi-megabyte committed fixture or unbounded recipe.

## Consent and retention state oracles

[state-cases.json](state-cases.json) holds 29 named traces with expected capture/storage/
export outcomes, zero external diagnostic requests, and zero execution mutations. They
cover default-off/refusal, scoped one-shot/non-sticky consent/deadline, cancel/back/retry,
separate rolling consent and snapshot, opt-out including ready preview, restart, expiry,
wall-clock changes and uncertain monotonic time, sleep/wake expiry, bounded buffer, full
disk, deletion failure, missing key, unverifiable ACL, save failure, sanitizer throw/hang,
and failed key revocation.

Each trace starts in the off state; consent events abbreviate the disclosure/acceptance
sequence and `confirm_export` includes choosing/reviewing the local destination unless a
case explicitly cancels it. `safe_event` means already minimized/validated data.
`purged_key_revoked` means both operations succeeded in this oracle; cleanup-pending and
key-revocation-pending must remain distinct when failures are injected. External traffic
excludes authorized local app/daemon projection IPC, which has its own trust tests.

**These are design oracles, not an implemented state machine.** The Python tests confirm
fixture declarations and schema behavior only; no real consent, retention timer, disk,
key/ACL, network or execution state is driven. Later #416 tests must execute each trace
against the actual implementation and fill a separate result record.
