Electron's [safeStorage API](https://www.electronjs.org/docs/latest/api/safe-storage) says synchronous macOS calls can block on Keychain access, macOS identity depends on consistent code signing, Windows protection is DPAPI user-bound but accessible to other apps in that user context, and Linux can select `basic_text`. The current documentation recommends asynchronous APIs, which expose temporary unavailability and rotation signals; verify availability and behavior against locked Electron `44.4.5` and packaged builds before choosing an adapter. Merely calling `safeStorage.encryptString` on each checkpoint gives app/OS-managed protection, not a diagnostics-only key that can be revoked independently. Windows [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) can also be configured machine-wide, which would widen access; no such mode is approved. Windows files inherit DACLs at creation unless a security descriptor is supplied; Node mode bits are no proof of owner-only access ([Microsoft file security](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)).

## Candidate key and publication shapes for review

| Shape | Benefit | Question or cost before selection |
| --- | --- | --- |
| Direct `safeStorage` ciphertext for each checkpoint | Small app-main dependency surface, with existing native smoke pattern | No independently deletable diagnostics key; deleting ciphertext does not revoke the app's OS key, and backup/copy semantics remain. This cannot satisfy an independently revocable key requirement by assertion. |
| Fresh diagnostics data key, wrapped by `safeStorage`, with authenticated checkpoint ciphertext | Separate domain and potential crypto-erasure by deleting only the wrapped key; existing OS facility is reused | Decide session/key lifecycle, crash recovery, rotation, orphan/backup semantics, and whether wrapper deletion is an acceptable revocation claim. Need secure bounded memory and authenticated binding of generation/session/format. |
| Dedicated native Keychain item / DPAPI-protected diagnostics key | Explicit key namespace/lifecycle and potentially clearer revocation | Requires a supported native adapter, stable signed identity, Windows user-scope and DACL verification, packaged Mac/Windows tests, and migration/update behavior. Do not assume a Keychain item delete erases snapshots or backups. |

A candidate checkpoint protocol can write only already minimized and validated records to an operation-owned exclusive temporary file, flush it, then publish a bounded encrypted generation under a dedicated diagnostics directory. Its recovery reader should accept only a fully authenticated, versioned generation and reject truncated, tampered, wrong-session or unknown-format bytes without exposing source data. Replacing a sole checkpoint by rename can preserve a previous complete generation on process interruption, but whether it survives power loss needs a stronger platform/filesystem claim. POSIX directory `fsync` after publication is used by existing code; it is not available through that Node pattern on Windows. A pointer/manifest, generation slots, backup generations, and non-overwriting publication each change the retention/space/cleanup contract and should be evaluated after the owner selects previous-session count and total on-disk budget. An interrupted write can leave an owned temporary file; startup must bound discovery and cleanup instead of interpreting it as recoverable history. No file should be created before capture consent, and there is no plaintext spill, raw-log fallback or execution-store dependency.

Path checks must cover the selected directory and every opened/published object against symlinks/reparse points, owner and effective rights, including races. `O_NOFOLLOW` in the protected-store reader is useful on POSIX but does not by itself verify ancestor components or Windows reparse behavior. A local plaintext export has its own destination and access policy; it must be an exclusively created operation-owned temporary file and publish the *same immutable preview bytes* only after current grant/generation/destination revalidation. Whether an existing final file must be refused instead of overwritten is part of the pending destination/save decision. A cancellation after publication must report saved status honestly; cleanup never removes a user-selected saved file.

## Interface and failure model to freeze with the lead

This analysis follows the seven operation boundaries frozen by the lead in `integration-contract.md`: safe ingress, capture authority, checkpoint adapter, recovery intake, frozen preview, local save and diagnostic-only failure channel. The seam should be app-main-owned and injectable for tests. These are roles, not competing shared TypeScript exports or a selected persistence design:

- **Capture admission** accepts only a closed, validated safe observation plus current consent generation; returns accepted or a fixed omission category. It cannot accept arbitrary JSON, raw errors, logs, paths, or renderer-supplied content. Any queue is bounded; dropped work increments a bounded omission counter.
- **Checkpoint request** consumes one immutable bounded snapshot and generation, returning `committed`, `superseded`, or a fixed diagnostic-only failure category. The result states what was published, not that all events up to request time are durable. A crash may lose both queued observations and a checkpoint in flight. The owner must approve the disclosed interval and tail-loss wording, including scheduler and I/O delay.
- **Recovery inspection** on fresh startup returns `none`, `candidate`, `expired/uncertain`, `unreadable`, or `cleanup-pending` with no plaintext IPC. Only an authenticated, within-policy candidate may produce a separately authorized immutable preview. Restart begins capture off; whether a previous candidate is visible before renewed capture consent awaits an owner answer.
- **Revoke/delete** fences the consent generation first, rejects queued and in-flight publication, invalidates preview/save handles, then attempts key and owned-file cleanup. Report key and file outcomes separately. A successful file unlink cannot promise physical erasure of SSD/backups; a failed unlink cannot be called successful deletion. No execution key or shared app material is touched.
- **Exact export** takes an opaque ready-preview handle, the frozen bytes, current grant/generation and a validated destination. It never recollects or reserializes. Its result distinguishes no publication, final publication, and cleanup-pending; it never sends data over the network.

Only fixed error categories should reach UI or diagnostic counters: secure store unavailable, permission/path unsafe, capacity or deadline exceeded, corrupt/unsupported record, partial publication, deletion incomplete. Underlying exception text, paths, ciphertext and keys stay out of the bundle and logs. Storage errors must stop or omit diagnostics without waiting on execution locks or changing admissions, runs, gates, retries, or app credentials. A main-thread Keychain prompt, synchronous `fsync`, or unbounded scan would violate that isolation even if caught later; schedule and time work accordingly.

The approved five-minute default is a lookback setting only. The capacity result from #455 (4,096 offered events retained 238.95 seconds in its burst) and its tmpfs write cannot prove complete coverage or disk durability. Surface requested versus observed coverage, capacity omissions, and a possibly missing post-checkpoint tail. Repeated failed checkpoints must extend the visible uncertainty rather than silently claiming a fixed maximum loss.

## Evidence still needed

- Synthetic state/fault harness: default-off/no file, generation fencing during queued write/opt-out, interrupted writes before/after publication, corrupt/truncated/unknown-format input, unavailable/lost key, full disk, unsafe path, cleanup failure, expiry and uncertain clock. Assert unchanged execution progress beside each fault.
- Disposable actual Electron profiles: separate graceful restart and forced main-process termination around checkpoint boundaries; inspect files/keys and exact preview-to-export bytes. OS/power-loss durability is a separate physical claim, not inferred from either test.
- Native packaged Mac: stable signed identity and Keychain prompts/unavailability/update, owner and ancestry checks, process kill, sleep/wake and actual disk behavior. Native packaged Windows: DPAPI user scope, owner SID/effective DACL including inherited grants, reparse/replace behavior, second ordinary account, and save destination. Linux mock/tmpfs data cannot substitute.
- Paired execution load: bound snapshot, encryption, flush and cleanup latency, event-loop delay, heap and disk including preview copies; compare measured loss with the approved tail disclosure. Observe diagnostic network traffic separately. Keep exact candidate SHA, OS/build and pass/fail/blocked/not-run status.

The lead owns any eventual shared interface, schemas, exports, app bridge, consent state and integration. This note introduces no runtime API or policy-dependent persistence.
