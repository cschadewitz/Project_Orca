# Crash-recovery storage research for #469

Engineering research updated 4 October 2026 after the [consolidated decisions and engineering gates](https://github.com/cschadewitz/Project_Orca/issues/469#issuecomment-5976190374). The lead-owned [integration contract](integration-contract.md) is the authoritative engineering specification; this note explains its storage constraints and evidence gaps, and creates no competing runtime interface. Product choices are now recorded: one previous opted-in session after a main/full-app crash, up to 24 hours of checkpoint retention, clean-exit removal of the current checkpoint, persistent explicit opt-in with default off, approximately five-second checkpoints with one write in flight, 1–15-minute lookback with a five-minute default, 1 MiB complete canonical report and 8,192 events, and separate OS-protected diagnostics keys. No power-loss guarantee or upload permission exists. These choices do not satisfy technical/privacy review, actual user consent or independent/native acceptance.

Electron's [safeStorage API](https://www.electronjs.org/docs/latest/api/safe-storage) says synchronous macOS calls can block on Keychain access, macOS identity depends on consistent code signing, Windows protection is DPAPI user-bound but accessible to other apps in that user context, and Linux can select `basic_text`. The current documentation recommends asynchronous APIs, which expose temporary unavailability and rotation signals; the lead confirmed these API declarations in installed Electron `44.4.5` types, but actual packaged behavior still needs verification. Merely calling `safeStorage.encryptString` on each checkpoint gives app/OS-managed protection, not a diagnostics-only key that can be revoked independently. Windows [DPAPI](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata) can also be configured machine-wide, which would widen access; no such mode is approved. Windows files inherit DACLs at creation unless a security descriptor is supplied; Node mode bits are no proof of owner-only access ([Microsoft file security](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights)).

## Key lifecycle and publication rationale

Use a fresh random diagnostics data key for each newly captured session, protected by the reviewed OS-wrapped adapter in the integration contract. Encrypt reports with authenticated encryption that binds format/schema, session, authority generation, checkpoint sequence and immutable age information. Unique nonces and generation checks prevent ciphertext substitution or reuse across sessions. Only bounded canonical bytes enter encryption. Direct `safeStorage` encryption of whole reports is insufficient for independently deleting diagnostics-owned key material because its shared app key is not diagnostics-owned.

Creation follows the persistent setting's current-version explicit opt-in and secure-storage/path preflight. A restarted app can use the remembered setting for new capture; it never reuses a prior session's data key for that new session. Recovery unwraps only its matching key, and only within the age/current-authority checks. Key loss, unavailable secure storage, authentication failure or a rotation requirement never cause replacement of a missing key over old ciphertext, plaintext fallback, credential repair or an execution failure. The first implementation must establish the exact async adapter behavior in locked Electron `44.4.5` and packaged builds; synchronous main-thread Keychain access is not an acceptable fallback. Any wrapper rewrite preserves session identity and the original age deadline.

Opt-out first fences publication and unsaved preview/save authority, then releases plaintext and removes diagnostics-owned wrappers and retained files. Cleanup reports key and file outcomes separately. No shared safeStorage/Keychain item or execution key is deleted. Loss of the wrapper prevents the app's normal decryption path but is not forensic erasure: same-user compromise, copies, snapshots, backups and runtime string copies remain limitations. JavaScript cannot promise physical zeroization of every key copy.

A checkpoint transaction reserves aggregate capacity before allocating its immutable snapshot or creating its operation-owned exclusive encrypted temporary file. It flushes and authenticates the new generation, then publishes under a serialized diagnostic authority gate after rechecking consent, session, expiry and expected predecessor. Only the previous complete generation may remain recoverable if interruption occurs before publication. Temporary/uncommitted generations never become recovery candidates by directory scanning. A manifest or pointer is a commit record, not a third history slot; its replacement, old bytes and key-wrapper staging all consume the same aggregate budget. Cleanup failures retain their charge and suppress further writes before the ceiling can be exceeded.

The current and single previous logical session must be distinguished from temporary generation duplication during replacement. Retiring an older previous session invalidates its preview/save handles before publication can make a newer session recoverable. On a new crash, recovery selects the immediately preceding eligible opted-in session and retires the older one; it must not accumulate a session per restart. Clean exit removes only the current session's checkpoint and key. Existing previous history keeps its unchanged deadline until expiry, replacement or explicit discard/opt-out. The lead's contract specifies the exact ordering and failure states, including what happens if cleanup prevents replacement.

## Age, resource and file-safety rationale

Retention is an upper bound, not a lease renewed on open. Authenticate checkpoint capture time and a fixed expiry no later than capture time plus 24 hours. This is conservative relative to an unobservable crash instant. Copy, preview, reopening and recovery rewrapping preserve that deadline. The contract requires a native, same-boot, suspend-inclusive elapsed clock plus authenticated private boot identity. Wall-clock arithmetic, file mtime and a stored high-water mark cannot establish elapsed age across reboot. A changed or unavailable boot identity, regressing clock or uncertain elapsed time makes recovery unavailable; there is no wall-clock-only fallback. This conservatively supports main-process crash recovery without promising recovery after an OS reboot. New live checkpoint snapshots receive their own capture anchor; reopening or rewrapping an existing snapshot never resets it.

Apple documents [`mach_continuous_time`](https://developer.apple.com/documentation/kernel/1646199-mach_continuous_time) as advancing during sleep, unlike `mach_absolute_time`. Microsoft's [interrupt-time documentation](https://learn.microsoft.com/en-us/windows/win32/sysinfo/interrupt-time) distinguishes sleep-inclusive interrupt time from unbiased interrupt time that excludes sleep. These APIs support the direction, not a completed adapter: native review must establish unit conversion, same-boot stability across processes, sleep/hibernate/Fast Startup behavior and a reliable boot identity. Until those are proven, native recovery remains gated. Boot identity is internal encrypted storage metadata, never producer content, renderer IPC or exported report data. The associated user disclosure and all exact age rules belong to the single integration contract.

The 1 MiB cap includes the complete uncompressed canonical envelope, formatting and all omission/coverage metadata. The 8,192-event cap is independent. Drop the oldest eligible events when either limit wins; do not truncate an exact preview or silently impose a smaller save cap. Aggregate retained disk accounting also includes ciphertext/authentication overhead, current and previous generations, wrapped keys, commit records, temporary files and undeleted leftovers. Explicitly reviewed local export may briefly use a restricted-access plaintext temporary file; charge that separately and also state the aggregate unsaved disk ceiling. User-owned published exports are outside automatic retention/deletion.

Memory accounting must cover the ring, immutable checkpoint, encryption/decryption buffers, canonical UTF-8 bytes, JS strings/objects, IPC and renderer preview copies, queues, counters and native/external allocation. A serialized cap or sampled heap figure does not enforce process RSS. The integration contract owns numerical reservation limits, measured incremental-heap targets and operation deadlines. Reserve before work, allow one active checkpoint and one frozen preview, coalesce checkpoint requests without queuing snapshots, and keep timed-out work charged until actually released. A Promise timeout cannot cancel a native call: late results must be fenced, and a stalled operation cannot permit a fresh unbounded chain of workers. No diagnostic task waits on execution locks or blocks ordinary execution.

Path checks cover the selected directory and every opened/published object against symlinks/reparse points, owner and effective rights, including races. POSIX `O_NOFOLLOW` alone does not verify ancestor components or Windows reparse behavior. Windows Node mode bits do not prove an owner-only DACL. A local export uses an exclusively created operation-owned temporary file and publishes the same immutable preview bytes only after current grant/generation/destination revalidation. The destination must never be overwritten merely because a picker returned it. Publication and revocation have a single serialized ordering: if native dispatch won, report pending until its outcome is known, then report actual success/failure without deleting a user-owned final file; if revocation won before dispatch, publication is refused and only settled, owned temporary bytes are cleaned up. Native guarantees for no-clobber publication and path-race resistance remain acceptance gates.

## Interface and failure model to freeze with the lead

This analysis follows the seven operation boundaries frozen by the lead in `integration-contract.md`: safe ingress, capture authority, checkpoint adapter, recovery intake, frozen preview, local save and diagnostic-only failure channel. The seam should be app-main-owned and injectable for tests. These are roles, not competing shared TypeScript exports or a selected persistence design:

- **Capture admission** accepts only a closed, validated safe observation plus current consent generation; returns accepted or a fixed omission category. It cannot accept arbitrary JSON, raw errors, logs, paths, or renderer-supplied content. Any queue is bounded; dropped work increments a bounded omission counter.
- **Checkpoint request** consumes one immutable bounded snapshot and generation, returning `committed`, `superseded`, or a fixed diagnostic-only failure category. The result states what was published, not that all events up to request time are durable. A crash may lose both queued observations and a checkpoint in flight. The approved five-second target is not a maximum lost tail; disclose scheduler and I/O delay and time since actual completed publication.
- **Recovery inspection** on fresh startup returns `none`, `candidate`, `expired/uncertain`, `unreadable`, or `cleanup-pending` with no plaintext IPC. Only an authenticated, within-policy candidate may produce a separately authorized immutable preview. Restart respects the remembered explicit setting for the unchanged consent scope; a fresh process authority generation is still required. Candidate visibility and explicit preview follow the lead-owned contract, not automatic preview or save.
- **Revoke/delete** fences the consent generation first, rejects queued/not-yet-dispatched publication, invalidates preview/save handles, then attempts key and owned-file cleanup. Already-dispatched native publication remains pending until its actual outcome is known, can complete after revocation, and cannot restore logical authority. Never report cleanup complete while any stale write can still appear. Report key and file outcomes separately. A successful file unlink cannot promise physical erasure of SSD/backups; a failed unlink cannot be called successful deletion. No execution key or shared app material is touched.
- **Exact export** takes an opaque ready-preview handle, the frozen bytes, current grant/generation and a validated destination. It never recollects or reserializes. Its result distinguishes no publication, final publication, and cleanup-pending; it never sends data over the network.

Only fixed error categories should reach UI or diagnostic counters: secure store unavailable, permission/path unsafe, capacity or deadline exceeded, corrupt/unsupported record, partial publication, deletion incomplete. Underlying exception text, paths, ciphertext and keys stay out of the bundle and logs. Storage errors must stop or omit diagnostics without waiting on execution locks or changing admissions, runs, gates, retries, or app credentials. A main-thread Keychain prompt, synchronous `fsync`, or unbounded scan would violate that isolation even if caught later; schedule and time work accordingly.

The approved five-minute default is a lookback setting only. The capacity result from #455 (5,250 offered events, 4,096 retained, 1,154 evicted, and 238.95 seconds retained in its burst) and its tmpfs write cannot prove complete coverage or disk durability. That earlier 4,096-event measurement does not validate the approved 8,192-event ceiling. Surface requested versus observed coverage, capacity omissions, and a possibly missing post-checkpoint tail. Repeated failed checkpoints must extend the visible uncertainty rather than silently claiming a fixed maximum loss.

## Evidence still needed

- Synthetic state/fault harness: default-off/no file, generation fencing during queued write/opt-out, interrupted writes before/after publication, corrupt/truncated/unknown-format input, unavailable/lost key, full disk, unsafe path, cleanup failure, expiry and uncertain clock. Assert unchanged execution progress beside each fault.
- Disposable actual Electron profiles: separate graceful restart and forced main-process termination around checkpoint boundaries; inspect files/keys and exact preview-to-export bytes. OS/power-loss durability is a separate physical claim, not inferred from either test.
- Native packaged Mac: stable signed identity and Keychain prompts/unavailability/update, owner and ancestry checks, process kill, sleep/wake and actual disk behavior. Native packaged Windows: DPAPI user scope, owner SID/effective DACL including inherited grants, reparse/replace behavior, second ordinary account, and save destination. Linux mock/tmpfs data cannot substitute.
- Paired execution load: bound snapshot, encryption, flush and cleanup latency, event-loop delay, heap and disk including preview copies; compare measured loss with the approved tail disclosure. Observe diagnostic network traffic separately. Keep exact candidate SHA, OS/build and pass/fail/blocked/not-run status.

The lead owns any eventual shared interface, schemas, exports, app bridge, consent state and integration. This note introduces no runtime API or policy-dependent persistence.
