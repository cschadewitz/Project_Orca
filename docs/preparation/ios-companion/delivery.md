# Companion delivery and acceptance plan

This implements nothing. It translates the [recommendation](README.md) and [shared security contract](architecture.md) into proposed work for Casey and Cal. Estimates assume experienced engineers, a small approved catalog, one host and one active human enrollment per phone, compact text artifacts, existing authenticated ORCA runtime and no initial native Watch app, Android client, custom relay, new identity provider or full editor.

## Distribution and device support

Use Casey's **paid individual Apple Developer membership** for the TestFlight pilot. The Watch research task explicitly records an active personal membership; verify renewal/account-holder details before implementation. Individual enrollment supports distribution but publishes under the individual's legal name; standard membership is US$99/year. A free Xcode Personal Team is different and is not the intended distribution plan. Decide organization ownership before a broader product release. [Apple enrollment](https://developer.apple.com/programs/enroll/).

Inviting Cal to App Store Connect on an individual account does not make Cal a Developer Program team member with certificate/profile/key access. Casey owns signing and APNs custody until a supported organizational arrangement is chosen; give appropriate separate Connect roles, never share the Apple Account password. Apple supports requests to convert an individual membership to an organization subject to verification. [Roles](https://developer.apple.com/help/account/access/roles/), [membership changes](https://developer.apple.com/help/account/membership/updating-your-account-information/).

TestFlight allows up to 100 internal Connect users and 10,000 external testers; builds expire after 90 days, and the first external build is reviewed. Budget refresh/release work and expiry reminders. Ad hoc provisioning is useful for development, but needs registered devices and has a 100-device-per-product-family annual limit. For a sustained release choose public or unlisted App Store distribution; unlisted still requires review and its link is not access control. [TestFlight](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/), [devices](https://developer.apple.com/help/account/devices/devices-overview), [unlisted apps](https://developer.apple.com/support/unlisted-app-distribution).

**Proposed deployment floor: iOS 18**, conditional on actual devices and chosen APIs passing the spike; test the minimum and current OS. An iOS 26+ private pilot is a reasonable simplification if both phones support it. Do not silently choose a floor from a framework default. Inventory Casey's/Cal's phone models/OS, inherited Watch model/watchOS, pairing compatibility, cellular plan if any, and available Mac before commitment. iPhone first; compact SE-sized and large screens must work. iPad-specific UX, independent Watch, Mac and visionOS compatibility are not v1 acceptance claims; explicitly configure distribution availability.

Build SDK and deployment floor differ. Since 28 April 2026, App Store uploads require Xcode 26+ with iOS 26 SDK or later. Apple's current requirements table lists Xcode 27 on macOS Tahoe 26.6+; pin a supported stable Xcode/macOS image at implementation and recheck before submission. A newer SDK does not require all users to run that OS. TestFlight's current installation requirements and inherited Watch compatibility must also be checked before promising its use. [Upload requirement](https://developer.apple.com/news/upcoming-requirements/?id=04282026a), [Xcode requirements](https://developer.apple.com/xcode/system-requirements), [TestFlight device requirements](https://beta.itunes.apple.com/).

All packaged alternatives—SwiftUI, React Native, Flutter and Capacitor—need an Apple build/signing/distribution path. A PWA avoids that binary pipeline but needs secure web hosting/session/installation/update support. Xcode Cloud or EAS may reduce local infrastructure work; neither removes Apple entitlements, review or physical-device tests.

Prepare an isolated synthetic review host/demo journey, credentials or an Apple-approved full demo mode, complete review notes and a functioning backend during review. Explain remote workflow controls and keep arbitrary downloaded code execution off the phone. Follow background-use, IPv6 networking, minimum-functionality and notification-content rules. A Capacitor wrapper needs useful app behavior beyond a repackaged website. Push opt-in must not be required for foreground use. Review acceptance is unverified until submitted. [App Review Guidelines, especially 2.1, 2.5, 4.2 and 4.5.4](https://developer.apple.com/app-store/review/guidelines/).

Publish an accurate privacy policy and App Store privacy disclosures covering device/account identifiers, APNs registration, relay traffic and any diagnostics. Audit privacy manifests, required-reason APIs and included SDK signatures. Avoid analytics SDKs initially. Complete encryption/export-compliance questions for the actual shipped binary; no exemption is assumed here. If a future relay creates user accounts, Apple requires in-app initiation of account deletion; a host enrollment alone is not automatically account creation. [Privacy disclosures](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/), [SDK requirements](https://developer.apple.com/support/third-party-SDK-requirements/), [account deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/), [export compliance](https://developer.apple.com/help/app-store-connect/manage-app-information/overview-of-export-compliance/).

A future primary `ship-group:ios-companion` could identify client release work after agreement; notification/shared-runtime slices should retain their own single primary group and cross-reference it.

| P5a Read-only pilot release | Physical-device monitoring/notification/connectivity evidence, read-only security and accessibility acceptance, signed TestFlight delivery, privacy/review-host documentation and named support/revocation owners. Commands remain unavailable and server-denied. No write-MVP or public-launch claim. | P1, P2, N1 | 1–1.5 person-weeks |
| P5b Command MVP release | Extend P5a evidence to P4 commands, including fresh confirmation, acceptance-fence authority/revision checks, race/crash/replay and lost-response recovery. Revalidate affected device, accessibility, signing, privacy and support evidence for the exact command-enabled build. No public launch until full pilot criteria are met. | P5a, P4 | 1–1.5 person-weeks |

Total **17–26 person-weeks**, including shared runtime, notifications and client work once. Client-only work is roughly 6–10 weeks after contracts exist; it is not an extra line to add to the total. Allow roughly **20–34 person-weeks** with 20–30% contingency for unfamiliar Swift, native signing and unresolved acceptance defects. Two experienced contributors might deliver in 10–16 calendar weeks with backend/client parallelism, excluding waiting for hardware, security decisions or review; one contributor should plan roughly 4–7 months before contingency. These are planning ranges, not commitments or estimates based on measured implementation velocity.

For framework sensitivity, approximate client-only ranges after the safe backend exists are 6–10 person-weeks for SwiftUI or React Native/Expo, 6–10 for Capacitor, 8–12 for Flutter and 4–7 for a PWA. These overlap because lifecycle and command safety dominate. Assume an experienced maintainer of the selected stack; PWA's smaller range excludes native Watch integration and is not equivalent capability for less money. A stack change does not remove P1/P3/N1 server work, and these ranges must not be added to the SwiftUI total again.

The proposed dependency order is acyclic: P0 → P1/P2 fixtures/P3; P1 → connected P2/N1; P1+P2+P3 → P4; P1+P2+N1 → P5a; P5a+P4 → P5b. The #443 fix is now a satisfied upstream prerequisite when using current main, with regressions retained; it is not a reason to delay read-only monitoring or alerts. #460 gates relevant editing workflows, not harmless read workflows. P3 can work against the existing runtime without waiting for mobile UI. A secure read-only pilot can ship only after P5a acceptance over P1+P2+N1; it does not wait for P3/P4 and does not satisfy the full requested command MVP. P5a and P5b partition the original 2–3 person-week P5 allowance, leaving the total unchanged.

Later separately scoped work: native Watch low-risk review (roughly 3–6 additional person-weeks after hardware spike), custom command relay (4–8+ plus operations/security review), multi-host/account UI (2–4), Android (estimate only after framework decision), broader live approvals and protected revision composer (separate safety contract). Estimates overlap if scopes change; do not add every future row as an implied roadmap commitment.

N1 includes a single-host APNs sender. A hosted notification-only broker is smaller than the command relay but still needs separately estimated tenancy, registration and operations work; the 4–8+ range is for the command relay, not a mandatory notification charge.

## Cost assumptions and operating budget

USD before taxes, checked 3 October 2026. Assume two users, one host, existing paid Apple membership and usable Mac/phones, fewer than 1,000 commands/day and 1 GB/month of safe summaries/metadata, no large artifact proxying or SLA. Volume is a budgeting assumption, not measured load.

| Item | One-time or incremental cost | Recurring cost and qualification |
| --- | --- | --- |
| Engineering | 17–26 person-weeks; at an illustrative $100/hour × 40 hours, $68,000–104,000 opportunity/contract cost before contingency | 1–3 engineer-days/month for stable phone/shared pilot plus 3–8 days around major iOS/Xcode upgrades; hosted-service on-call/security response is additional |
| Apple membership, Xcode | $0 incremental if membership/equipment already available; Xcode/SDK license allowance $0 | $99/year total membership, about $8.25/month; same membership for phone and Watch, not per device/app |
| Missing Mac/test hardware | Estimate $800–2,500 after inventory and current quotes | Replacement/repair/power excluded; inherited Watch compatibility unknown |
| CI | Pipeline setup in engineering estimate | Xcode Cloud includes 25 compute hours/month; 100 hours $49.99/month. Alternative GitHub 500–1,000 billable standard macOS minutes at $0.062/min is $31–62 before allowances/storage. Choose one baseline, do not sum both by default. |
| VPN and domain | Setup in engineering; domain estimate $10–30/year if needed | Tailscale $0 eligible Personal or two Standard seats $16/month; existing homelab ISP/power separate |
| APNs sender on existing host | Shared N1 engineering and provider-key custody | No separate per-message APNs price identified in reviewed Apple program guidance; budget host operations. This is not a promise of a delivery SLA or zero total notification cost. |
| Optional broker/relay | Separate engineering estimate above | $10–30/month modest pilot allowance; $30–100+/month for redundant monitored deployment, excluding on-call, IdP, bandwidth spikes and support |

With existing equipment, eligible free VPN and included CI, incremental hosting can be near $0; total allocated membership is still $99/year and staff time remains. A two-seat paid VPN plus modest broker adds roughly $26–46/month before CI/domain; GitHub CI in the example adds $31–62. These are scenarios, not a single misleading all-inclusive price.

Official price anchors: [Apple membership](https://developer.apple.com/programs/enroll/), [Xcode Cloud](https://developer.apple.com/xcode-cloud/), [GitHub macOS pricing](https://docs.github.com/en/enterprise-cloud%40latest/billing/reference/actions-runner-pricing), [Tailscale](https://tailscale.com/pricing), [Lightsail compute](https://aws.amazon.com/lightsail/pricing/) ($5–7/month small Linux IPv4 examples), [Workers](https://developers.cloudflare.com/workers/platform/pricing/) ($5/month paid minimum, usage extra). Small compute price is not the cost of a complete reliable relay. Hourly labor rate, hardware, domain, maintenance and relay ranges are explicit estimates, not vendor quotes.

## Acceptance and security evidence

The following are **future release gates**, not tests this research ran. Run backend tests over real authenticated transport and durable stores, client contract tests against shared fixtures, simulator UI tests, and physical iPhone/Watch scenarios where Apple lifecycle and notification behavior matter. Preserve sanitized results with exact app build, daemon SHA/protocol, OS/device and network topology. Never use real credentials or private artifacts in uploaded evidence.

| Area | Required cases | Passing evidence |
| --- | --- | --- |
| Contract/version | Missing method, partial capability, unknown fields, incompatible major, changed target/principal, malformed/oversized reply | Accurate unavailable reason; no guessed RPC fallback, wrong-host display or mutation |
| Identity/enrollment | Reused/expired pairing, QR substitution, wrong audience, revoked/rotated credential, restore/reinstall, passcode removal, device key replacement, notification re-registration after revocation | Single consumption and verified device binding; no secret logs; restore/notification registration cannot create an approver; independent revocation works |
| Authorization | Casey/Cal/trigger ownership, workflow restrictions, artifact-to-run substitution, raw RPC bypass, revoke while lease/read awaits, read-only daemon | Deny before disclosure/effect and recheck under acceptance fence; no owner fallback or elevation from `runs.control` alone |
| Approval/replay | Double tap, same key/body, changed body/key, two clients with conflicting answers, stale evidence/options, old boot/turn, expired first attempt | One authoritative decision/receipt; stale conflicts require fresh review; no later callback receives old answer |
| Durability/uncertainty | Host crash before/after journal sync, first response lost before server ID, killed/locked app, damaged/missing receipt, storage full, old backup restoration | No false success; original intent enables authorized non-mutating lookup; read-only inspection has no dispatch; unresolved evidence remains unknown; no fresh key or duplicate run |
| Execution truth | Record-only stays parked, answer recorded then resume fails, accepted continuation blocked, #443 interleavings, terminal run versus stale receipt | Correct separate statuses; #443 deterministic regression passes; no blanket success from HTTP 200 or receipt settlement |
| Launch/cancel/resume | Workflow/config drift, typed/sensitive input, root isolation, cancellation racing completion/resume, child cancelled before parent failure, original execution authority revoked | Current reviewed target/effect only; partial tree cancellation shown accurately; no premature terminal claim; unsupported resume explains boundary; no shared checkout damage |
| Offline/reconnect | Airplane mode before and after send, app suspension, missed/out-of-order events, per-run sequence gap, old snapshot arriving after a newer event | Timestamped cache; no automatic draft sends; pending intents reconcile original identity; inbox converges through authorized current reads |
| Notifications/handoff | Duplicate/delayed/reordered/expired alert, permission denied, Focus, locked phone, phone absent, APNs token rotation/unregistered response, provider timeout, same/different-principal cross-device lookup | Generic payload and safe logs; functional inbox without push; original command/device attribution preserved; unauthorized lookup denied; no handoff acknowledgement, resubmit or Watch gesture answers a request; no unproved phone-off independence |
| Network | Wi-Fi/cellular, VPN off/another VPN, forced DERP, captive portal, IPv6-only, LAN permission denied, TLS expiry/rotation, wrong proxy/host | Useful reachability state; no ATS/certificate bypass; notification delivery never implies command reachability |
| Privacy/content | Canary secrets in vars, error, artifact, note and title; malicious Markdown/links; revoked access after cache; cache expiry/logout | No canary in push/log/export; inert bounded rendering; necessary omitted evidence disables decision; local sensitive cache minimized/protected |
| Accessibility/UX | VoiceOver, largest Dynamic Type, reduced motion, light/dark/contrast, compact screen, rotation, external keyboard, long/missing evidence | Readable consequence and host; no clipped unreachable action; status glyph and word; destructive action never default; truthful announcements |
| Distribution/operations | TestFlight install/update/expiry, signed archive provenance, daemon compatibility, independent recovery/revocation access, review-host journey | Reproducible exact build, documented renewal/support owner, scoped signing secrets, no real private host required for review |

**P5a release evidence:** run the contract/version, identity/enrollment, read authorization, offline/reconnect, notifications/handoff, network, privacy/content, accessibility/UX and distribution/operations cases on the supported physical devices and signed pilot build. Prove mutation attempts with read-only credentials are denied at the server, including direct calls; hiding controls is insufficient. Record device/OS/build/server versions, observed failures and the named support and independent revocation owner. Approval/replay, command durability, execution truth and launch/cancel/resume acceptance are deferred to P5b, not waived. P5b requires those command cases plus regression of affected P5a evidence on the exact release build.

Extend existing `control-methods`, `live-input`, `execution-resume-authority`, `operator-mutation-authority`, `operator-mutation-receipts`, admission and continuation runtime/transport tests. Existing desktop Vitest/Playwright acceptance remains useful server scenario evidence, not proof of iOS behavior. Swift Testing/XCTest can cover native logic/UI; React Native JS component tests do not execute native backing code, and Flutter standard integration tests need additional handling for native notification/permission UI. [Apple testing](https://developer.apple.com/documentation/xcode/testing), [React Native testing](https://reactnative.dev/docs/testing-overview), [Flutter testing](https://docs.flutter.dev/testing/overview).

Keep server/TypeScript checks on existing Linux CI. Add pinned macOS/Xcode builds and simulator checks, with signing only in protected release environments, never untrusted PR jobs. Archive exact signed bytes and matching test evidence; do not rebuild different bytes for promotion without revalidation. Real-device APNs, Keychain, VPN, accessibility and Watch testing remain necessary. A local web test or simulator push injection cannot establish end-to-end delivery.

## Decisions for Casey and Cal

| Decision | Recommended starting choice | What changes if declined |
| --- | --- | --- |
| Apple focus and staffing | SwiftUI; name a Swift/Xcode owner; no Android promise in v1 | React Native/Expo if Android within a year or TypeScript staffing dominates; same backend gates |
| Devices and support floor | Inventory actual devices, aim for iOS 18+, test minimum/current; mirrored Watch alerts only | Restrict private pilot to newer OS or defer incompatible Watch; never infer compatibility from simulator |
| Connection and operations | Tailscale plus authenticated HTTPS; named host/VPN/revocation operator | Prove native managed-edge login or fund relay/on-call; do not substitute existing OpenAI MCP tunnel |
| Identity and visibility | Dedicated device credentials for actual human principal, selected workflows; explicit cross-owner visibility choice | Exact-run/delegation policy refinement under #328 before exposure |
| Catalog and action risk | Small reviewed workflows; durable choices only; no live/standing grants or mobile revision composer | Additional shared policy, stronger-auth and acceptance work before adding risky actions |
| Privacy and retention | Generic alerts, bounded protected summaries, no analytics; start with artifacts fetched on demand | Rich push/cached sensitive artifacts or vendor-readable relay needs explicit policy and security review |
| Account and release custody | Casey's paid individual account for TestFlight; decide legal seller/organization before broad release | Organization conversion changes signing/key/role planning; no credential sharing |
| Effort and budget | Fund spike first, then 17–26 person-weeks before contingency; maintain physical tests and monthly upkeep | Deliver read-only pilot first and label write scope deferred, rather than asserting the full MVP is done |
| Shared ownership | One APNs/outbox/enrollment and command contract with #459; trigger cohort owns intake/admission/publication | Resolve interface disagreements before parallel implementation; do not build duplicate systems |

Research completion does not grant future implementation, Apple credential access, host enrollment, live deployment or notification consent. Those follow only from separate owner instructions after these decisions and evidence gates are concrete.
