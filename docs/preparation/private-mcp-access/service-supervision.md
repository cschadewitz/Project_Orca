## Post-start boot identity: mandatory before reopening the tunnel

`workspaceId` persists, but `instanceId` is generated anew on every daemon boot. A foreground preflight proves the foreground boot only. Cutover, daemon restart, reboot and binary rollback all invalidate that pin; tunnel-only restart must preserve it. There is deliberately no automatic “accept whatever instance answered” refresh.

1. Stop/keep stopped the tunnel before a planned daemon restart. Preserve pending/uncertain admission IDs. After starting the approved daemon, use the existing authenticated discovery client with the dedicated scoped credential and the clean reviewed environment to read `operator.discover`. Compare endpoint, stable workspace UUID, principal, authentication mode, ORCA version, exact permissions and workflow/run scope to the reviewed profile. Verify the local unit process, workspace path and pinned runtime commit/binary independently; discovery's version alone does not prove a build. Do not use an owner credential, unauthenticated health response or a workspace-ID change to make this pass.
2. Have the operator explicitly review the new boot UUID from that authenticated response. Prepare a private candidate profile changing **only** `target.instanceId` and the review metadata (reviewer, current approval time and reference to this boot check). Keep endpoint, workspace, principal, credential ID, grants and runtime pins unchanged. The profile is still subject to all ownership, private-file and symlink checks. No credential issuance or mutation is involved.
3. Against the running daemon, execute the guarded launcher's `--check-only` mode using that candidate. For example, render the following with reviewed absolute paths and literal environment values; it is a future activation command, not part of this preparation:

   ```text
   /usr/bin/env -i HOME=<reviewed-home> PATH=<reviewed-path> LANG=C <absolute-node> <absolute-launch-mcp.js> --check-only --profile <candidate-profile> --token-file <dedicated-token-file> --credential-store <credential-store-file>
   ```

   Insert reviewed proxy/CA assignments only as described above. Exit 0 with no stdout means local file/grant validation and authenticated discovery matched; no MCP child was spawned and no file was changed. Any failure emits only a generic stderr message and returns nonzero. Keep the tunnel stopped on failure; do not relax a pin, retry with broader authority or copy a token into argv.
4. Install the checked profile at the tunnel's reviewed profile path using an atomic private-file replacement, retaining owner/mode and the prior non-secret review record. Start the tunnel; its launcher repeats the authenticated exact-pin check before opening stdio. If the daemon restarted again between checks, the stale profile fails closed and this procedure must be repeated. Confirm fresh Cal discovery before any further operation.
5. For a tunnel-only restart, leave the daemon and profile untouched. Confirm the same daemon process and boot UUID; do not refresh a mismatching pin as if this were an expected daemon restart. Investigate it first. For an unexpected daemon restart or reboot, a stale pin intentionally prevents fresh MCP startup; bounded retries can exhaust the tunnel start limit. After reviewing the new boot and validating the replacement profile, reset only the tunnel's failed/start-limit state if needed and start it explicitly. This is a manual recovery gate, not unattended reboot recovery. Existing daemon-disconnected sessions must rediscover and reauthorize; do not replay uncertain writes.
