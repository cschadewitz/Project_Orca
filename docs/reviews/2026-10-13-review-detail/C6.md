## Findings

### C6-01 — Enter on any focused control inside a gate or permission card sends the default option (permission inversion)
- **Category:** correctness / safety / accessibility
- **Severity:** High. For a permission ask this is a consent bypass and borders on Critical.
- **Confidence:** High
- **Location:**
  - `attention/use-card-keys.ts:71-86` registers `Enter` and `Shift+Enter` in the `card` scope.
  - `attention/answer-card.tsx:279-287` maps `submit` to `send()`, which uses `selected`.
  - `answer-card.tsx:301-313` gives the section the `card` scope, and `onFocus` bubbles.
  - The buttons at `answer-card.tsx:336-386`.
  - `keyboard-map.ts:334-348`: `handle()` calls `preventDefault()` and runs the action.
- **Issue:**
  - The card's `Enter` is resolved from focus, and every button, artifact chip and "Always …" control sits inside the `section` that owns the `card` scope.
  - Focusing any of them fires the section's `onFocus`, so the card becomes `focused` and registers `Enter`.
  - Pressing `Enter` on a focused button therefore never activates that button. `KeyboardMap.handle` calls `preventDefault()`, which cancels the button's own activation, and then runs `submit()`.
  - `submit()` sends whatever option is `selected`, and that defaults to the first non-destructive option.
- **Scenario / evidence:**
  - Take `PERMISSION_ASK`, whose options are `[{allow}, {deny, destructive}]`, so `selected = "allow"`.
  - A keyboard or screen-reader user Tabs to **Deny**, or to **Always deny**, and presses Enter. `inputs.answer({ optionId: "allow" })` is sent. The agent runs the command the person tried to deny, and no standing rule is written.
  - On a gate, Tab to the destructive **Roll back** and press Enter: **Retry** is sent.
  - Tab to an artifact chip to read it first and press Enter: the gate is approved instead of the panel opening.
  - Coverage: the tests only dispatch `keyDown` on the card section (`test/attention-cards.test.tsx:189`, `test/attention-surface.test.tsx:90`), never on a focused button inside it.
- **Recommendation:**
  - Register the card's `Enter` so it only fires when the event target is the card section itself, for example `event.target === section`, or a `when` predicate on the shortcut.
  - Alternatively, have `KeyboardMap.handle` skip bare `Enter` and `Space` when the target is a `button`, `a`, `summary` or `[role=menuitem]`, and let the platform activate the control.
  - Add a test that Tabs to **Deny** and to **Always deny** and presses Enter.

### C6-02 — Palette answer and cancel rows act on whatever card is focused when they run, not the card they name
- **Category:** correctness / safety (stale target)
- **Severity:** High
- **Confidence:** Medium-High
- **Location:**
  - `attention/attention-surface.tsx:451-528` (`useCardWrites`). The actions at `:490-493`, `:509-512` and `:519-522` read `current.current.input`.
  - `palette/command-palette.tsx:62-67`: commands are snapshotted when the palette opens.
  - `palette/entries.ts:122`: `run: shortcut.action`.
- **Issue:**
  - The palette reads `keyboard.list()` once, when it opens. Its comment says "Nothing registers or unregisters while the palette has focus", but that is false: registrations churn with pushes.
  - Each card row's label, its `confirm` sentence and its `optionId` are built for input A.
  - The action, however, dereferences `current.current.input`. That is `waits[focusIndex]` at the time the action runs, and it is never checked against A.
- **Scenario / evidence:**
  1. Card A for run R1 ("Ship release?") is focused. The person opens ⌘K and arms **Cancel the run this is waiting on**. The armed label reads "Cancel R1-name ⬡ TOKEN — confirm".
  2. Meanwhile A is answered from the CLI or another window. `input.answered` removes A, so `waits[0]` is now B, on run R2.
  3. The second Enter calls `act.cancel(now.runId)` and **cancels R2**.
  4. Likewise, "Answer Ship release?: Approve" calls `act.answer(B, {optionId: "approve"})`. Gates commonly share option ids, so B is approved.
- **Recommendation:**
  - Capture the input in the row: use `held`, or compare `now?.id === held.id` and no-op or announce otherwise.
  - Refresh palette commands while it is open. One option is a change counter on `KeyboardMap` with `useSyncExternalStore`, which would also fix a stale `unavailable`.
  - At minimum, re-validate before running an armed row.

### C6-03 — Any change to the waiting list moves focus to a different card while the person is working in a card
- **Category:** correctness / accessibility (focus)
- **Severity:** High
- **Confidence:** High
- **Location:** `attention/attention-surface.tsx:103-113`, with `inList` set at `:213-216` and cleared only at `:196-198`.
- **Issue:**
  - The "advance to the next card" effect runs whenever `ids` changes, if focus is anywhere in the list.
  - It focuses `cards.current[focusIndex]`, which after an insertion or removal is a *different* card.
  - The `inList` guard only covers the case where focus is outside the list. It does not separate "this window answered the card" from "a push reshaped the list".
- **Scenario / evidence:**
  1. The person is typing a note in gate X, at index 2.
  2. A new permission ask arrives. Permission asks sort first (`items.ts:132-134`), so it lands at index 0. Or a gate above X is answered elsewhere.
  3. The effect focuses the card now at index 2, gate W. Focus leaves the note input.
  4. The keystrokes that follow land on W: `j`/`k` move cards, digits select W's options, and Enter submits W's default.
  - No test covers this. `test/attention-surface.test.tsx` only checks advancing after this window answers a card.
- **Recommendation:**
  - Advance focus only after this surface's own `answered(id)` for the card that held focus. For example, record `answeredFocusId` in `onAnswered` and consume it in the effect.
  - Otherwise, track the focused card by id and re-focus that id if it still exists, or leave focus alone.

### C6-04 — Every transport reattachment, even a silent blip, resets surfaces to loading: Runs loses its selection and gate cards lose typed notes
- **Category:** correctness / data loss of unsent input
- **Severity:** High
- **Confidence:** High
- **Location:**
  - `packages/app/src/main/connection-state.ts:180-185` and `:333-338`: on every link re-arrival, `generation` is bumped and published even while `state` stays `live`.
  - `runs/use-runs.ts:59` and `:116` call `setState({phase:"loading"})`.
  - `runs/use-run-selection.ts:158-160` clears the selection when the id is not in `[]`.
  - `runs/tree/use-run-tree.ts:71-79` does `setDetails(new Map())`. Then `runs-surface.tsx:142` and `:319-324` unmount `StepDetail`.
  - `runs/timeline/use-run-events.ts:120` and `:143` show loading.
  - `step/use-step-log.ts:101` creates a new buffer.
  - `attention/use-attention.ts:111` and `:240` show loading, and `attention-surface.tsx:127` replaces every card with a spinner.
- **Issue:**
  - `useSubscriptionGeneration` is meant to *reconcile* after reattachment.
  - Instead, each consumer throws away what is on screen and re-renders from a loading state. AGENTS.md says "a blip changes nothing on screen".
- **Scenario / evidence:**
  - A laptop wakes, Wi-Fi changes or the SSH tunnel blips. The link goes `reconnecting` and then `live` within the 5-second quiet window, so no banner appears, but `generation` goes from 1 to 2.
  - On Runs:
    - the tree flashes "Loading runs" and its scroll position resets;
    - the selected run is cleared;
    - the step detail and its output pane unmount, losing the held position, the search query and expanded tool calls;
    - the timeline reloads and loses its place.
  - On Attention, every card unmounts. A half-typed note, a free-text answer and the chosen option, all local `AnswerCard` state, are lost. This contradicts the "never loses an unsent draft" rule in `layers.ts`.
- **Recommendation:**
  - On a generation bump, keep the last snapshot and re-read in the background (stale-while-revalidate).
  - Swap the snapshot in only when the fresh read lands, and only drop rows that are actually gone.
  - Do not clear `details` in `useRunTree`; refetch over the held map.
  - Keep the Attention cards mounted, keyed by id, so `AnswerCard` state survives.

### C6-05 — After following any run link, the Runs selection snaps back to the linked run on every App render
- **Category:** correctness (React effect deps / object identity)
- **Severity:** High
- **Confidence:** High
- **Location:**
  - `App.tsx:321-331`: `open={…}` is built as a fresh object literal on each render.
  - `runs/runs-surface.tsx:136-138`: `useEffect(() => { if (open) selectRun(open.runId) }, [open, selectRun])`, and `:143-152`, which does the same for the step.
  - `App.tsx:101-104` and `runs-surface.tsx:206-208`: each selection reports crumbs, which calls `setHeader(newObject)` and re-renders App.
- **Issue:**
  - `route` persists until another link replaces it.
  - Any App re-render, including the one caused by the Runs surface reporting its own crumbs, creates a new `open` object. The effect then re-selects `route.runId`, and the step when the link named one.
- **Scenario / evidence:**
  1. Press `G` on an Attention card, click an OS notification or follow a palette jump. Each of these navigates to `orca://run/A`.
  2. Click run B in the tree. Selection becomes B, crumbs change, App re-renders, `open` is a new object, and the effect calls `selectRun(A)`.
  - The person cannot select any other run, or another step when the link named one, until a different link is followed.
  - App also re-renders on every attention publish, so even keyboard `J` is undone.
  - Coverage: `test/entry-points.test.tsx` only asserts the first landing.
- **Recommendation:**
  - Pass a stable key: memoise `open` on `route`, or pass `route` and key the effect on `[open?.runId, open?.nodeId, open?.attempt, navigationSerial]`.
  - Use a navigation sequence number so the *same* link followed twice re-selects, but a re-render does not.

### C6-07 — `VirtualList` ignores its in-scroller header, so the selected or newest row sits just below the fold
- **Category:** correctness (windowing math)
- **Severity:** High
- **Confidence:** Medium-High. It needs real layout; happy-dom tests run unmeasured.
- **Location:**
  - `list/virtual-list.tsx:256-283`: the header is rendered inside `.orca-list__scroller`, above `.orca-list__rows`.
  - `list/list-window.ts:127-134` (`revealScrollTop`) and `:186-191` (`isAtBottom`) assume row *i* starts at `i * rowHeight`.
- **Issue:**
  - `.orca-pane__head` is in flow with `height: var(--bar-pane)`, which is **34px**. `--row-h` is **32px** comfortable and **24px** compact.
  - Row *i* actually spans `[H + iR, H + (i+1)R]`.
  - When `reveal` scrolls a row to the bottom it sets `scrollTop = (i+1)R − V`, so the row's top is at `(i+1)R + (H − R)`. That is 2px (comfortable) or 10px (compact) **below** the viewport, so the row is entirely hidden.
- **Scenario / evidence:**
  - In the run tree or the timeline, both of which pass `header`, press `J`, `↓` or PageDown at the bottom edge. The newly selected row is invisible, and stays one row below the fold on each further press.
  - A *following* timeline calls `reveal(count-1)` and never shows the newest event.
  - `isAtBottom` under-reports the remaining distance by `H`.
  - Neither the unit tests nor the smoke test exercise measured navigation.
- **Recommendation:**
  - Measure the header and include it as an offset (`rowsTop`) in `ListMetrics`, then use it in `revealScrollTop`, `isAtBottom`, `shiftScrollTop` and `listWindow`.
  - Alternatively, render the header outside the scroller, which the timeline already does for its bar.

### C6-08 — Following is not released by keyboard, minimap or search moves, so the next append pulls the view back to the end
- **Category:** correctness / accessibility
- **Severity:** High
- **Confidence:** Medium-High
- **Location:**
  - `list/virtual-list.tsx:211-219` (`move` calls `select` and `reveal`) and `:236-238` (the follow effect).
  - `list/use-list-viewport.ts:151-156`: `offsetTo` writes `bottomRef = false` *before* the scroll event, so `onScroll` at `:191-197` sees `was=false` and never calls `onLeaveBottom`.
  - Minimap `onGoTo` at `virtual-list.tsx:310`, and output-pane search `goTo` at `step/output-pane.tsx:155-171`.
- **Issue:**
  - Only a pointer or wheel scroll leaves following.
  - `K`, `↑`, `Home`, `PageUp`, a minimap tick, and `n`/`N` search hits all move the offset programmatically, yet `follow` stays true.
  - The next `count` change, roughly every 100ms on a streaming run, calls `reveal(count-1)`.
  - `output-pane.tsx:179-185` patches this for `G` only: "a key that moves the offset itself is not one of those".
- **Scenario / evidence:**
  - Select a live run and press `K` a few times, or `Home`, in the timeline or the output pane. Within about 100ms the list jumps back to the newest row.
  - Clicking a "failed" minimap tick jumps there and then straight back.
  - Keyboard users cannot read back through a live stream.
- **Recommendation:** in `move` and the minimap's go-to, when `follow` is set and the target is not the last row, call `onHold`. The simplest place is inside `reveal`: if `follow` and the index is less than `count − 1`, call `leave`.

### C6-09 — Timeline entries grow without bound, every append costs O(n), and live batches diverge from replay
- **Category:** performance / memory / correctness
- **Severity:** High (memory and CPU growth during a long run)
- **Confidence:** Medium
- **Location:**
  - `runs/timeline/use-run-events.ts:150-157`: one append per `agent.update` and per `event.appended`.
  - `runs/timeline/timeline-entries.ts:163-179`: `mergeEntries` rebuilds a `Map` over all held entries and sorts them, every append.
  - `timeline.tsx:91-113` and `:179`: filter, `kindsOf` (O(n·k)), ticks, and two passes of `eventsIn`, every append.
  - `runs-surface.tsx:156`: `buildSelectionIndex`, O(n), every append.
  - `agentUpdateEntry` (`:142-153`) compared with `toEntries` (`:92-115`).
- **Issue:**
  - Unlike the output buffer, which is capped at 50,000 events, the timeline has no cap.
  - A live step emits up to 10 `agent.update` batches per second, and **each becomes its own row**, because live batches are never merged with the adjacent row.
  - Replay coalesces every consecutive update for the step into one row, so live and replay diverge. The test "draws a live batch the same way it draws a replayed one" only covers identical ranges.
  - When a run is selected mid-stream, the batches held in `pending` during the initial read (seq 10–14, say) are keyed by `seq` and survive next to the replayed coalesced row (`fromSeq` 10 – `seq` 20). The result is overlapping rows and double-counted "N agent updates".
- **Scenario / evidence:**
  - A four-hour session with steady output gives about 100k entries, roughly 20–40MB plus a full copy per append.
  - At 10 appends per second, the ~8 O(n) passes per append become visible main-thread jank that grows with time.
- **Recommendation:**
  - In `append`, extend the last row when it is an `agent.update` for the same `stepRunId` with `fromSeq = last.seq + 1`, which is what replay does.
  - Merge incrementally: append when `seq > last.seq`, and use a full merge only for pages.
  - Cap held entries (front-trim with `hasEarlier = true`).
  - Derive `kinds` and ticks incrementally, or only when the filter menu opens.

### C6-10 — `shiftBy` runs before the prepended rows commit, and timeline `loadEarlier` overwrites state from a stale snapshot
- **Category:** correctness (async ordering / React batching)
- **Severity:** Medium
- **Confidence:** Medium-High
- **Location:**
  - `runs/timeline/use-run-events.ts:191-205`: `setState({...held, entries…})`, then `prepend.current?.(prepended)` synchronously.
  - `step/use-step-log.ts:240-254`: `buffer.prepend` calls `setRows` and then `prepend.current?.(added)`.
  - `list/use-list-viewport.ts:172-183`: `shiftBy` reads `metricsRef.current`, which is only updated in render.
- **Issue:**
  - React 19 batches `setState` inside a promise callback, so the rows are not in the DOM when `shiftBy` runs. The comment "After the rows are in `entries`, so the metrics `shiftBy` reads are the ones the prepend produced" is incorrect.
  - In the measured case, `scroller.scrollTop = old + rows·R` is clamped by the browser to the *old* scroll height. React state holds the unclamped value until a scroll event corrects it.
  - In the unmeasured case, `shiftAnchor` clamps to the old `count`.
  - Separately, `loadEarlier` uses `stateRef.current`, the last *rendered* state, and a non-functional `setState`. Any `append` updaters queued between the last render and this `.then` are applied and then overwritten, so those events are dropped from the timeline.
- **Scenario / evidence:**
  - At the top of a 200-row timeline, click "Load earlier events". The reader lands roughly one viewport (V − H) too high rather than in place.
  - On a streaming run, a batch arriving in the same tick as the page response vanishes until a reload.
- **Recommendation:**
  - Queue the shift and apply it in a `useLayoutEffect` after `items.length` changes, for example `pendingShift.current += n`, consumed on commit.
  - Use a functional `setState(prev => merge(prev.entries, page))`.

### C6-11 — Output buffer at its cap: front trims are not compensated, and a just-loaded earlier page is trimmed straight away
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:** `step/line-buffer.ts:272-294` (`prepend` does not trim) and `:356-365` / `:412-422` (`drain`, then `trim`); `step/use-step-log.ts:110-116`.
- **Issue:**
  - Once a step's buffer holds 50,000 events, every commit (about every 100ms while streaming) drops rows from the front, but nothing calls `shiftBy(-n)`.
  - "Load earlier output" prepends a page, pushing `marks` over the cap. The *next* live `drain()` then trims exactly that page, and `trimmedBefore` moves back forward.
- **Scenario / evidence:**
  - On a long agent session with the reader held mid-buffer, the text slides upward under them on every commit. This breaks the documented promise that "nothing scrolls under the reader's eyes".
  - Clicking "Load earlier output" on a live step shows the page for about 100ms. It then disappears, and the reader's offset is now wrong by two pages.
- **Recommendation:**
  - Have `trim()` report how many rows were dropped, and let the hook call `shiftBy(-dropped)` when the person is held.
  - While a prepended page is held (until the person returns to the end), raise the cap, or trim from the newest side only after release.

### C6-13 — Feed publishes recompute from scratch on every notification, O(C·n log n), and the held maps grow for the session
- **Category:** performance
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - `runs/use-runs.ts:63-81`: a `mergeRun`, which is a full `orderRuns` sort with `localeCompare`, for every resolved run *and* every changed run, on every `run.changed`.
  - `attention/use-attention.ts:113-137`: `forget` and `file` (filter, then `mergeRun`) for every entry in `changes`, on every push.
  - `runs/tree/use-run-tree.ts:65` and `:194-196`: `wanted` and `details` only grow, and each push copies `details` (`:112-123`).
- **Issue:**
  - `changes`, `resolved` and `runs` are never pruned within a generation.
  - On a busy store, every run that has changed this session is re-applied and re-sorted on every notification.
  - With fan-out child runs this means hundreds of runs, so roughly C × n·log n `localeCompare` calls per push. That is tens to hundreds of ms per notification on the always-mounted `useAttention` in App, and on Runs.
- **Recommendation:**
  - Maintain the derived list incrementally: patch one row, then re-insert it by binary search.
  - Compare ISO strings with `<`, not `localeCompare`.
  - Drop entries from `changes` once they have been folded into a held row.

### C6-14 — Synchronous IPC on the render path of the always-mounted chrome
- **Category:** performance / reliability
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `attention/use-revisions.ts:101-112` (`currentScope()`), called at `:151` on *every render*, and again in `active()` closures and in `answerDraft` (`:690-699`).
  - `packages/app/src/preload/index.cts:314` and `:328`: `connection.read` and `workspace.read` are `ipcRenderer.sendSync`.
- **Issue:**
  - `useRevisions` runs inside `useAttention`, inside `App`. Each App render therefore makes two blocking round trips to the main process.
  - App renders on every attention publish, which happens on every `run.changed`, `input.*` and `step.changed` (waiting), and on crumb changes.
  - `sendSync` stalls the renderer whenever main is busy, for example during a store switch, a large IPC broadcast or GC.
- **Recommendation:** derive `scope` from the already-subscribed `useConnection()` and `useWorkspace()` values. Reserve synchronous reads for the few guard checks that need one, outside render.

  - Choosing a palette **Search → artifact** row, or pasting `orca://artifact/spec@v3?run=…`, selects the run but never shows the artifact.

  - Handle the `artifact` route in App by calling `panel.open({runId, name, version})` (resolving `version` from `artifacts.list` when it is absent).

### C6-16 — A held Enter defeats the palette's two-press confirmation of destructive rows
- **Category:** safety
- **Severity:** Medium
- **Confidence:** High
- **Location:** `palette/command-palette.tsx:141-149` and `:167-170`. `keyboard-map.ts:334-348` also never checks `event.repeat`.
- **Issue:** The first `Enter` arms and the second runs, but an auto-repeated `keydown` counts as the second.
- **Scenario / evidence:** Type "cancel" so the danger row comes to the top (`entries.ts:154-157` acknowledges this), then press Enter slightly too long (past the OS repeat delay). The run is cancelled without the confirmation ever being read.
- **Recommendation:**
  - Ignore `event.repeat` when confirming an armed row, and ideally for every write action in `KeyboardMap.handle`.
  - Optionally require the key to be released between arming and confirming.

## Strengths
- **No HTML sinks anywhere in scope.** Agent output, artifact bodies (deliberately raw, `artifact-panel.tsx:258-260`), diffs, tool-call bodies and vars are all React text.
- **The diff is bounded.** `MAX_CELLS` caps the work, and identical prefix and suffix lines are skipped before the table is built.
- **The bridge contract is sound.** Main's `handle()` turns every failure into `{ok:false}` (`packages/app/src/main/index.ts:313-341`), so the many `void promise.then(...)` calls do not leak rejections. Effects use `live` / epoch guards consistently against late responses.
- **The output buffer is careful work.** Commits are rate-limited on rAF rather than debounced. There is a 50k-event cap and a 2,000-character line cap. Rows are re-keyed on prepend, and `seq` is used as the line address.
- **Shared infrastructure is built once.** There is one notification stream with a refcounted bridge subscription and per-run filters, one 1Hz ticker for every duration, and one polite announcer fed as a listener rather than as a second subscription.
- **`KeyboardMap` is a real registry.** Collisions throw, keyless commands get unique slots, text-entry suppression is in place, and `Menu`'s refcounted `menu`-scope keys avoid double registration.
- **The arithmetic lives in plain, tested modules.** `list-window`, `tree-rows`, `run-rows`, `card-model`, `timeline-entries` and `line-buffer` each have a plain module and tests. The destructive-option rules (never bound to 1, never selected by default, sunk in the palette) are encoded and tested.
