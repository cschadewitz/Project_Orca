### C5b-01
- **Verdict:** CONFIRMED. The trigger set is wider than reported.
- **Adjusted severity:** High. It is not yet in any shipped build (v0.6.0 predates the gate), but it is on `main` and goes out with the next release.
- **Evidence:**
  - **How the gate decides.** `mac-managed-replacement-startup.ts:78-85` skips provisioning whenever `<control>/enrolled.json` exists. It then calls `inspectUpdateWindowRoots` (`:86`), and any throw lands in `catch { bootstrap.seal(); return "unknown"; }` (`:96-98`). `index.ts:1229-1237` then shows "Native replacement recovery is required" and returns.
  - **Why an identity change throws.** `state()` (`update-window.ts:126-133`) compares `enrolled.json.control` to a live `fenceDirectory(control)`. `anchor()` (`:135-142`) compares the guard's `root` the same way. `fenceDirectory` (`first-run-fence.ts:56-67`) is `{path, dev, ino, uid}` from `lstat`. A Migration Assistant copy, a Time Machine restore or a renamed home folder therefore throws on every launch.
  - **What I looked for and did not find:**
    - No re-anchor, reprovision or reset path anywhere in `packages/*/src` or `tools`.
    - No Time Machine exclusion (`tmutil` / `com_apple_backup_excludeItem`).
    - No documented manual recovery step.
    - `provisionMacUpdateNamespace` is unreachable once `enrolled.json` exists. Deleting the control directory alone also fails: `mac-update-namespace.ts:70` and `update-window.ts:333` refuse when a guard survives.
  - **The refusal is deliberate.** Tests assert it: `update-window.test.ts:84-101,198-220`. `mac-closed-window-fixed-path.md:49-51` says "Lost control …, missing completed anchors, changed roots and torn temporary records refuse." So this is fail-closed by design, but its user consequence is unmitigated.
  - **Broader trigger the report missed.** `inspectUpdateWindowRoots` (`:145-151`) calls `anchor(root.path)` for every enrolled root. First-run enrolls the user-chosen workspace directory (`first-run/setup.ts:290` → `index.ts:699` → `enrollUpdateWindowRoots`). If the user later deletes, renames or moves that workspace folder, the guard read hits ENOENT and the app refuses startup permanently. That is a far more common action than Migration Assistant.
  - **Torn-write variant (narrow but real):**
    - First-provision writes use `O_EXCL` straight to the final name (`write(..., replace=false)`, `:94-117`).
    - The enrollment sequence is `window.json` rename (`:426`), then guard, then `enrolled.json` (`:429`). A crash between those steps leaves `window.json.roots ≠ enrolled.json.roots`, so `state()` throws forever.
    - A failed `fileSync` leaves `window.json.tmp` behind, which `state()` (`:127`) also refuses forever.
- **Fix note:** The recommendation should also cover enrolled workspace roots that go missing or move. While the window is `open` with `attempt === null`, de-enroll or re-anchor them under all slots, rather than refusing. A supported reset is needed either way.

### C5b-07
- **Verdict:** CONFIRMED.
- **Adjusted severity:** Medium (unchanged). It will also fail the next release's macOS app-verification leg.
- **Evidence:**
  - **Why the addon never loads unpackaged.** The gate is mounted on `process.platform === "darwin"` with no `app.isPackaged` check (`index.ts:82-89`). Under Electron, `diagnosticsAddonPath` resolves only to `process.resourcesPath/native/diagnostics/darwin-<arch>/…` (`diagnostics/native-addon.ts:18-22`). The file's header says "Electron uses external resources and never repository fallback."
  - **No dev fallback anywhere.** `loadDiagnosticsAddon` returns `undefined` on failure (`:35-39`). `scripts/dev.js` and `pnpm start` stage nothing into `node_modules/electron/dist/Electron.app/Contents/Resources`. Only the packaged `mac.extraResources` (`electron-builder.yml:94-96`) and `desktop.yml:128-154` stage the addon.
  - **Result on every unpackaged run.** `provisionMacUpdateNamespace` throws "unavailable" (`mac-update-namespace.ts:46-50`), which leads to `"unknown"` and the recovery dialog. `mac-replacement-storage.ts:26-27` makes the same intentional fail-closed choice.
  - **CI exposure.** `app-smoke.yml:176-188` does run `macos-latest`. Its `app:admission-intents` and `app:revision-workflow` steps (`:236-292`) launch unpackaged Electron (`admission-intents.spec.ts:97`, `revision-workflow.spec.ts:74`) and wait for `connection.state === "live"` (`:101-104`), which the closed gate never reaches.
  - **Why CI has not caught it.** No App smoke or release run has executed since the gate landed. The unit test mocks the module (`daemon-connection-integration.test.ts:157-168`).
  - **Release impact.** `release-publish.yml:109-118` makes `publish` depend on `app-verification`, so the next release will fail on the macOS leg until this is fixed.

### D8-02
- **Verdict:** CONFIRMED, but partly overstated.
- **Adjusted severity:** Medium, down from High. This is a docs variance; the operational harm is already counted in C5b-01 and C5b-07.
- **Evidence:**
  - **Code.** `mac-managed-replacement-startup.ts:85` auto-provisions on the first darwin launch. Every darwin launch (dev included) is gated by `index.ts:82-89,1230-1237`.
  - **Stale doc statements, confirmed:**
    - `mac-replacement-native-producers.md:65-67,89-93`: provisioning authority "must be supplied first" and is unresolved.
    - `app-same-boot-config-composition.md:108-113`: "deliberately held … not mounted production authority".
    - `app-native-recovery-composition.md:56-57,94`: "not a mounted production journal gate".
  - **Where the report overstates:**
    - `mac-replacement-native-producers.md:33-34` ("never implicitly provisions its root") is about the journal storage layer. That is still true: `createHandleRelativeStorage` never provisions, and provisioning is a separate explicit call.
    - `mac-closed-window-fixed-path.md:49` ("provisioning is explicit") is consistent with the code.
    - "No doc says it gates every Mac launch" is wrong. `mac-closed-window-fixed-path.md:95-99` says `createManagedMacReplacementStartup` "begins closed before producers … checks durable admission for every new main dispatch".
  - **What is genuinely undocumented:** first-launch auto-provisioning, its failure modes (missing addon, non-APFS or external volume, port collision) and the effect on dev/unpackaged runs.
- **Fix note:** Update or retire only the three stale statements, and add the failure modes. Leave the fixed-path doc's "explicit" wording alone.

### C5b-02
- **Verdict:** CONFIRMED as a design defect. It cannot be reached today.
- **Adjusted severity:** Medium (latent), down from High. Two independent switches would both have to flip before it could happen.
- **Evidence:**
  - **The defect is real.** `act("approve")` calls `closedWindow.closeAdmission()` (`mac-update-application.ts:90-99`), which durably commits phase `draining` (`update-window.ts:508-513`). The defer path commits `deferring` before `session.defer` (`mac-update-application.ts:79-81`). `reopen()` (`update-window.ts:617-620`) and the managed `captureClosedRecovery`, `verifyClosed`, `finishAfterCleanChildExit` and `restoreClosed` have no production caller; I grepped `packages/*/src`.
  - **Switch 1: no session.** `index.ts:850-866` passes no `authority`, so `session` is `undefined` (`mac-managed-update-application.ts:171-182`) and `offer()` returns refused (`:187`).
  - **Switch 2: activation off.** `activationAllowed: () => false` (`index.ts:864`), and `allowed()` requires both switches (`:74`).
  - **Consequence.** `MacUpdateApplication.act` returns `invalid()` at `:41-53` before reaching `closeAdmission`, and `state` is `unavailable`. No renderer or IPC input can reach it.

### C5b-03
- **Verdict:** CONFIRMED (latent). The ordering and the CLI-slot path are certain; the Electron/xattr specifics are plausible.
- **Adjusted severity:** Medium (latent), down from High. Same double gate as C5b-02: `activate()` returns `"refused"` unless `allowed()` holds (`mac-managed-update-application.ts:126`), and no session or handoff is ever built.
- **Evidence:**
  - **Ordering.** `mac-closed-window-commit.ts:51-61` runs `beginStop()`, then `stopOwned`, then `pauseAppWriters`, then `capture()`, then `backupPrevious`. A `false` from `capture()` on EADDRINUSE (`update-window.ts:549-566`) maps to `"unknown"`.
  - **CLI slots.** CLI leases are never released before process exit (`cli/src/update-bootstrap.ts:109-123`).
  - **Protected-root inventory.** `backupPrevious` digests every enrolled root, userData included, twice and requires the two digests to match (`mac-fixed-path-recovery.ts:247-253`). The inventory rejects:
    - absolute symlink targets;
    - xattr names outside `[A-Za-z0-9._-]` (`mac-fixed-path-files.ts:120-155`).
  - **Why the inventory would trip on a real Mac.** Electron's posix process singleton puts `SingletonSocket` → absolute temp path in userData on macOS, and Chromium keeps writing to the profile. I am fairly but not fully sure of both, since I could not run them.
  - **Mitigation.** None of this is reachable in production today.

### D8-01
- **Verdict:** CONFIRMED.
- **Adjusted severity:** Medium, down from High. It is a stale internal implementation note: diagnostics production capture is disabled, and the real code is *more* private than the doc claims, so a reader would overestimate exposure rather than underestimate it.
- **Evidence:**
  - **The doc.** `docs/implementation/diagnostics-byte-preview.md:3-53` describes `preparePreview`, `readPreviewBlock`, `releasePreviewBlock`, renderer byte owners and a full-report `pre`. It uses the present tense and carries no superseded marker.
  - **The code has none of it.** No production source matches these names:
    - `DiagnosticsBridge` (`diagnostics-contract.ts:57-69`) exposes only the save-only set.
    - Tests assert the names are absent: `daemon-connection-integration.test.ts:406`, `diagnostics-preload.test.ts:89-91`, `renderer/test/diagnostics.test.tsx:270`, `diagnostics-report-performance.test.ts:256`.
  - **The docs contradict each other.** `docs/preparation/crash-recovery/windows-save-only-followup.md:29-32` records the removal.
  - **Stale on arrival.** Both docs were *added* in the same integration commit `b3a2846` that removed the API. `windows-byte-preview-followup.md:18` still links to the stale doc as "the architecture".

### C8-01
- **Verdict:** CONFIRMED.
- **Adjusted severity:** Medium, down from High. The repo is private with a single owner, the job runs only on a merged `release`-labelled PR or a writer's dispatch, and the attack needs a malicious package already in the lockfile at release time. The impact is still real, because `main` is unprotected (verified via API) and release assets are unsigned.
- **Evidence:**
  - **The over-broad token.** `release-publish.yml:42-43` grants `contents: write` workflow-wide. The `check` job (`:46-99`) has no job-level `permissions`.
  - **It is exposed to dependency code.** Its checkout (`:56-59`) omits `persist-credentials: false`, so the token sits in `.git/config` while `pnpm install`, typecheck, lint, test and build run (`:75-83`) on the self-hosted `homelab` runner.
  - **Partial refutation:** `pnpm-workspace.yaml` `allowBuilds` limits install scripts to esbuild and electron. Dependency code still runs during test, lint and build. The reusable `desktop.yml` and `app-smoke.yml` correctly downgrade to `contents: read`.
  - **Not refutable:** I could not find an environment, ruleset or job override that narrows the token.
- **Fix note:** Scoping `contents: write` to `publish` is necessary but not sufficient. `publish` (`:116-208`) runs on the same, likely persistent `homelab` label: it uses the host's toolcache Node, `gh`, `python3` and `ssh`, writes the feed key to `~/.ssh`, and runs right after the Linux `desktop` leg and `app-smoke`, which execute full dependency code on that host. A host compromise from any earlier job can therefore still reach the write token and the feed key. Run `publish` on a GitHub-hosted or dedicated ephemeral runner.

### C8-02
- **Verdict:** CONFIRMED.
- **Adjusted severity:** Medium, down from High.
- **Evidence:**
  - **Every action is tag-pinned** (grep across `.github/workflows/*.yml`).
  - **Only one is third-party:** `pnpm/action-setup@v6`, used at `release-publish.yml:68`, `ci.yml:59`, `ci-shadow.yml:27`, `app-smoke.yml:92,205` and `desktop.yml:74`. Everything else is GitHub-owned (`actions/*`, `github/codeql-action/*`).
  - **High-exposure use.** In the release `check` job it runs after a credential-persisting checkout with a write token on the self-hosted runner. That is a tj-actions-style exposure, so Medium.
  - **Lower-exposure uses.** In `ci.yml` and `ci-shadow.yml` it runs on hosted runners with `contents: read` and `persist-credentials: false`.
  - **Why the rest is Low.** Tag-pinning GitHub-owned actions in a private personal repo is Low on its own.
  - **No mitigation.** Dependabot's `github-actions` group (`dependabot.yml:41-47`) keeps tags current but gives no integrity guarantee.
- **Fix note:** The simplest high-value fix is to SHA-pin `pnpm/action-setup`, or drop it from write-token and self-hosted jobs in favour of corepack with the existing `packageManager: pnpm@12.4.2`. SHA-pinning the GitHub-owned actions is good hygiene, but optional at this repo's scale.
