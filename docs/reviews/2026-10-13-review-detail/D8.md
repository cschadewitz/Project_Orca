## Findings

### D8-01 — The byte-backed diagnostics preview doc describes an IPC/bridge API that was removed
- **Doc:** `docs/implementation/diagnostics-byte-preview.md:3-53`. It says "`preparePreview` returns metadata and a fresh handle". It also describes one sequential `readPreviewBlock(handle, offset)` returning 16,384-byte blocks, `releasePreviewBlock` erasure, 1,048,576 + 49,152-byte renderer and transport reservations, preload and renderer byte owners, a text-node pool and a focusable `pre` holding the complete report. Line 40 says "The picker is refused until every byte is acknowledged."
- **Code:** `packages/app/src/diagnostics-contract.ts:57-69`: the bridge exposes only `status/setEnabled/setMinutes/prepareExport/cancelExport/chooseDestination/save/discardPrevious/retryCleanup/acknowledgeUnknown/subscribe`. `packages/app/src/preload/index.cts:151-168` exposes the same set. Main registers `prepareExport/cancelExport/chooseDestination/save` (`packages/app/src/main/index.ts:260-273`). Tests assert the preview channels are absent: `packages/app/test/daemon-connection-integration.test.ts:406-407` (`preparePreview`, `readPreviewBlock`, `releasePreviewBlock`, `closePreview` not registered), `packages/app/test/diagnostics-preload.test.ts:89-91` and `packages/app/renderer/test/diagnostics.test.tsx:270`. No renderer receives report bytes. `docs/preparation/crash-recovery/windows-save-only-followup.md:29-37` records the owner-approved switch to save-only, so the docs also contradict each other.
- **Variance type:** stale-doc (also doc-conflict)
- **Severity:** High. It misdescribes the diagnostics bridge/IPC contract and where report content flows (the doc says the renderer holds the full report; in code it never does).
- **Confidence:** High
- **Suggested resolution:** update doc. Mark it superseded by the save-only scope and describe the `prepareExport → chooseDestination → save` lifecycle, or retire the file.

### D8-02 — Ordinary macOS startup now depends on the mounted replacement bootstrap, which auto-provisions the recovery namespace. Docs call the authority undecided or say it never happens implicitly.
- **Doc:**
  - `mac-replacement-native-producers.md:33-34`: "the replacement namespace never implicitly provisions its root". Lines 65-67: "The initial namespace provisioning/continuity authority must be supplied first". Lines 89-93 list "Who may provision the first recovery namespace" as an unresolved decision.
  - `app-same-boot-config-composition.md:108-113`: "#581's native updater journal/bootstrap is deliberately held … the owner has not chosen initial provisioning authority … The app-only optional bootstrap input is not mounted production authority."
  - `app-native-recovery-composition.md:56-57`: "not a mounted production journal gate". Line 94: "This slice does not mount that journal."
  - `mac-closed-window-fixed-path.md:49` says only "Initial namespace provisioning is explicit".
  - `app-held-nonmac-verification.md:29-32` notes the app-root bootstrap is mounted. No doc says it provisions on first launch or that it gates every Mac launch.
- **Code:**
  - On every darwin launch, whether packaged or not, `index.ts:82-89` mounts `createManagedMacReplacementStartup`, and `index.ts:1230-1238` awaits `initialize([appWriterRoot])`. If ordinary startup is not allowed, the app shows "Native replacement recovery is required" and returns with protected IPC closed.
  - `mac-managed-replacement-startup.ts:77-85`: when `<control>/enrolled.json` is absent it calls `provisionMacUpdateNamespace` automatically. That creates `<userData>-native-replacement`, writes `window.json` and a `.orca-update-window.json` guard into userData (`protocol/src/update-window.ts:333-354`), then `enterUpdateWriter` holds a loopback kernel slot (`update-window.ts:204-222`).
  - Every step requires the `diagnostics_storage` addon with `replacementStorage: 1` (`mac-update-namespace.ts:46-50`), loaded only from Electron `resourcesPath/native/diagnostics/darwin-<arch>` (`diagnostics/native-addon.ts:18-22`). It also requires an internal APFS volume (`update-window.ts:315-318` → `first-run-fence.ts:150-161`).
  - Any failure seals the bootstrap and returns "unknown" (`mac-managed-replacement-startup.ts:96-98`). An unpackaged dev run on macOS has no staged addon in Electron's resources, so by this code path it would show the recovery shell. Tests mock this module (`daemon-connection-integration.test.ts:157-167`), so the real first-launch path is not exercised.
- **Variance type:** undocumented (also doc-conflict)
- **Severity:** High. The docs present the updater as "held/disabled", but its recovery bootstrap gates every macOS launch and chooses the namespace-provisioning authority that the docs list as an open decision.
- **Confidence:** Medium. The code path is clear; it was not run on macOS.
- **Suggested resolution:** decide. Record the chosen provisioning authority (main at first launch, before producers) and its failure modes (missing addon, non-APFS, port collision → recovery shell). Decide whether unpackaged/dev Mac runs should be gated. Then update the superseded statements.
