### D1-01 — ADR 0008 still says the daemon control port is unauthenticated and auth is "not on the roadmap"
- **Doc:** `docs/adr/0008-daemon-protocol-and-desktop-app-in-one-workspace.md:68-73`
  - "**The control port is unauthenticated, and that is accepted.** `orca serve` binds loopback and asks nobody who they are, so any process running as the same user can answer a gate, cancel a run or start one … `orca serve --help` says so in those words … `--read-only` is the answer today; authentication on the port is not on the roadmap."
  - No dated correction is attached, although the same ADR does annotate another consequence ("Resolved 2026-09-21", lines 80-85).
- **Code:**
  - `packages/cli/src/commands/index.ts:736-740`: `serve` help reads "Run the **authenticated** ORCA daemon" and "Token authentication is on by default; the local credential is stored in auth/local-client.token … --unauthenticated-loopback explicitly permits unauthenticated local access."
  - `index.ts:1048-1064`: token mode (`openAuthDirectory`, credentials, ownership, audit) unless `--unauthenticated-loopback` is passed.
  - `index.ts:1273-1276`: prints which mode is active.
  - Per-operation authorization lives in `packages/daemon/src/auth/operations.ts`.
- **Also contradicts:** `README.md:107` ("`orca serve` defaults to authenticated token mode") and `docs/ARCHITECTURE.md:57-58, 69-70`.
- **Variance type:** stale-doc / doc-conflict
- **Severity:** High. A settled decision record misstates the daemon's security posture and quotes `--help` text that no longer exists.
- **Confidence:** High
- **Suggested resolution:** Update the doc. Add a dated "Superseded (#328)" note to that consequence: token auth is the default, unauthenticated loopback is an explicit opt-in, and authorization is per operation.

### D1-03 — DATA-MODEL gives the wrong store location and the wrong resume precedence for stored workflow definitions
- **Doc:** `docs/DATA-MODEL.md:158-161`
  - "`workflowStored: true` … says the definition the run started on is in the store's `workflows/<id>@v<version>.json` (#179)."
  - "Resume prefers the live definition when its version matches, otherwise the stored copy … Same-version edits are not immutable recipe snapshots."
- **Code:**
  - `packages/store/src/workflow-store.ts:7-12, 53-56, 81-86`: new snapshots are written with `writePrivateJson` to **`private-workflows/<id>@v<version>.json`**, encrypted AES-256-GCM (`protected-file.ts:38`). `workflows/` holds only legacy plaintext records.
  - `packages/engine/src/orchestrator.ts:1125-1140` (`definitionFor`): for a stored run, the **stored copy comes first** and a loaded file at the matching version is only the fallback. Only legacy runs (`stored=false`) use the file first.
  - `orchestrator.ts:1150-1170` (`selectDefinition`): "A version is immutable once a run has recorded it". A same-version edit is refused (`versionCollision`).
- **Also contradicts:** `docs/ARCHITECTURE.md:80-87`, which is correct: "stored copy first … New unversioned launches reject changed content at an already stored `(id, version)`".
- **Variance type:** stale-doc / doc-conflict
- **Severity:** Medium. It misstates resume behaviour and points readers (and backups) at a plaintext path that no longer holds new protected definitions.
- **Confidence:** High
- **Suggested resolution:** Update the doc to match ARCHITECTURE. Name `private-workflows/` (encrypted) for new records and `workflows/` as legacy, and state the stored-first precedence and same-version refusal.

### D1-05 — Sidecar-fallback security claim: ADR 0009's 2026-10-01 clarification contradicts the in-code documentation
- **Doc:** `docs/adr/0009-permission-grants-in-a-workspace-sidecar.md:128-133` says the corrupt-sidecar fallback "can lose restrictions too: the sidecar schema allows deny/ask rules, and dropping them can expose a later default allow … A conservative error policy is not established."
- **Code:**
  - The behaviour matches the ADR. `packages/agents/src/acp-session.ts:120-128` skips an unreadable sidecar, and `effectivePermissionPolicy` (`packages/core/src/model/agent.ts:289-298`) then appends `DEFAULT_PERMISSION_POLICY`'s in-workspace `allow` rules (`agent.ts:128-139`). A recorded `reject_always` (`deny`) for an in-workspace edit is therefore lost and the default `allow` fires.
  - The governing code comments still say the opposite:
    - `acp-session.ts:116-118`: "The fallback is the conservative direction … what is lost is a grant, never a restriction."
    - `packages/agents/src/permissions.ts:242-245`: "skipping is the *conservative* direction … it can never turn an `ask` into an `allow`."
- **Variance type:** doc-conflict (ADR vs code documentation on a security property)
- **Severity:** Medium. Anyone reading the code is told the fallback fails safe; the ADR correctly says it does not.
- **Confidence:** High
- **Suggested resolution:** Decide. At minimum fix the two code comments to match the ADR. If fail-closed is wanted, make a corrupt sidecar suppress default rules or refuse the ask, and update the ADR.
