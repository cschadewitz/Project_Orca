## Findings

### C1-01 — Socket closing during `subscribe` leaks a permanently attached event-store listener
- **Category:** resource-leak (concurrency)
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/socket.ts:172-232`, related `socket.ts:252-255`, `auth/guard.ts:627-640`, `auth/resources.ts:99-112`
- **Issue:** The `subscribe` handler awaits `authorizer.subscribeScope(...)`, then creates a `Subscription`, puts it in the connection's map, and calls `start()`. That attaches a listener to the engine's event store, plus agent, config, plan and live-input listeners. After the await it never checks whether the socket is still open or whether `principal` was cleared by revocation. If the `close` event fires during that await, `stopAll()` has already run over a map that does not yet hold the new subscription. The subscription is then added and started on a dead connection, and nothing ever stops it.
- **Scenario / evidence:**
  - For a restricted principal (the `client` preset, used by the MCP adapter), `subscribeScope` → `runs.allows` → `RunAccess.root` → `resolver.run` → `eventsRange(...)` does real file I/O whenever the run is not cached. Absence is deliberately never cached (`resources.ts:109`: "Absence is not cached"), so every subscribe to a non-existent or unknown run id hits disk.
  - A client that sends `{"method":"subscribe","params":{"runId":"run_bogus"}}` and closes the socket at once leaks one silent subscription per attempt. Repeated in a loop, this grows the event store's listener list without bound.
  - `EventStore.publish` iterates every listener on every append (`store/src/event-store.ts:174-183`), so every run's appends slow down for the whole daemon.
  - A visible-run variant also keeps calling `current()` (a `statSync`) and `projectNotification` for every event, forever.
  - No test covers close-during-subscribe.
- **Recommendation:** After every await in the subscribe path, bail out if `ws.readyState !== ws.OPEN || principal === undefined`. Register the subscription in the map before the first await and have `stopAll` stop it, or keep a `closed` flag that `start()` checks. Cap subscriptions per connection.

### C1-02 — No backpressure for slow or stalled socket subscribers: unbounded daemon memory
- **Category:** resource-leak (reliability)
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/socket.ts:116-118`, `socket.ts:192-203`, related `subscriptions.ts:301-305`
- **Issue:** `send()` calls `ws.send(JSON.stringify(...))` with no check of `ws.bufferedAmount` and no drop, coalesce or close policy. Each notification also appends a `.then` to a per-subscription `delivered` promise chain, which grows whenever projection (resolver I/O for restricted principals) is slower than the event rate. There is no ping/pong heartbeat, so a half-open peer is only noticed when TCP gives up.
- **Scenario / evidence:**
  - A remote daemon is reached over an SSH tunnel, as the deployment docs recommend. The laptop sleeps or the app's main process hangs while an agent run streams output.
  - `agent.update` batches (one frame per step per 100 ms) and `event.appended` frames keep being written. Once the kernel socket buffer is full, `ws` queues in user space without limit until TCP retransmission times out, which takes many minutes.
  - A client that is merely slow (for example, a debugger paused in the Electron main process) grows the same buffer for as long as it stays slow.
  - Nothing in the repo references `bufferedAmount` or backpressure.
- **Recommendation:**
  - Before sending, check `ws.bufferedAmount` against a high-water mark. Past it, either drop to a "resync required" notification (clients already re-read via cursors) or close with a dedicated code.
  - Add a heartbeat (`ws.ping` with a pong deadline).
  - Bound the per-subscription pending-projection queue.

### C1-03 — `OwnershipStore.owner()` copies the whole ownership map on every call; the file grows forever and is rewritten with two fsyncs per run
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/auth/ownership.ts:23-30` (`owner`), `ownership.ts:115-131` (`readDisk`), `ownership.ts:80-115` (`persist`), related `auth/resources.ts:137-140`, `execution-runtime.ts:32-45`, `live-input-authority.ts:94,130-132`
- **Issue:**
  - `owner()` calls `readDisk()`, which on a cache hit still does a `statSync` and returns `new Map(this.diskCache.runs)`, a full copy of every root-run → principal entry.
  - `owner()` is on hot paths:
    - `RunAccess.rootAllows` for every `owned` principal: every notification, every row of a restricted `runs.list`, `inputs.list` and `claims.list`, every subscribe.
    - `execution-runtime.currentPrincipal`, which `LiveExecutionAuthorities` re-runs for every bound run every 1000 ms.
  - The ownership file is never pruned: one entry per root run, ever.
  - Every `record()` rewrites the whole JSON file and fsyncs both the file and the directory.
- **Scenario / evidence:**
  - Take a store with 20k root runs and an MCP `client`-preset principal (`runs: "owned"`) on a store-wide subscription.
  - Each appended event costs a `statSync` plus a 20k-entry Map copy.
  - A restricted `runs.list` costs about R × 20k copies (see C1-04).
  - Ten concurrently executing runs add 10 × 20k copies per second from revalidation alone.
  - Starting a run rewrites a JSON file of several megabytes under a lock and fsyncs it twice.
- **Recommendation:**
  - Have `owner()` read from the cached map without copying it; return a single value.
  - Restrict `readDisk()` copies to the write path.
  - Rate-limit `statSync` (or watch the file).
  - Consider an append-only format, or sharding by run id, instead of whole-file rewrites.
  - Prune entries for runs whose logs no longer exist.

### C1-04 — Restricted `runs.list` and `artifacts.list` cost quadratic full-store scans
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/auth/guard.ts:499-521` (`runsList`), `guard.ts:528-575` (`artifactsList`), related `read-model.ts:442-466`
- **Issue:**
  - For a restricted principal, the guard pages the underlying `runs.list` 500 rows at a time until `offset >= total`.
  - `ReadModel.runsList` does not page at the store. On every call it walks all `listRuns()` ids, reads each run's summary events, builds every view, then slices.
  - So one restricted `runs.list` costs ⌈N/500⌉ full-store scans, followed by N `runs.allows` checks, each of which also hits C1-03.
  - A restricted `artifacts.list` with no `runId` does all of that, then pages every visible run's artifacts.
- **Scenario / evidence:**
  - Store with 10,000 runs, MCP adapter on the `client` preset calls `runs.list` (or polls it).
  - The guard makes 20 calls to `ReadModel.runsList`, each running `readTypes` over all 10,000 run logs: about 200k log scans and summary folds per request.
  - Each visible check then copies the ownership map.
  - Unrestricted callers pay a single scan.
- **Recommendation:** Call the read model once with no paging (an internal "all rows" entry point) and filter in memory. Better, push the scope filter (workflow allowlist and owner set) into the read model before it builds views. For artifacts, filter the artifact index by the visible run set in a single `artifacts.list` instead of one call per run.

### C1-05 — `operator.page` paging is quadratic in run length (rows re-projected from offset 0, and the log rescanned per 100-event chunk)
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/operator-read-model.ts:200-207` (cursor skip), `operator-read-model.ts:532-567` (`eventSnapshot`), related `store/src/jsonl-event-store.ts:169-194`
- **Issue:**
  - A cursor stores only an `offset`. Every page re-opens the snapshot and iterates and projects every row from the start, discarding rows while `visible <= after`. For `runs`/`inputs` with enrichment, that includes the HMAC'd boundary projection.
  - The row generator calls `events.readRange(runId, { after, limit: 100 })` repeatedly. The JSONL store implements `after` by scanning and parsing lines from the start of the file (zod per line).
  - Each chunk therefore costs O(after), a full traversal costs O(N²/100) line parses, and page k costs O(k²).
- **Scenario / evidence:** A `runs.read` principal (for example the MCP adapter) pages the `events` collection of a long agent run with about 50k events, at the maximum page size of 100. Reaching the last page parses roughly 12 million JSON lines in one call. Paging the whole collection costs about 500 times that. This is reachable by any principal with `runs.read` on a run it can see.
- **Recommendation:** Encode the last emitted `seq` in the cursor (it is already HMAC-bound) and restart `readRange` from that `seq` rather than from offset 0. Have the generator carry its own byte-offset or `seq` position instead of calling `readRange(after)` repeatedly, or add a seq→offset index to the JSONL store.

### C1-06 — `subscribe { runId, since }` replays the entire tail in one materialized read, coalescing all `agent.update` events into a single giant frame
- **Category:** performance (resource)
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `packages/daemon/src/subscriptions.ts:255-271`, `subscriptions.ts:307-349`, related `protocol/src/subscriptions.ts:456`
- **Issue:**
  - `since` is any non-negative integer.
  - `start()` reads `eventsRange(runId, { after: since })` with no limit, so the whole tail lands in memory at once.
  - Meanwhile every live event is buffered in `this.buffered`, also unbounded.
  - Replayed `agent.update` events are merged into one batch per step and flushed as a single notification carrying every update.
  - Every frame also enters the `delivered` chain (C1-02).
- **Scenario / evidence:** A client subscribes with `since: 0` to a long run (tens of thousands of agent lines, which `read-model.ts` documents as a normal case). The daemon holds the full log, plus per-step arrays of all updates, plus the serialized frames, at the same time. Single frames can reach many megabytes, and memory spikes per subscriber. Any principal with `runs.read` on the run can trigger this.
- **Recommendation:** Replay in bounded pages and await socket drain between them. Cap updates per coalesced `agent.update` frame and split oversized batches. If `lastSeq - since` exceeds a threshold, answer "cursor too old, page with `runs.events`" instead of replaying.

### C1-07 — Plan writes are journalled under a fixed actor (`"daemon"`), not the authenticated principal
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/daemon/src/plan-control.ts:68` (`this.origin = { kind: "human", actor: opts.actor ?? "daemon" }`), `methods.ts:683-705`, `cli/src/commands/index.ts:1039-1047` (no `actor` passed)
- **Issue:**
  - `dependencies.waive`, `decisions.decide`, `decisions.reopen` and `risks.update` ignore `ctx.mutationActor`, which the guard sets for every call.
  - They record the same static origin in the plan journal for every caller.
  - The `journal.list` method presents the plan journal as the plan's audit trail.
  - `claims.release` is likewise unattributed (`control.ts:512-531`).
- **Scenario / evidence:** Two principals hold `plan.write` (the `owner` bootstrap credential and an `operator` credential such as `ci-bot`). Both waive dependencies or decide decisions. Every journal entry says `actor: "daemon"`, so the plan history cannot say who made a decision. Only the separate, owner-only `audit.jsonl` records the principal.
- **Recommendation:** Pass `ctx.mutationActor` through the plan-control methods and build `PlanOrigin.actor` from the principal id per call (and the credential id where the schema allows it). Do the same for `claims.release`.

### C1-08 — Prototype pollution through `config.set` patch paths (`__proto__`), even with `validateOnly`
- **Category:** security (correctness)
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/daemon/src/config-model.ts:583-595` (`setInPlain`), called from `config-model.ts:446` and `config-model.ts:467`, reached from `config-model.ts:280` (`validateOnly`); schema `protocol/src/config.ts:325-327` (`path: z.string().min(1)`)
- **Issue:**
  - `splitPath("__proto__.x")` gives `["__proto__","x"]`.
  - `setInPlain` walks `node["__proto__"]`, which is `Object.prototype`, and assigns `Object.prototype.x = value`.
  - This happens for the permissions sidecar always, and for `orca.config.yaml` when the file is absent or empty.
  - The `validateOnly` branch runs `nextText` too, so a "no writes" validation call pollutes the long-lived daemon process.
  - The sister module `config-collection-edits.ts:33` explicitly refuses `__proto__`, `prototype` and `constructor`; the legacy patch path does not.
- **Scenario / evidence:** `config.set { document:"permissions", expectedRevision:<rev>, patch:[{path:"__proto__.polluted", value:{...}}], validateOnly:true }` from an owner-level client, or from a buggy form that builds paths from user input. `({}).polluted` is now set process-wide, which can change behavior in zod parsing, `in` checks and object-literal lookups until restart. This requires `config.write` plus `config.read` (owner), so it is not a privilege escalation. The test coverage for `__proto__` exists only for collection edits.
- **Recommendation:** Reject the segments `__proto__`, `prototype` and `constructor` in `splitPath`. Build plain objects with `Object.create(null)`, or use `Object.hasOwn` and `Object.defineProperty`. Add a test for both documents and for `validateOnly`.

### C1-09 — WebSocket inbound limits much weaker than `/rpc`: 100 MiB frames, unlimited subscriptions and in-flight requests per connection
- **Category:** reliability (DoS hardening)
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/daemon/src/socket.ts:82-87` (no `maxPayload`), `socket.ts:145-250`; compare `server.ts:137-149` (`MAX_BODY_BYTES = 1_000_000`)
- **Issue:**
  - `new WebSocketServer({ noServer: true, handleProtocols })` leaves `maxPayload` at the `ws` default of 100 MiB, so any authenticated principal (even a `viewer`) can send a single 100 MB JSON message for the daemon to buffer, `String()` and `JSON.parse`.
  - Each message is handled in its own detached async closure, with no cap on concurrent requests.
  - There is no cap on subscriptions per connection. Each one attaches up to five listeners and does per-event projection work.
- **Scenario / evidence:** An authenticated script opens one socket and sends a few 100 MB frames, or creates thousands of store-wide subscriptions. Memory and CPU in the shared daemon grow accordingly, with no equivalent path on `/rpc`.
- **Recommendation:** Set `maxPayload` to about 1 MB to match `/rpc`. Cap subscriptions per connection (for example, 32) and in-flight requests per connection, and refuse beyond the caps.

### C1-10 — `agents.ping` spawns agent processes in a caller-chosen, unconstrained `cwd`, with no concurrency limit (also on `--read-only`)
- **Category:** security
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/daemon/src/agent-model.ts:89-116` (`const cwd = params.cwd ?? host.spec.workspaceRoot ?? ...`), schema `protocol/src/agents.ts:96-103` (`cwd: z.string().min(1).optional()`), `methods.ts:971` (registered whenever `ctx.agents` is set)
- **Issue:**
  - The `cwd` an agent is spawned in for an ACP handshake is any string the caller supplies. It is not confined to `workspaceRoot` or the config directory.
  - Pings are not rate-limited or serialized.
  - Agents such as Claude Code load project-level settings, `CLAUDE.md` and hooks from `cwd` at session start, so the caller chooses which project config a spawned agent loads.
  - `agents.ping` stays mounted on `--read-only` daemons (documented: "neither method touches a run"), where it is the only process-spawning path.
  - The `operator` preset holds `agents.ping`.
- **Scenario / evidence:** On a read-only daemon, an `operator` credential calls `agents.ping { agentId, cwd: "/path/with/.claude/settings.json" }` in a loop. The daemon spawns one agent process per call with that working directory. It costs process churn and runs the agent under arbitrary project configuration.
- **Recommendation:** Ignore or validate `cwd`: restrict it to the host's `workspaceRoot` or the config directory, or drop the parameter. Serialize pings per agent and rate-limit them.

### C1-11 — Audit trail durability: records are not flushed on shutdown, and long-running mutations are only audited when they finish
- **Category:** data-integrity
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/daemon/src/auth/audit.ts:106-130` (async queue), `server.ts:1031-1047` (`close()` never flushes the audit sink), `auth/guard.ts:307-321`, `cli/src/commands/index.ts:1298-1301` and `cli/src/main.ts:162` (`process.exit` right after `serve` returns)
- **Issue:**
  - `close()` awaits pending handlers. Those handlers emit `operation` audit records through `FileAuditSink.record()`, which only queues an `appendFile`.
  - The CLI then returns, and `main` calls `process.exit(code)` without awaiting `flush()`, so records produced during shutdown can be lost.
  - Separately, the guard writes a mutation's `operation` record only after the handler settles. `runs.start`, `runs.resume` and `inputs.answer` with resume drive the run until it parks or finishes, which can take hours. If the daemon crashes first, the trail has no record of who started or resumed the run.
- **Scenario / evidence:** A SIGTERM arrives while `runs.start` is driving a run. `close()` settles the handler, its "failed/succeeded" record is queued, and the process exits before the append lands. In the crash case, no audit line ever appears for that `runs.start`.
- **Recommendation:**
  - Add `flush()` to the `AuditSink` contract and await it in `DaemonHandle.close()`.
  - Write a `started` record before dispatching audited mutations, then an outcome record afterwards (or audit at admission time).

### C1-12 — Raw messages of non-`OrcaError` exceptions are returned to any authenticated caller
- **Category:** security (information disclosure)
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/daemon/src/server.ts:199,217,960`, `socket.ts:168,183,231`; `core/src/errors.ts:84-88` (`if (e instanceof Error) return { code: "INTERNAL", message: e.message }`)
- **Issue:**
  - Any Node or library error reaching `dispatch` is sent back verbatim as `INTERNAL` with its `message`. That covers fs errors (`EACCES: permission denied, open '/home/u/.orca/store/...'`), V8 `JSON.parse` errors (which quote a snippet of the offending text) and zod internals.
  - This reaches restricted principals too.
  - Other parts of the daemon deliberately suppress provider diagnostics (`operator-host-resources.ts:137`), so the generic dispatch path is the outlier.
- **Scenario / evidence:** A restricted `client` principal reads its own run, and a store file is unreadable or a draft or JSON file is corrupt. The response reveals absolute paths, or an excerpt of file contents, from the daemon host.
- **Recommendation:** In `dispatch` and the socket handlers, map non-`OrcaError` and non-`ProtocolFault` exceptions to a generic `INTERNAL` message with a correlation id, and log the full error server-side.

### C1-13 — `inputs.answer` without `runId` scans every run's full state, up to three times per call
- **Category:** performance
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/daemon/src/control.ts:149-173` (`findInput`: `ids = runId ? [runId] : await orc.listRuns()`, then `getState` for each), called at `control.ts:281`, `control.ts:298` (when `always` is set) and `control.ts:103` (`answerAndResume`)
- **Issue:** For unrestricted principals (restricted ones are forced to pass `runId` by the guard), `findInput` folds every run's complete event log until it finds the request. `answerInput` repeats the lookup up to three times.
- **Scenario / evidence:** Answering a gate in a store of thousands of runs without `runId` replays every log, up to three times, on the request path.
- **Recommendation:** Resolve the request once with `pendingInputs()` or an index (the guard already has `resolver.inputRun`), then pass the found `runId` into the later steps.

### C1-14 — Credential-file robustness: no fsync, an unvalidated `expiresAt` fails open, revoked bootstrap records accumulate
- **Category:** reliability
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/daemon/src/auth/credentials.ts:104-110` (`writePrivateFile`: write, chmod, rename, no fsync), `credentials.ts:50,276`, `credentials.ts:206-214`
- **Issue:**
  - `credentials.json` and `local-client.token` are replaced by rename without fsyncing the file or the directory. A power loss can leave a zero-length or partial `credentials.json`, which per the design refuses every credential and blocks daemon start until repaired. `ownership.ts` does fsync.
  - `expiresAt` is `z.string()`. A malformed value gives `Date.parse` → `NaN`, and `NaN <= now` is false, so the credential never expires. This fails open on a malformed record.
  - Every daemon start appends a new bootstrap record and keeps the revoked one forever, so the file grows without bound. It is re-parsed with zod on every change.
- **Scenario / evidence:** A machine crashes shortly after `orca serve` starts; on some filesystems this leaves an empty `credentials.json`. Separately, a hand-edited or third-party-issued record with `expiresAt: "tomorrow"` is accepted indefinitely.
- **Recommendation:**
  - fsync the temp file and the directory in `writePrivateFile`.
  - Validate `expiresAt` and `revokedAt` with `z.iso.datetime()` and treat an unparseable expiry as expired.
  - Prune revoked bootstrap records older than N days.

### C1-15 — HTTP body-limit path cannot actually deliver its 413, and client aborts are reported as 413
- **Category:** reliability (error-handling)
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/daemon/src/server.ts:139-149` and `server.ts:956-961`
- **Issue:**
  - `readBody` throws from inside `for await (const chunk of req)`, and leaving the loop destroys the request stream (and with it the socket). The following `sendJson(res, 413, ...)` therefore usually never reaches the client, which sees a connection reset.
  - The same `catch` maps any read failure, such as a client abort or an `ECONNRESET`, to a 413 that carries the raw error message.
  - The second-admission refusal at `server.ts:965-967` omits `connection: close`, unlike the first.
- **Scenario / evidence:** A 2 MB POST to `/rpc` gets a TCP reset, not the documented envelope.
- **Recommendation:** Check `content-length` up front and answer 413 before reading. On overflow, stop consuming, send 413 with `connection: close`, then destroy. Distinguish `aborted` from oversize.

### C1-16 — An IPv6 host yields malformed `url` and `socketUrl`
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/daemon/src/server.ts:996` (`` const url = `http://${host}:${port}` ``), `server.ts:1030`
- **Issue:** `validateDeployment` accepts `::1` as a loopback bind (`transport.ts:88-92`), but the handle's `url` becomes `http://::1:6722`. That is not a valid URL, and `socketUrlFor` propagates it. Callers and the CLI banner hand out an unusable endpoint.
- **Scenario / evidence:** `orca serve --host ::1` prints and returns `http://::1:6722`.
- **Recommendation:** Bracket IPv6 literals when formatting (`net.isIPv6(host) ? \`[${host}]\` : host`).

### C1-17 — `TransportGate.current()` falls back to the owner principal when `credentialId` is undefined, even in token mode
- **Category:** security (hardening)
- **Severity:** Info
- **Confidence:** High
- **Location:** `packages/daemon/src/auth/transport.ts:204-207`
- **Issue:** `if (this.auth.mode !== "token" || credentialId === undefined) return { ok: true, principal: LOCAL_PRINCIPAL }`. Today every token-mode admission carries a `credentialId`, so the branch is unreachable. If a future path admits a principal without one (a new auth mechanism, a refactor of `Admission`), every socket re-check would silently upgrade that connection to the owner-equivalent `LOCAL_PRINCIPAL`.
- **Recommendation:** In token mode, return `{ ok: false, reason: "unavailable" }` when `credentialId` is undefined, and fail closed.

### C1-18 — Literal NUL bytes embedded in `read-model.ts`
- **Category:** maintainability

### C1-19 — Cross-package relative type imports into sibling packages' `src/`
- **Category:** maintainability
- **Severity:** Info
- **Confidence:** High
- **Location:** `packages/daemon/src/admission-retry.ts:5-14`, `request-submission.ts:3`, `revision-input.ts:3` (`../../core/src/model/admission-retry.js`, `../../engine/src/...`)

### C1-20 — Per-notification synchronous filesystem work and per-subscriber serialization
- **Category:** performance
- **Severity:** Info
- **Confidence:** High
- **Location:** `packages/daemon/src/socket.ts:131-141,193-203`, `auth/credentials.ts:266-272,290-308`
- **Issue:**
  - For every notification, each subscription calls `current()`, which runs `credentials.current()` → `reload()` → a `statSync` on the event loop.
  - Restricted principals add another `statSync` from ownership (C1-03).
  - Every subscriber also re-serializes the same frame with its own `JSON.stringify`.
  - With K sockets and E events per second, that is K×E synchronous stats and K×E serializations.
- **Recommendation:** Cache the credential stamp check for a short TTL, or use `fs.watch` with a periodic fallback. Serialize each notification once per projection variant: with artifacts, without artifacts, and with the subscription id spliced in.

## Strengths

- **Authentication done carefully:**
  - Tokens are 256-bit random secrets stored only as SHA-256.
  - The secret compare uses `timingSafeEqual`, with dummy hashing for unknown ids.
  - All failures map to one generic `AUTH_INVALID`; the reason goes to the audit log only.
  - Credentials in URLs are refused.
  - The bearer subprotocol is never echoed.
  - Files are written 0600 and directories 0700, with a `.gitignore`.
- **Transport policy is sound:** Host checks (against DNS rebinding) and an Origin allowlist apply in both modes, trusted-proxy enforcement blocks direct-backend bypass, and a non-loopback bind is refused without a proxy. `startDaemon` fails closed without an explicit auth policy.
- **Deny-by-default operation inventory:**
  - The operation check runs before params are validated.
  - Restricted scopes can never hold workspace-wide permissions; this is checked at issue time and again at call time.
  - Resource not-founds are canonicalized so they do not confirm existence.
  - Notifications are re-authorized per frame against current grants, with artifact projections applied.
- **Strict read-only mode:** the write methods (control, plan control, `config.set` and `config.apply`, template and draft writes, operator mutations) are absent from the method table, not present-but-refusing.
- **Revocation takes effect promptly:** pinned-credential re-checks after awaits, socket revalidation that closes with 4401, and sealed actors on execution and continuation recovery all stop a revoked credential quickly.
- **Bounded host telemetry:** the native I/O worker has a fixed path allowlist, and the telemetry path has deadlines, busy slots and a publication fence.
- **Defensive path handling:** workflow-draft and template paths are confined by realpath/relative checks and regex-constrained ids (`^[a-z0-9][a-z0-9-]*$`, pack `^[A-Za-z0-9_-]+$`), and refuse symlinks.
