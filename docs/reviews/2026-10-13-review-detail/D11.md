## Findings

### D11-01: Code comment still calls the corrupt-sidecar skip "conservative"; docs say it can drop deny rules
- **Doc:** docs/research/tool-call-safety/current-state.md:121-125 says `loadEffectivePermissionPolicy` skips unreadable sidecars, that sidecars can hold deny/ask rules so skipping can expose later default allows, and that "Source comments that say only grants are lost are too strong". The same position is in docs/adr/0009-permission-grants-in-a-workspace-sidecar.md:130-132 (2026-10-01 clarification), docs/ROADMAP.md:93-94 ("Unreadable permission sidecars can drop deny/ask rules") and policy.md:325-327.
- **Code:** packages/agents/src/permissions.ts:238-246 still says skipping "is the *conservative* direction … Dropping it can turn an `allow` back into an `ask`; it can never turn an `ask` into an `allow`." The behaviour is unchanged: permissions.ts:248-262 skips through `onUnreadable`, and acp-session.ts:121 passes that callback. The comment is false:
  - The sidecar schema permits `deny` (core/model/agent.ts:56,59).
  - `reject_always` writes `deny` rules (permissions.ts:272).
  - Default allow rules are layered after the overlays (agent.ts:289-297; agent.ts:146-148 itself says "a sidecar `deny` still outranks a default `allow`").
  - So dropping a corrupt sidecar can turn a recorded `deny` for a workspace read/edit/delete into a default `allow` (agent.ts:128-138).
- **Variance type:** contradicts-design (the source comment contradicts the ADR 0009 clarification and the research findings; the fail-open behaviour is still open)
- **Severity:** Medium. It misleads maintainers about a safety property, but the ADR, ROADMAP and research all state the gap correctly.
- **Confidence:** High
- **Suggested resolution:** Fix the code comment now. Separately, decide whether to make the skip fail closed (the policy.md:325-327 direction). The docs are right.
