# V5 — Adversarial verification of C5a-01 … C5a-06

HEAD 0c75d01. Static, read-only. Pinned Electron is `^44.4.5` (`packages/app/package.json:33`). I checked Electron behaviour against the upstream `44-x-y` branch: `docs/api/structures/web-preferences.md`, `docs/api/app.md`, `shell/browser/web_contents_preferences.cc` and `lib/browser/guest-window-manager.ts`.

### C5a-01
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **Startup refuses an unsettled attempt.** `reserveFirstRunOwnership` runs strict inspection (`src/main/first-run/ownership.ts:370`), and that inspection refuses any attempt that is not settled (`ownership.ts:327`).
  - **Recovery is same-boot only.** The only repair is `FirstRunRecovery.reconcile`. It refuses when the claim's boot differs from the current one (`src/main/first-run/recovery.ts:72`) and when the writer's boot differs (`recovery.ts:73-77`). `bindQuiescentConfiguration` has the same rule (`recovery.ts:144`). The request schema hard-codes `authority: "explicit-same-boot-fence"` (`ownership.ts:202`). `fenceBoot()` reads `/proc/sys/kernel/random/boot_id`, `kern.bootsessionuuid` or the native Windows boot ID (`packages/protocol/src/first-run-fence.ts:103-141`), so every reboot changes it.
  - **No other recovery route exists.** I searched for alternatives and found none:
    - `packages/cli/src/first-run-recovery-fence.ts` only reports that recovery is needed.
    - `packages/protocol/src/closed-first-run-inspection.ts` is a read-only update inspection and never settles anything.
    - Nothing deletes or rewrites attempts.
    - `assertNoFirstRunOwnership` (`ownership.ts:165-182`) also blocks "Open a store" and `ORCA_WORKSPACE` on that path (`workspace.ts:990, 1052-1054`).
  - **Tests and docs encode this.** `test/first-run-recovery.test.ts:236` expects wrong-boot evidence to be refused. `docs/implementation/first-run-same-boot-recovery.md:7` says "No reboot route is included here."
  - **The Windows trigger is real.** Electron 44's `app.md` says `before-quit`, `will-quit` and `quit` are not emitted on a Windows shutdown, restart or logout. Main handles only `before-quit`/`will-quit` (`src/main/index.ts:1305, 1330`) and has no `session-end`/`query-session-end` handler.
  - **Caveat:** on Windows shutdown, settlement is a race. If the OS kills the child while main is still alive, `onExit` → `recordFirstRunExit` could still write `terminal.json`. Power loss, BSOD, a kernel panic or a forced restart leave the attempt unsettled for certain. The end state is unrecoverable inside the app.
- **Fix note:** The recommended "different-boot ⇒ terminated" settlement is close to #577's `same-host-new-boot-fenced` route, which the doc says must not be composed (`first-run-same-boot-recovery.md:142-146`; "Casey rejected the whole-computer restart prerequisite"). Any cross-boot route therefore needs owner sign-off. It should be an explicit, user-confirmed, fence-held resolution, not automatic. A read-only "export/inspect stranded history" path is a cheaper interim mitigation.

### C5a-02
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium (down from High). The flow fails every time, but in-app updates only run in Windows packaged builds with an operator-provisioned `ORCA_UPDATE_URL`/`ORCA_UPDATE_TOKEN_FILE` (`src/main/update-driver.ts:6-14`; the default feed is `https://updates.invalid/`). The stranding can also be repaired in the app if the user does it on the same boot. It escalates to C5a-01 only if the machine reboots first.
- **Evidence:**
  - **The update stop skips settlement.** `stopForUpdate` calls `this.daemon.stop()` directly and clears `this.daemon` (`src/main/workspace.ts:881-888`). It does not call `stopFirstRunOwned` (`workspace.ts:752-759`), which is the only stop path that calls `complete()`.
  - **No exit callback fires.** `stop()` sets `stopping`, so `onExit`/`recordFirstRunExit` is suppressed (`src/main/daemon-process.ts:347`).
  - **Quit does not settle it either.** After `quitAndInstall`, `close()` sees `this.daemon === undefined` (`workspace.ts:1013-1016`), so nothing writes `terminal.json`.
  - **A failed install cannot reconnect.** `cancelUpdate` → `connect()` → `switchTo(this.target)` (`workspace.ts:907-918, 965-975`). The first-run activation set `target.path` to the first-run workspace and cleared `savedUrl` (`workspace.ts:711-713`), so `assertNoFirstRunOwnership` throws (`workspace.ts:1052-1054`). `Updates.act` swallows that error (`src/main/updates.ts:64`).
  - **Coverage and recovery.** No test covers update with a first-run owner; `test/workspace.test.ts:267-296` covers only read-only stores and external daemons. Same-boot recovery does work after relaunch: status reads `prepared`, the UI offers Prepare recovery and then Reconcile (`renderer/src/first-run/first-run-section.tsx:139, 211`), the fence is free, and `recovery.json` is written. So "manual recovery after every update" is accurate, but "permanent" only follows a reboot.
- **Fix note:** The recommendation is correct. `stopFirstRunOwned` settles only when `daemon.exited === true`. Combine it with `cancelUpdate` reusing the first-run connect path (`connectFirstRun`/`FirstRunSetup.connect`), not `switchTo`.

### C5a-03
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **The cap.** `inspectFirstRunOwnership` refuses unconditionally at `names.length >= 256` (`src/main/first-run/ownership.ts:226`). Each reservation creates `String(names.length+1)` (`ownership.ts:372-376`).
  - **One attempt per launch.** Every app launch with no live owned daemon reserves a new attempt (`workspace.ts:618-620`; only reuse of a live owned child skips it, `workspace.ts:599-608`).
  - **No compaction anywhere.** Nothing in `first-run/**`, `first-run-fence.ts` or the CLI deletes or rotates attempts (searched for `rm`/`unlink`/`rename`).
  - **No way back.** Recovery (`recovery.ts:28, 61`) and status also go through the same inspection, so once the cap is hit nothing in the app can clear it.
  - **This is a known, deferred limitation.** `docs/implementation/first-run-durable-ownership.md:41-43` says inspection is limited "to fewer than 256 prior attempts. Budget exhaustion requires a future explicit archival/reconciliation decision; there is no automatic deletion or rotation." `packages/cli/src/first-run-recovery-fence.ts:7` mirrors the cap. That confirms the mechanism; it does not mitigate it. The default packaged workspace still stops starting after about 255 launches.
- **Fix note:** Compaction must preserve the hash chain (`claim.previous`) and the `effectiveHash` rebind lineage that inspection re-verifies (`ownership.ts:244-258`). A checkpoint record therefore has to carry both the last claim hash and the effective config hash, and it needs its own owner-reviewed authority, consistent with the doc's "explicit archival decision".

### C5a-04
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **HEAD is captured at selection.** `preparedProject` captures `symbolic-ref --short HEAD` and `rev-parse --verify HEAD` (`src/main/first-run/directories.ts:124-130`). `verify()` refuses when either differs from the receipt (`src/main/first-run/setup.ts:158-166`).
  - **Every reopen re-runs it.** `verify()` runs on every `status()` via `readReceipt()` (`setup.ts:101, 127/151`), and on connect and recovery (`setup.ts:333-347`).
  - **The receipt is never refreshed.** `bindConfiguration` rewrites only the config hash and keeps `project` as it was (`setup.ts:450`).
  - **The failure is silent.** `readReceipt` swallows the failure and returns `undefined` (`setup.ts:152-154`). `startFirstRunWorkspace` then falls to `workspace.connect()` (`src/main/first-run/ipc.ts:77`), which reports "Choose a project and empty app workspace in Config." (`workspace.ts:970-972`; `defaultPath` is only `ORCA_WORKSPACE`, `index.ts:693`).
  - **The old history becomes unreachable.** `choose`/`prepare` require an empty workspace (`setup.ts:249, 288`), and the old store cannot be opened (`assertNoFirstRunOwnership`).
  - **Tests and docs.** Tests cover only HEAD changing between choose and prepare (`test/first-run.test.ts:266-280`), not after prepare. The README documents "Reopening checks both root identities, branch/base…" (`src/main/first-run/README.md:30`), so the pin is intended. The README also calls this a "narrow bootstrap" whose "explicit rebind remains integration work", so the orphaning consequence is acknowledged as open work, not designed behaviour. Any commit, pull or branch switch in the selected project triggers it.

### C5a-05
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged; arguably Medium, because deleting `userData/admission-intents.enc` is a workaround, but the in-app message misdirects users to the keychain)
- **Evidence:**
  - **Hard caps.** Reading refuses more than 1000 rows (`src/main/admission-intents.ts:53`). `retain` throws "Run-intent journal is full" at 1000 (`:138`), and `retainGuided` throws the keychain `refusal()` (`:171`, message at `:31-32`).
  - **Records are never removed.** `abandon` only flips `state` (`:213-220`). No code path removes records, and `write()` persists the whole array (`:93-119`).
  - **Every run adds one record.** The palette start keeps its intent after success (`:264`), and the renderer tells users to "abandon it explicitly to start another run" (`renderer/src/palette/start-run.tsx:43`). The renderer never calls `runs.start` directly, so every app-initiated run (palette or guided, `src/main/guided-launch.ts:56, 121`) leaves exactly one record.
  - **One journal for the whole app.** The journal is global per `userData` (`src/main/index.ts:353`), not per workspace, so all targets count toward the 1000.
  - **Cost and coverage.** Each guided review can be up to 64 KiB (`src/main/guided-intent-contract.ts:82`), and every call decrypts and re-validates the whole file. No test exercises the cap.

### C5a-06
- **Verdict:** PLAUSIBLE. The hardening gap is real, but the stated exploit path is refuted.
- **Adjusted severity:** Low (down from High). This is defence in depth, with no reachable trigger at HEAD.
- **Evidence:**
  1. **webPreferences.**
     - `contextIsolation: true` and `sandbox: true` (`src/main/index.ts:1184-1191`).
     - `nodeIntegration` and `webSecurity` are not set, so they take the Electron 44 defaults: Node integration off, web security on.
     - `navigateOnDragDrop` is not set. Its Electron 44 default is `false`: `web_contents_preferences.cc` sets `navigate_on_drag_drop_ = false` and maps it to `renderer_prefs->can_accept_load_drops`.
  2. **Navigation and window-open handlers.**
     - The only navigation handler is `will-frame-navigate` in `src/main/mac-update-windows.ts:90-92`. The reviewer missed it, but it calls `preventDefault()` only while an update hold is active.
     - `setWindowOpenHandler` (`:99`) returns `allow` whenever no hold is active.
     - Both are installed on every window through `browser-window-created` (`index.ts:874`) and `track` (`index.ts:1214`).
     - There is no `will-navigate`/`will-redirect`, no `setPermissionRequestHandler` and no `web-contents-created` hardening.
  3. **Drag-and-drop.** The renderer has no global `dragover`/`drop` prevention; the editor canvas only handles its own MIME type (`renderer/src/workflow/editor/editor-canvas.tsx:366-391`). Because `navigateOnDragDrop` defaults to `false`, dropping a file or link does **not** navigate the window in Electron 44. The reviewer's primary scenario (step 1) is refuted.
  4. **The bridge is origin-agnostic.**
     - The preload exposes `window.orca` unconditionally (`src/preload/index.cts:353`) and obtains a valid epoch with `sendSync("orca:daemon.read")` (`:45`), which main answers without any sender check (`index.ts:930-932`).
     - The generic `handle()` ignores `event` entirely (`index.ts:313-341`).
     - The checks that do exist test only `senderFrame === mainFrame` and membership in a known window (`index.ts:207-220, 1004`). A foreign top-level document passes both.
     - Popups from `window.open` would **not** get the preload: Electron 44's `makeWebPreferences` inherits only security preferences, never `preload`.
  5. **CSP.** `renderer/index.html:16-19` sets `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:` with no inline scripts. CSP cannot block top-level navigation.
- **Realistic attacker path:** none found at HEAD.
  - The production renderer contains no external `<a href>`, no `window.open`, no `iframe`/`webview`, no `dangerouslySetInnerHTML` and no markdown or link rendering of agent output. Artifacts are raw text (`renderer/src/artifacts/artifact-panel.tsx:13, 259`), and the only anchors are in DEV-only preview routes (`renderer/src/routes.tsx:16-18`).
  - Both forms call `preventDefault()` on submit. Deep links route through the in-app hash router, never `loadURL`.
  - Foreign content can therefore reach privileged methods only through a future link or HTML-rendering feature, a renderer XSS that also bypasses the CSP, or `ORCA_RENDERER_URL` in a packaged build (C5a-16).
  - The "extra windows break diagnostics and the draft acknowledgement" side effect also requires an attacker-controlled `window.open`.
- **Fix note:** Drop the renderer-level `dragover`/`drop` recommendation; it is unnecessary in Electron 44. Instead, pin `navigateOnDragDrop: false` explicitly. The main-side controls still matter as defence in depth: a renderer-URL allow-list on `will-frame-navigate`/`will-redirect`, a deny-by-default `setWindowOpenHandler`, a deny-all permission handler, and checking `event.senderFrame.url` against the renderer URL in `handle()` and in the `sendSync` handlers.
