## Findings

### C2-01 — Fan-out "earlier sibling" visibility leaks one work item's artifacts into another's prompts
- **Category:** correctness
- **Severity:** High
- **Confidence:** High
- **Location:**
  - `packages/engine/src/run-context.ts:209-258`: `visibleArtifacts`, `earlierSiblings`
  - `packages/engine/src/orchestrator.ts:1785-1816`: `resolveInputs` by name/kind
  - `workflows/ai-sdlc.yaml:69-72`
  - `templates/sdlc/build.md`
- **Issue:**
  - `earlierSiblings()` makes every child of the same container step visible if it finished before this run was created. That covers the whole subtree, via `collect(sibling, "down")`.
  - The rule was added for `loop` iterations (#32). It is applied to every container, including `parallel` forEach and `custom:plan-dispatch`, whose children are unrelated work items.
  - Optional inputs resolved by name (`visible.get(ref.name)`, newest version wins) therefore resolve to another item's artifacts.
- **Scenario / evidence:**
  1. A program has items A and B. The plan's concurrency is lower than the item count, or B is in a later wave.
  2. A finishes, then plan-dispatch spawns B.
  3. On B's first `build` step, `inputs: [{ name: testReport, required: false }, { name: review, required: false }]` resolves to **A's** `testReport` and `review`. B has produced none yet.
  4. `templates/sdlc/build.md` then renders "## Previous test report … Fix the failures below before anything else" and "## Review feedback … Address every 'changes requested' item" with A's content.
  5. The prompt also tells the agent to "Use only the explicitly supplied input artifacts as prior workflow context", so B's builder is steered to fix A's problems.
  6. `artifacts.*` in every template and condition, and `nextArtifactVersion`, also see A's artifacts. B's first `spec`, for example, gets version A+1.
  7. Whether it happens depends on timing: it depends on whether A completed before B's `run.created`.
  8. `loop-siblings.e2e.test.ts` covers only loops. `plan.e2e` and `program.e2e` use scripted agents and never assert prompt inputs.
- **Recommendation:**
  - Restrict sibling visibility to `loop` steps, where iteration N−1 is the intended predecessor.
  - Alternatively, exclude siblings whose `workItemId` differs from this run's.
  - Cross-item context already has an explicit channel, `vars.upstream`, so this needs no replacement.
  - Add a plan-dispatch test with concurrency 1 asserting B's build inputs exclude A's reports.

### C2-02 — Malformed YAML front matter in a deliverable crashes the turn instead of triggering the bounded follow-up
- **Category:** reliability/error-handling
- **Severity:** High
- **Confidence:** High
- **Location:**
  - `packages/engine/src/executors/agent-step.ts:117-159`: `collect`, especially lines 139-140
  - `packages/core/src/util/frontmatter.ts:21`: `parseYaml` throws
  - `packages/engine/src/orchestrator.ts:1825-1848`: `recordArtifact` re-parses
- **Issue:**
  - `collect()` calls `extractStructuredData()` and `parseFrontMatter()` without a try/catch.
  - yaml@2.9's `parse` throws on any document error, such as `title: Fix: the bug` or duplicate keys.
  - The exception escapes `runAgentTurn`. No `artifact.rejected` is emitted, the problem is never put into the follow-up prompt, and the documented "bounded follow-up listing exactly what is wrong" contract is bypassed.
- **Scenario / evidence:**
  1. An LLM writes `spec.md` whose front matter has an unquoted colon.
  2. `YAMLParseError` propagates to `executeStep`, which records `step.failed` (`INTERNAL`, retryable).
  3. `completion.maxAttempts` defaults to 1 (`core/model/workflow.ts:64,78`), so the whole run fails, although `maxFollowUps: 1` would have let the agent fix it.
  4. Deliverables earlier in the same loop were already recorded (artifact plus plan intake), so a retry records them again.
  5. This applies equally to optional deliverables and to decision nodes with `source.kind: agent`.
- **Recommendation:**
  - Catch parse errors per deliverable in `collect()`.
  - Emit `artifact.rejected` with the reason `front matter is not valid YAML: <message>`.
  - Push the reason to `problems` when the deliverable is required, and skip optional ones.
  - Add a test with an invalid-YAML deliverable that expects a follow-up turn.

### C2-03 — `void self.cancel(child)` races child attachment: unhandled `RUN_LEASED` and a child that is never cancelled
- **Category:** concurrency
- **Severity:** High
- **Confidence:** Medium (timing-dependent)
- **Location:**
  - `packages/engine/src/orchestrator.ts:1725-1733`: `onAbort` / `onOwnAbort`
  - `orchestrator.ts:517-563`: non-live `cancel`
  - `orchestrator.ts:494-511, 1311-1342`: attach window before `live.set`
  - `packages/cli/src/main.ts:139-153`: one-shot commands `exit(1)` on an unhandled rejection
- **Issue:**
  - `cancel(childId)` treats a run as live only once `loadContext` has put it in `this.live`.
  - Between `self.run(childId)` starting and `live.set`, the window spans `getSummary`, `takeRunLease` and `loadContext`. The child is already leased by this orchestrator's `leaseHolder`.
  - `cancel` takes the non-live path and tries to acquire the lease with a fresh holder. The acquire is refused and it throws `RUN_LEASED`.
  - The call is `void`-ed in an abort listener, so the rejection is unhandled. The child is never aborted and runs to completion while the parent waits on it.
  - Conversely, if `cancel` wins the lease first, the child's `run()` throws `RUN_LEASED` and the parent step fails with a misleading "take the lease with `orca leases break`" message.
- **Scenario / evidence:**
  1. A `parallel` node has the default `failFast: true` (`core/model/workflow.ts:308`) and concurrency 3.
  2. Branch A fails fast. `FanOut.halt` aborts `stop.signal` while branch C is inside `executeLeased` (or C registers after the abort, which triggers the `own?.aborted` immediate path).
  3. Under `orca run`/`resume`/`plan dispatch`, the CLI's `unhandledRejection` handler calls `exit(1)` mid-run, leaving the tree running with lapsing leases. The daemon logs and continues, but C runs its full agent workflow anyway.
  4. The same applies to an operator `orca cancel <parent>` during a child's attach.
- **Recommendation:**
  - Make `cancel()` aware of `this.running` without `live`: record a pending cancellation that `executeLeased` checks right after `live.set`, and abort the fresh `rc` then.
  - Attach `.catch(log)` to both listener calls.
  - Add a fail-fast test with a deliberately slow `takeRunLease` for one sibling.

### C2-04 — Child workspace provisioning runs inside the parent's lease mutation mutex, starving heartbeats and sibling writes
- **Category:** concurrency
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/orchestrator.ts:1685-1708`: `rc.withOwnership(() => self.startRun(...))`
  - `orchestrator.ts:448-456`: `provision` is called inside `startRun`
  - `packages/store/src/lease-store.ts:159-251` (`keepLease`: renew uses the same `exclusive(resource)`; `watchExpiry` loses at `renewedAt + ttl`) and `:343-352`
  - `packages/engine/src/workspace/git-worktree.ts:22-49` and `provider.ts:35-77`: no timeout on git
- **Issue:**
  - `runChild` wraps the whole child `startRun` in the parent's ownership mutex. That includes `GitWorktreeProvider.provision`: `git worktree add` of the full tree, possibly over SSH.
  - The parent's heartbeat (`store.renew`) needs the same per-resource mutex. `keepLease` declares the lease lost once `ttl` (60 s by default) passes after the last successful renewal, however long a renewal has been waiting.
  - Sibling `rc.emit` calls (`child.finished`, `child.spawned`, claim writes) also queue on that mutex. `FileLeaseStore` gives up after the default 60 s lock timeout with `STORE_LOCK_TIMEOUT`.
- **Scenario / evidence:**
  1. Plan-dispatch over a large monorepo starts the worktree for a new item. Checkout takes about 50 s.
  2. The parent's renewal is blocked, and roughly 40–60 s after the last renewal `onLost` fires: `rc.leaseLost = true` and an abort.
  3. The program run stops without writing, and siblings' `child.finished` writes time out.
  4. Combined with C2-05, all in-flight item runs are then cancelled.
  5. A git command that hangs, for example on an LFS smudge or a credential helper, blocks forever because there is no timeout.
- **Recommendation:**
  - Provision the workspace outside `withOwnership`.
  - Hold the fence only around the durable writes: `putInputs`, `run.created` and `child.spawned`.
  - Alternatively, let the lease keeper renew through a separate, non-mutating path.
  - Add timeouts to provider git invocations.

### C2-05 — Losing the parent's lease cancels its live children durably
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/orchestrator.ts:1725-1726`: `onAbort` → `self.cancel(childId, "parent cancelled")`
  - `orchestrator.ts:1387-1399` and `run-context.ts:148-159`: lease loss calls `rc.abort.abort()`
  - `orchestrator.ts:1566-1572`: the child writes `step.cancelled` and `run.cancelled`
- **Issue:**
  - `rc.abort` serves both operator cancel and lease loss, and `runChild`'s listener cancels children on any abort.
  - The docs promise that a holder whose lease was taken "stops there, without writing". The parent itself honours that.
  - Its live children, whose own leases are still valid, receive `cancel()` and append `run.cancelled`.
  - The default `breakLease` covers the subtree, so fencing refuses those writes. Two paths are not fenced:
    - `orca leases break <parent> --force --keep` (`descendants: false`)
    - local lease expiry from C2-04
- **Scenario / evidence:**
  1. The parent's lease is broken with `--keep`, or the parent is starved as in C2-04.
  2. The parent aborts and every in-flight item run becomes `cancelled` in its own log.
  3. The new holder resumes the parent. Plan-dispatch re-attaches to those children, sees `cancelled` with `fan.stopped` false, and records the items as `failed`.
  4. No test covers `descendants: false` with live children (`run-lease.test.ts`).
- **Recommendation:**
  - In `onAbort`, skip child cancellation when `rc.leaseLost` is set, since the new holder re-attaches to the children.
  - Alternatively, give lease loss its own signal instead of reusing `rc.abort`.

### C2-06 — `custom:plan-register` and `materialize-work-items` are not idempotent on re-attempt and duplicate work items
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `packages/engine/src/plan/executors.ts:117-195`
  - `packages/engine/src/plan/service.ts:343-482`, with slug suffixing at 354-357
  - `packages/engine/src/program/executors.ts:36-108`
  - resume re-attempt logic at `orchestrator.ts:1474-1480`
- **Issue:**
  - Registration has many side effects: item, dependency, risk and decision puts; journal entries; and the Request status put. They happen before `vars.set` and `step.completed`.
  - On crash-resume, or on any retry when a node sets `maxAttempts > 1`, the step re-runs with the same decomposition.
  - Every slug now "already exists in plan", so each is re-registered as `<slug>-2` with fresh IDs and dependencies.
  - `materialize-work-items` mints fresh IDs and leaves the first batch `pending` forever.
- **Scenario / evidence:**
  1. The daemon restarts while `plan-register` is between `registerWorkItems` and `step.completed`.
  2. Resume emits `step.cancelled` and re-attempts the step.
  3. The plan now holds `api` and `api-2`, both ready.
  4. Plan-dispatch runs both (`scope: request`), creating duplicate agent work, duplicate worktrees (`<root>/api-2`) and duplicate PRs.
  5. No test re-executes plan-register.
- **Recommendation:**
  - Make registration idempotent per `(requestId, decomposition artifact id)`, for example with keyed IDs like risks and decisions use (`keyedId`).
  - Alternatively, short-circuit when items for this request and artifact already exist.
  - Apply the same to materialize-work-items.

### C2-07 — Duplicate slugs within one decomposition corrupt dependency registration
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `packages/engine/src/plan/service.ts:351-392`, `batch.set(item.slug, wi)` at 377
  - `service.ts:396-398, 437-450`
  - `packages/engine/src/program/executors.ts:53-71`
  - `DecompositionSchema` (`core/model/request.ts:177-185`) does not enforce unique slugs
- **Issue:**
  - When a decomposition (agent output) lists `slug: api` twice, the second is renamed `api-2`, but `batch.set("api", wi2)` overwrites the first entry.
  - Later passes use `batch.get(item.slug)`, so both items' `dependsOn`, `parent` and `risks` attach to `api-2`.
  - Other items' `dependsOn: [api]` also bind to `api-2`.
  - The warning wrongly says the slug "already exists in plan".
  - `materialize-work-items` silently drops the first item.
- **Scenario / evidence:** `items: [{slug: api, dependsOn: [db]}, {slug: api, dependsOn: [auth]}]` leaves the first `api` with no dependencies. It is immediately ready and is dispatched before `db` exists.
- **Recommendation:**
  - Reject duplicate slugs in `DecompositionSchema` (superRefine). The `ARTIFACT_INVALID` that results lets an agent follow-up or a human fix it.
  - Alternatively, key `batch` by input index instead of slug.

### C2-08 — `plan-dispatch` with `scope: plan` fails every item from another request when the dispatcher run carries a `requestId`
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `packages/engine/src/orchestrator.ts:1701`: the child inherits `rc.state.run.requestId`
  - `orchestrator.ts:380-386`: "Request and work item associations do not match"
  - `packages/engine/src/plan/executors.ts:612-641`
- **Issue:** `runChild` always forwards the parent's `requestId`. For an item registered by a different request, `startRun` throws `RUN_STATE` after the claim was already taken.
- **Scenario / evidence:**
  1. A program workflow (launched by `orca submit`, so it has a `requestId`) uses `custom:plan-dispatch` with `scope: plan`, a documented option.
  2. Every ready item from earlier requests throws, `FanOut` records the first failure and halts, and the step fails.
  3. Each such item stays claimed by this run until an operator releases it.
  4. Tests only use `scope: plan` with a single request (`plan-dispatch.test.ts:51,117`, `work-item-claims.test.ts:249`), or with no request at all (`plan.e2e` plan-resume).
- **Recommendation:** When `options.workItemId` is set, pass the item's own `requestId`, or omit the parent's when they differ.

### C2-09 — Git worktree directory and branch are keyed by slug only, so different plans' items share a checkout
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/workspace/git-worktree.ts:33-49`
  - `plan/service.ts:336`: "Slugs are unique per plan"
- **Issue:**
  - The directory is `<repo>-worktrees/<slug>` and the branch is `orca/<slug>`.
  - `if (await host.fs.exists(dir)) return …` reuses whatever is there without checking which item or plan owns it, which branch is checked out, or whether a previous `worktree add` failed partway.
- **Scenario / evidence:**
  1. Requests in plans `alpha` and `beta` both decompose to an item `api`.

  - Validate on reuse (`git -C dir rev-parse --abbrev-ref HEAD` equals the expected branch, and the directory is a registered worktree), refusing otherwise.

### C2-10 — `visibleArtifacts` re-reads and decrypts every related run log on every evaluation (cache regression)
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `packages/engine/src/orchestrator.ts:1293`: `loadState: (id) => this.executionState(id)`
  - `orchestrator.ts:579-588`: no cache
  - `orchestrator.ts:296-304`: the terminal cache exists for this purpose
  - `run-context.ts:209-258, 290-293, 305-309`
- **Issue:**
  - The terminal-state cache was added (#17) so that `visibleArtifacts()` would not re-reduce finished children.
  - Since the protected-execution work (`df2d9f3`), `loadState` calls `executionState`. That always does `stores.events.read` plus `executionEvents`, which decrypts protected payloads, for every ancestor, earlier sibling subtree and descendant.
  - `visibleArtifacts` runs on every render, routed edge with `when`, `resolveInputs` and `nextArtifactVersion` (once per recorded artifact).
  - `context-caching.test.ts` only asserts that `getState` is cached, so the regression went unnoticed.
- **Scenario / evidence:** A program with N items, each with about 10 steps and thousands of `agent.update` events, makes every child evaluation re-read the program log plus all earlier items' full logs. That is O(N²) log reads and decryptions per program, and the top-level program run's `summarize` render walks every descendant.
- **Recommendation:**
  - Cache terminal execution states, keyed by run and invalidated by the existing store subscription, as `getState` does.
  - Alternatively, give `visibleArtifacts` an artifact index such as `stores.artifacts.list` by `producedBy.runId`, instead of reducing logs.

### C2-11 — `pendingInputs()` without a run id reduces every run in the store, and the 256-entry FIFO cache thrashes
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - `packages/engine/src/orchestrator.ts:647-669, 689-691` (`answer` without `runId`), `2081`
  - callers: `packages/daemon/src/auth/guard.ts:485` → `auth/resources.ts:61-63`
- **Issue:**
  - `pendingInputs()` calls `getState()` (a full log reduce) for every run id in the store.
  - Terminal states are cached in a FIFO of 256. A sequential scan over more than 256 terminal runs evicts every entry before it is reused, so each scan re-reads every log.
  - The daemon's guard calls it on every `inputs.answer` by a restricted principal, and `answer()` without `runId` calls it again.
- **Scenario / evidence:** A workspace with a few hundred program runs, each spawning loop, parallel and item children, quickly exceeds 256 runs. Each answer then reads the whole store twice.
- **Recommendation:**
  - Skip terminal runs using `getSummary` (cheap `readTypes`) before reducing.
  - Alternatively, scan only `human.requested`/`human.answered` with `readTypes`, or maintain an index of open input ids.

### C2-12 — Truncating or splitting text before value-based redaction leaks partial secrets to the public log
- **Category:** security
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/executors/agent-step.ts:334`: `prompt.slice(0, 400)`
  - `agent-step.ts:188-193`: the coalescing buffer flushes after more than 4000 chars, at a chunk boundary
  - `packages/store/src/execution-store.ts:325-361`: redaction matches whole substrings only
- **Issue:**
  - `ProtectedEventStore` redacts the public payload by searching for each secret's full value.
  - The engine cuts text before it reaches the store: `promptPreview` is sliced at 400 characters, and agent text is split into separate `agent.update` events at a chunk boundary once the buffer passes 4000 characters.
  - A secret that straddles the cut appears in no single string intact, so neither half is redacted.
  - Tool-call args and results capped at 2000 characters in the agents package have the same problem.
- **Scenario / evidence:**
  - A sensitive input (an API token) is rendered into a prompt template at offset 380. The public `agent.turn.started.promptPreview` contains its first 20 characters unredacted.
  - Likewise, if an agent echoes the token across the 4000-character flush boundary, both halves land in public events visible to any `runs.read` client.
- **Recommendation:**
  - Redact before truncating or splitting: the engine can apply `redactExecutionValue` with the run's secrets, which the `rc.logger` already does.
  - Alternatively, have the store mask any suffix or prefix that is a partial secret at a string's edges.
  - Never split the coalescing buffer mid-chunk without a redaction pass over the joined text.

### C2-13 — Resume re-executes a step that already failed non-retryably
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:**
  - `packages/engine/src/orchestrator.ts:1474-1480, 1512-1521`
  - `core/src/events/reduce.ts:132-140`: `willRetry` is not kept on the step
- **Issue:**
  - If the process dies between `step.failed {willRetry:false}` and `run.failed`, resume treats the failed step as interrupted and schedules `attempt + 1` with no budget or retryability check.
  - This covers `WORKFLOW_INVALID`, `AGENT_MODEL_NOT_FOUND`, and agent steps that have exhausted `maxAttempts`.
- **Scenario / evidence:** The resumed attempt can run one more agent turn after the budget was exhausted, or re-run a step whose failure was marked non-retryable.
- **Recommendation:** On resume, if the last step is `failed`, check `willRetry` (carry it in the reduced step, or read the last `step.failed` event). If it is false, emit `run.failed` instead of re-attempting.

### C2-14 — `protectExecutionInputs` over-collects secrets (whole objects, keys, numbers, every enum value)
- **Category:** data-integrity
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/execution-inputs.ts:17-38`
  - `packages/store/src/execution-store.ts:329-343`: `gather` adds object keys and stringified numbers
- **Issue:**
  - A top-level input that merely contains a sensitive property has its whole value pushed as a secret.
  - So does every value of a sensitive enum.
  - The store's `gather` then turns sibling non-sensitive values, property names and numbers into substring needles.
- **Scenario / evidence:** An input `config: {properties: {token: {sensitive: true}, region: {type: string}}}` with value `{token: "…", region: "us"}` makes every "us", "token" and "region" substring in public events and logs become `[REDACTED]` ("stat[REDACTED]"). This garbles timelines and diagnostics for that run and every descendant.
- **Recommendation:** Push only the sensitive leaf values, walking the declaration in parallel with the value. Do not seed enum alternatives that were not selected.

### C2-15 — Rendered artifact paths are not confined to the workspace, and deliverables are read without size or symlink checks
- **Category:** security
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/plan/executors.ts:386-405`: `artifactPath` (default `.orca/plans/{{ vars.plan }}/schedule.md`), then `mkdirp` and `writeFile`
  - `packages/engine/src/executors/agent-step.ts:58-60, 73-84, 130-132`
- **Issue:**
  - `plan-schedule` joins a template rendered from run vars to `cwd` and writes there with no containment check.
  - `planOf` prefers `vars.planId`, so a caller with run-start rights can supply a valid `planId` plus `plan=../../../../<dir>`. That creates directories and writes `schedule.md` outside the workspace.
  - Agent deliverable paths may be absolute.
  - `collect` reads each deliverable fully with no size cap, follows symlinks, and every later `evalContext` loads all visible bodies into memory.
- **Scenario / evidence:**
  - `orca run plan-resume --var planId=<id> --var plan=../../../../tmp/x` writes `/tmp/x/schedule.md`.
  - A runaway agent writing a multi-hundred-MB report is read into one string, stored, and re-read on every render.
- **Recommendation:**
  - Resolve rendered paths and require them to stay under `workspace.cwd`.
  - Render `artifactPath` from the resolved plan's key, not from raw vars.
  - Cap the deliverable size, using `lstat` or a size-limited read.
  - Refuse symlinked deliverables.

### C2-16 — Container results copy every child's full execution vars into the parent's `step.completed`
- **Category:** performance
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/engine/src/executors/containers.ts:36-49`, `:460` (`childVars`)
- **Issue:**
  - `childOutcome` embeds `s.run.vars` for each child. These are the private execution vars, which include everything inherited from the parent, such as `request` (with body), `workItems` and `leafWorkItems`.
  - The parent's `step.completed` payload therefore grows as children × (size of the parent's vars).
- **Scenario / evidence:** A `parallel` forEach over `vars.leafWorkItems` (the materialize flow) with 50 items produces one event of about 50 × (50 items + request) bytes. That is O(N²), and it is reduced into state, exposed in `steps` to every expression, and encrypted and stored twice.
- **Recommendation:** Record only child id, status and outcome, plus vars the child set itself (diffed against the inherited vars), or make the vars opt-in.

### C2-17 — Lease release is not guarded in `executeLeased`, and `execute()`'s `finally` can mask a terminal result
- **Category:** reliability/error-handling
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - `packages/engine/src/orchestrator.ts:1350-1353` (compare the guarded `878-885`)
  - `orchestrator.ts:1578-1582`
- **Issue:**
  - In `executeLeased`, `this.liveInput?.releaseExecution?.(runId)` runs before `await held.release()` with no inner try/finally. If it throws, the keeper keeps heartbeating, so the lease is held indefinitely and a new keeper is added on the next attach.
  - Separately, `execute()`'s `finally` runs `rc.withOwnership(() => plan.onRunFinished(...))`. If the lease was lost after the terminal event, this throws `RUN_LEASED` and replaces the successful return.
- **Scenario / evidence:**
  - A future or embedder `liveInput` whose `releaseExecution` throws leaves a lease that never lapses.
  - A lease broken between `run.completed` and the `finally` makes `run()` reject even though the run completed, and the work-item projection is skipped.
- **Recommendation:**
  - Mirror the nested try/finally from `executeContinuationLeased`.
  - In `execute()`'s `finally`, skip `onRunFinished` when `rc.leaseLost`, or catch and log its failure.

### C2-18 — `artifact-present` mode cancels on mere existence, so a deliverable still being written can be recorded truncated
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/engine/src/executors/agent-step.ts:250-290, 342-351, 387`
- **Issue:** The watcher checks `existsMany` only, then `session.cancel()`s and collects immediately. A file written incrementally is read before it is complete.
- **Scenario / evidence:** An agent streaming a report via `echo >>` or a multi-write tool has it collected mid-write. Validation may pass on the partial front matter and record a truncated artifact.
- **Recommendation:** Require two consecutive polls with an unchanged size and mtime, or a completion marker, before cancelling.

### C2-19 — `parallel` forEach `dependsOn` cycles are not detected and are misreported as failFast skips
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/engine/src/executors/containers.ts:217-227, 264-276, 389-404`
- **Issue:** Branches in a dependency cycle are never `met`, never `unmeetable`, and stay `held`, so they are neither run nor recorded.
- **Scenario / evidence:** `dependsOn: "item.deps"` with a→b→a (agent-authored data) fails with "2 not started: failFast". The real cause, a cycle, is never mentioned, and no `branch.skipped` is written for those items. Their work-item status remains whatever it was.
- **Recommendation:** After the loop drains with no parked prerequisite, mark the remaining held branches `skipped: dependency` and report the cycle (reuse `findCycles` from core).

## Strengths

- **Writes are carefully fenced.** Every execution write goes through `RunContext.withOwnership`, which shares the lease mutation mutex. A broken holder is refused at its next append, and `leaseLost` stops the interpreter without appending.
- **Live permission handling is rigorous** (`live-input.ts`): the claim is taken synchronously before any await, the answer is recorded durably under the lease, and failures are classified as uncertain, refused or expired without allowing replay.
- **Owned-root worktrees are defensive** (`owned-root-worktree.ts`):
  - an exclusive, fsync'd receipt before any git effect
  - symlink and realpath checks on every path component
  - registration validation via `worktree list --porcelain -z`
  - `--end-of-options` and `--` argument separation
- **Admission and retry logic is exact.** It uses canonical JSON with size and depth bounds, re-authorizes at every boundary, and fails closed on any evidence mismatch (`admission-execution.ts`, `admission-retry.ts`, `direct-admission.ts`).
- **Work-item status is a projection of the event log**, not a side write, so a crash mid-dispatch cannot strand an item in `in-progress`.
- **Agent streaming failures do not crash the process.** `UpdateRecorder` buffers agent text into bounded chunks and turns a failed store append into a retryable step failure instead of an unhandled rejection (#268).
