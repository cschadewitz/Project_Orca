### C6-02
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **Stale snapshot.** `palette/command-palette.tsx:62-67` memoises `commandEntries(keyboard.list(), …)` on `[keyboard, scopes, open]` only. `palette/entries.ts:122` copies `run: shortcut.action` into each entry. When the row runs, `run()` (`command-palette.tsx:130-145`) calls `entry.run()` without checking that the shortcut is still registered. `KeyboardMap.register` (`keyboard-map.ts:308-320`) gives every keyless row a fresh slot id, and the palette never compares against it.
  - **Live target.** Every row action in `useCardWrites` (`attention/attention-surface.tsx:480-526`) dereferences `current.current.input`. That ref is reassigned on every render to `waits[focusIndex]` (`:453` and `:107`).
  - **Why focusIndex does not follow the card.** Opening the palette moves focus to its input, so the section's `onBlur` (`:207-209`) sets `inList = false`. The focus-advance effect (`:103-113`) then returns early and `focusIndex` stays at its old number.
  - **Two triggers.** One is removal: `input.answered` from elsewhere, which runs `use-attention.ts:193-196` and then `answered()`. The other, more common one, is insertion: a new **permission ask**, which `orderWaits` puts first (`attention/items.ts:30-31`, not `items.ts:132` as C6-02 and C6-03 cite). Either way, `waits[focusIndex]` becomes a different card while the armed label still names the old run.
  - **Result.** `act.cancel(now.runId)` cancels the wrong run. An answer row goes to the new card when it has a matching option id.
  - **Refutation attempts that failed.** Nothing re-reads the registry while the palette is open. No id check exists in the row actions. `useControls.cancel` (`attention/use-controls.ts:128-142`) sends `runs.cancel` straight away.
  - **Tests.** `test/attention-surface.test.tsx:494-519` only covers the static case.
- **Fix note:**
  - Besides capturing `held.id`, a cheap general guard is for the palette to check, at run time, that `entry.id` (the registry slot) is still present in `keyboard.list()`.
  - Stale rows are unregistered and re-registered under new slot ids when the signature changes, so that check makes them inert in every surface, not only Attention.

### C6-03
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **The effect.** `attention/attention-surface.tsx:103-113` runs on `[ids, waits.length]` whenever `inList.current` is true. React's bubbling `onFocus` from any descendant sets it (`Wait onFocus` at `:228-231`, wired to the section at `answer-card.tsx:209`). The effect then calls `cards.current[min(focusIndex, len-1)].focus()`. Nothing checks which card, or which element inside it, already holds focus.
  - **Insertion ahead of the focused card** (a permission ask always sorts first, `items.ts:30-31`). The `cardRef` callbacks re-key by index (`:384-385`). React runs ref detaches before attaches, so `cards.current[i]` becomes the card that slid into slot *i*. Focus jumps to that different card W.
  - **Even when the focused card keeps its index** (for example, something is added below it), focus moves from the note `<input>` to the card's own `<section>`. That is worse than C6-03 states.
  - **Consequence.** Once focus is out of the text entry, the bare letters typed next are dispatched (`keyboard-map.ts:338`):
    - `J`/`K` move between cards;
    - `G` navigates to the run;
    - digits change the selection;
    - `Enter` submits the card that is now focused, with the half-typed note or with W's default.
  - **Tests.** `test/attention-surface.test.tsx:300-312` ("drops an ask answered somewhere else") never puts focus in the list. Nothing covers a push while focus is inside a card.
- **Fix note:**
  - Also never take focus from a text entry, or from anything inside the card that still exists.
  - Track the focused card by id and only advance when this window's own `onAnswered` removed that id.

### C6-04
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium (was High). The mechanism is certain. The trigger is a reattachment, which is rare for the bundled local daemon and common only for remote or tunnelled daemons and around sleep or wake. What is lost is UI context and small unsent drafts, not stored data.
- **Evidence:**
  - **The bump is published even after a silent blip.** In `packages/app/src/main/connection-state.ts:180-185`, `linkChanged("live")` bumps `generation` on every re-arrival. In `settle()` (`:330-349`), a return to `live` before the 5-second timer fires matches `shown.state`, so the code disarms and calls `publish()`. The snapshot differs in both `generation` and `since`, so the bump reaches the renderer through `useSubscriptionGeneration` (`chrome/use-connection.ts:75-84`).
  - **Every consumer resets synchronously:**
    - `runs/use-runs.ts:59` and `attention/use-attention.ts:111` set `{phase:"loading"}`;
    - `runs/tree/use-run-tree.ts:71-79` does `setDetails(new Map())`;
    - `step/use-step-log.ts:101` creates a new buffer.
  - **Runs loses the selection permanently.** While Runs is loading, `ids = []`, so `runs/use-run-selection.ts:158-160` calls `clear()`. The selection does not come back when the reload lands, and with `detail` undefined the `StepDetail` pane unmounts (`runs-surface.tsx:324-328`).
  - **Attention loses unsent input.** `attention/attention-surface.tsx:127` replaces every card with a spinner, which unmounts `AnswerCard` and drops its local `note`, `text` and `selected`. The only retained draft, `answerDraft` (`use-revisions.ts:690-699`), covers answers that were already submitted and paused, not typed but unsent ones.
  - **Refutation attempts.**
    - The re-read is sanctioned: AGENTS.md says "Reconnect generation changes can require fresh reads", and a store-wide subscription has no cursor to resume from. So the *read* is correct and the *reset* is the defect.
    - The reset is also locked in by tests: `test/reconciliation.test.tsx:204` asserts `phase === "loading"` after `generation: 2`.
    - AGENTS.md:201 ("a blip changes nothing on screen") refers to the banner, but the outcome still contradicts its intent.
- **Fix note:**
  - The stale-while-revalidate recommendation is right.
  - Also gate the selection-clear effect on `state.phase === "ready"`.
  - `test/reconciliation.test.tsx:204` will need to change with the fix.

### C6-05
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged)
- **Evidence:**
  - **The route persists.** `App.tsx:321-331` builds `open` as a fresh object literal on every App render. `route` (`App.tsx:68`) is only replaced by the next `navigate` (`:177-185`) or by `closeLaunch`, and Runs never clears it.
  - **The effects re-fire on every App render.** `runs/runs-surface.tsx:136-138` (`[open, selectRun]`) and `:143-152` (`[open, detail, selectStep]`) compare by identity. App re-renders whenever:
    - Runs reports crumbs (`runs-surface.tsx:208`, which leads to `setCrumbs` and then `setHeader({...})` at `App.tsx:101-103`);
    - attention publishes (`useAttention` state lives in App);
    - the connection changes.
  - **What the person sees.** Clicking run B leads to new crumbs, an App re-render, a new `open`, and `selectRun(A)`. The selection snaps back.
  - **It also drops steps in the linked run.** `reduceSelection` `select-run` (`use-run-selection.ts:87-88`) returns `{selectedRunId: A}` with no step. So after a run-only link, clicking a step *inside A* is also undone.
  - **No loop.** The second pass is a no-op through `settle()`/`same()`, which explains why this does not crash and goes unnoticed in tests.
  - **Tests.** `test/entry-points.test.tsx:65-84` and `test/keyboard-map-agreement.test.tsx:179-187` only assert the first landing.

### C6-06
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium (was High). This is a stale secondary display. The output pane still prints tool-call titles as dim lines (`step/line-buffer.ts:95,110`). Permission waits still show live, because `human.requested` arrives on `event.appended`. No wrong action results.
- **Evidence:**
  - **Where tool calls are read from.** `step/step-detail.tsx:79` folds `log.events`. `foldToolCalls` (`step/tool-calls.ts:131-140`) reads tool calls only from `agent.update` events.
  - **What feeds `events`.** In `step/use-step-log.ts:183-205`, live `agent.update` goes only to `buffer.push`. `events` grows only from `event.appended`.
  - **`event.appended` never carries them.** The daemon returns before emitting `event.appended` for `agent.update` (`packages/daemon/src/notifications.ts:155-158`: "deliberately absent from the raw stream").
  - **Refutation attempts that failed.** `Step` is keyed on `step.id` only (`step-detail.tsx:52`), so it is not remounted when the status changes. Nothing re-reads `runs.events` while the step runs.
  - **Practical effect.** A call settled by `agent.permission` goes back to `pending` (`tool-calls.ts:160`) and never reaches `ok` or `failed`. New calls never appear. The list only refreshes on re-selection, or incidentally on a generation bump (C6-04).
  - **Tests.** `test/step-detail.test.tsx:235-300` only scripts the initial read.

### C6-07
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium (was High). This is a real keyboard and follow-mode visibility defect on the main lists. It is a 2px (comfortable) or 10px (compact) overshoot, and scrolling recovers. No state is lost.
- **Evidence:**
  - **The header is in flow inside the scroller.** It is rendered at `list/virtual-list.tsx:256-279`, before `.orca-list__rows`. `.orca-pane__head` has `height: var(--bar-pane)` = 34px (`packages/design/css/components.css:59-69`, `tokens.css:258`). `--sticky` only adds `position: sticky; top:0` (`:75-79`), and a sticky element keeps its in-flow space.
  - **The arithmetic ignores it.** `measure()` uses `scroller.clientHeight`, which includes the header (`list/use-list-viewport.ts:88-99`). `revealScrollTop`, `isAtBottom` and `listWindow` (`list/list-window.ts:102-134`, `:186-191`) all assume row *i* starts at `i*R`.
  - **Searched for an offset, found none:** no `scroll-padding` anywhere in `packages/design/css`, no header-offset prop or metric, no CSS that moves the header out of flow (`runs/runs.css:117-126` only lays out cells).
  - **The reviewer's arithmetic holds.** A downward reveal sets `scrollTop = (i+1)R − V`, which puts row *i*'s top at `V + H − R`, i.e. V+2 (comfortable) or V+10 (compact). The row is fully hidden. Following reveals `count−1` the same way, so the newest row stays hidden.
  - **Upward reveals are fine.** The row lands exactly under the sticky header.
  - **Affected lists.** These pass `header`: `runs/tree/run-tree.tsx:176`, `runs/timeline/timeline.tsx:193`, and also `plan/schedule-table.tsx:103`, which C6-07 did not list.
- **Fix note:** `plan/schedule-table.tsx` is affected as well. Measure the header with the same `ResizeObserver` that measures the scroller, so a density or zoom change keeps the offset right.

### C6-08
- **Verdict:** CONFIRMED
- **Adjusted severity:** High (unchanged). This app is keyboard-first. On a live run, `K`, `Home`, `PageUp`, a minimap click, `n`/`N`, and even picking a step in the tree are undone within about 100ms. In the timeline, a keyboard user has no way to hold the position.
- **Evidence:**
  - **Programmatic moves never report leaving the bottom.** `offsetTo` sets `bottomRef` *before* assigning `scrollTop` (`list/use-list-viewport.ts:151-156`). The resulting scroll event in `onScroll` (`:185-197`) therefore sees `was === bottom`, and `leave()` never fires.
  - **No caller holds following itself.** These paths call `reveal` and never `onHold`:
    - `move` (`list/virtual-list.tsx:211-219`);
    - the selection effect (`:228-230`);
    - the minimap `onGoTo={reveal}` (`:310`);
    - output-pane `goTo` for search (`step/output-pane.tsx:155-158`).
  - **The follow effect wins.** `virtual-list.tsx:236-238` re-runs on every `count` change while `follow` holds and calls `reveal(count−1)`.
  - **Only one workaround exists.** The output pane's `G` calls `onHold` by hand (`output-pane.tsx:179-185`), and its comment admits the substrate does not report key moves. Runs only resets `follow` on a run change (`runs-surface.tsx:139`).
  - **An extra effect.** After a programmatic move, `bottomRef` is already false, so a following *wheel* scroll also fails to release until the next append re-pins the bottom.
  - **Tests.** None cover releasing follow by key.
- **Fix note:**
  - Put the release in the paths a person drives (`move`, the minimap and `goTo`), or in `reveal` with the `index < count−1` guard as recommended.
  - Make sure the follow effect's own `reveal(count−1)` and the selection effect on a fresh run do not trip it unintentionally.

### C6-09
- **Verdict:** CONFIRMED. The no-cap claim, the O(n)-per-append claim and the live-vs-replay divergence are all certain. The overlap or double-count claim is real, but the mechanism in C6-09 is slightly off (see Evidence).
- **Adjusted severity:** Medium (was High). Growth is per selected live run and resets on a run change or a reattachment. The 100k-row figure assumes about 4 hours of continuous streaming on one selected run. It degrades a long watch but breaks nothing.
- **Evidence:**
  - **No cap.** `PAGE = 200` (`runs/timeline/use-run-events.ts:38`), but `append` (`:150-157`) adds every `agent.update` notification and every `event.appended` with no trim. Nothing in `timeline-entries.ts` or `timeline.tsx` caps or windows `entries`.
  - **O(n) per append.** `mergeEntries` (`timeline-entries.ts:163-179`) rebuilds a Map over all held rows and sorts them on each append. Then these rerun in full on the new `entries`:
    - `kindsOf` (`timeline.tsx:93-95`);
    - the filter, `selectedIndex` and `ticks`;
    - `eventsIn` twice (`:179`);
    - `buildSelectionIndex` (`runs-surface.tsx:156`).
  - **Divergence.** `agentUpdateEntry` (`:142-153`) makes one row per 100ms batch. `toEntries` (`:92-115`) merges every consecutive update for the same step into one row. The test at `test/timeline-entries.test.ts:411-431` only compares one batch against an identical range.
  - **Overlap, corrected mechanism.** In the reviewer's example (pending 10–14 next to replayed 10–20), the row keyed 20 is overwritten by the live 15–20 batch, whether it arrives during the read or after it. That case heals. The persistent case is a page snapshot that ends mid-batch, for example replayed 10–17 followed by live 15–20. That is likely whenever a run is selected mid-stream, and it leaves overlapping rows and double-counted "N agent updates" that never heal, because rows are merged by `seq` alone.
- **Fix note:**
  - Extending the last row on append changes its `seq`, which is its row id, its DOM id and its `selectedSeq`. Selection must follow the range, or rows need keying by `fromSeq`.
  - The merge must be range-aware: trim or replace overlapping `fromSeq..seq` spans. Keying by `seq` alone does not prevent overlap.
