## Findings

### C4-01 — Default configuration puts ORCA's own policy, credential and store files inside the agent's workspace, where the default permission policy auto-allows read/edit/delete (agent can grant itself allow-all)
- **Category:** security
- **Severity:** High
- **Confidence:** High
- **Location:** `packages/cli/src/bootstrap.ts:204` (local provider root = `configDir` when `workspace.root` unset); `packages/core/src/config.ts:90` (default `workspace: { provider: "local" }`); `packages/core/src/model/agent.ts:128-139` (`DEFAULT_PERMISSION_POLICY` allows `read/search/edit/delete/move` with `scope: workspace`); `packages/agents/src/permissions.ts:80-111,187-189,248-263` (sidecar `orca.permissions.json` lives in `configDir`, is re-read on every ask, and its rules are layered *before* the default rules); `packages/agents/src/acp-session.ts:214-219` (`fs/write_text_file` writes with no policy check).
- **Issue:** With the default workspace provider the run's workspace *is* the config directory. That directory holds `orca.permissions.json` (the live permission sidecar), `orca.config.yaml`, `auth/local-client.token` + credentials, and the `.orca` store. `workspaceRelativePath()` classifies all of them as "inside the workspace", so an agent that declares no explicit `default:` (the documented default) gets auto-`allow` for reading the daemon token and for editing/deleting the sidecar, config and event store. Nothing in the evaluator has a protected-path concept (`protectedPaths` exists only as a proposal in `docs/research/tool-call-safety/policy.md:174`).
- **Scenario / evidence:** `orca run ai-sdlc` in a project with an `orca.config.yaml` and no `permissions:` block. A prompt-injected agent (e.g. instructions in a repo README) asks to edit `orca.permissions.json` (`kind: edit`, location `<configDir>/orca.permissions.json`) → `decidePermission` matches `{kind: edit, scope: workspace} → allow` without asking anyone. It writes `{"version":1,"agents":{"<id>":{"rules":[{"match":{},"decision":"allow"}]}}}` — valid under `PermissionPolicyFileSchema` (every `match` field optional). Because `policyForAsk()` re-reads the sidecar per ask and overlays precede the default rules, the very next `execute` ask (normally `ask`) is auto-allowed. The same auto-allowed read exposes `auth/local-client.token` (a bearer token usable for `inputs.answer`/`permissions.grant` on the local daemon), and auto-allowed `delete` can remove `.orca/` run history.
- **Recommendation:** Add a non-overridable protected-path check in `decidePermission`/`resolvePermission` (and in the `fs/*` client handlers) that forces `ask`/`deny` for the config file, the sidecar, `auth/`, `storeDir`, `.git/hooks`/`.git/config`, regardless of configured or sidecar rules. Separately, refuse or warn at bootstrap when the resolved workspace root contains `configDir`/`storeDir`/`auth`, and/or default the local provider to a sub-directory. Consider failing the sidecar load if it contains a rule with an empty `match` (a hand-written wildcard is better placed in config).

### C4-02 — Local agents inherit the full ambient environment of the CLI/daemon, including ORCA bearer tokens and integration API keys
- **Category:** security
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/agents/src/hosts/local-host.ts:50` (`env: { ...process.env, ...agent.env, ...options.env }`); env consumers: `packages/cli/src/daemon-client.ts:49` (`ORCA_DAEMON_TOKEN`), `packages/cli/src/commands/mcp.ts:120` (`ORCA_MCP_TOKEN`), `packages/cli/src/commands/index.ts:1194-1195` (`ORCA_MAINTENANCE_TOKEN`, `ORCA_ADMISSION_FILE`), `packages/integrations/src/jev/executor.ts:143` (`TYPESAFE_API_KEY`).
- **Issue:** Every coding agent spawned on the local host receives the parent's entire environment. The repo already scrubs some ORCA variables before they can leak to children (`update-bootstrap.ts:17-20`, `bootstrap.ts` deletes `ORCA_FIRST_RUN_LAUNCH`, `tools/deploy/orca-release.py:362` pops `ORCA_MAINTENANCE_TOKEN`), but the agent spawn path has no deny-list at all. Documented as a gap in `docs/research/tool-call-safety/current-state.md` ("LocalHost merges ambient process.env"), unmitigated.
- **Scenario / evidence:** A user exports `ORCA_DAEMON_TOKEN` (needed for `orca revisions`) or `ORCA_MCP_TOKEN` in their shell profile; Kepler/Zed launches `orca acp` from that environment; every downstream `claude-code-acp` inherits the token and can call the daemon's `inputs.answer`/`permissions.grant` to approve its own `ask` permissions or human gates. `TYPESAFE_API_KEY` configured for the JEV node likewise reaches every agent.
- **Recommendation:** Build the agent environment from an allow-list (PATH, HOME, locale, TERM, provider keys explicitly named in `agents[].env`/`agents[].inheritEnv`), or at minimum strip `ORCA_*` credentials (`ORCA_DAEMON_TOKEN`, `ORCA_DAEMON_TOKEN_FILE`, `ORCA_MCP_TOKEN`, `ORCA_MAINTENANCE_TOKEN`, `ORCA_ADMISSION_FILE`) and integration secrets (`TYPESAFE_API_KEY`) before spawn. Apply the same policy to `mcpServers[].env` delivery.

### C4-03 — SSH host puts agent environment values (including API keys) on the local `ssh` command line for the life of the session
- **Category:** security
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/agents/src/hosts/ssh-host.ts:66-73,89-93`
- **Issue:** `spawnAgent` renders `agent.env` as `env K='v' …` inside the remote script, which becomes an argv element of the local `ssh` process (and of the remote `bash -lc` until it execs). On Linux `/proc/<pid>/cmdline` is world-readable by default, so any local user (and `ps aux`) can read the values for as long as the agent session lives (per-run pooled sessions can last hours). `docs/REAL-AGENT-TEST.md:121-127` explicitly recommends placing `ANTHROPIC_API_KEY`/`CLAUDE_CODE_OAUTH_TOKEN` in `agents[].env`. Env *keys* are also interpolated unquoted, so a key containing shell metacharacters is executed by the remote shell (config-controlled; hardening).
- **Scenario / evidence:** `hosts: [{id: buildbox, type: ssh}]`, `agents[].env.ANTHROPIC_API_KEY: sk-ant-…` → `ps -o args= -p $(pgrep -n ssh)` on the daemon machine shows `ssh -T … ci@build.internal -- bash -lc 'cd /srv/work && exec env ANTHROPIC_API_KEY=sk-ant-… claude-code-acp'`.
- **Recommendation:** Send the environment over stdin instead of argv (e.g. remote script `IFS= read -r … ; export …; exec agent` fed a NUL/length-prefixed preamble before ACP traffic), or use `ssh -o SendEnv` with `AcceptEnv` on the server, or write a 0600 env file via the existing `writeFile` path and `set -a; . file; rm file`. Validate env keys against `^[A-Za-z_][A-Za-z0-9_]*$` in `AgentSpecSchema`.

### C4-04 — Host file reads are unbounded and SSH file operations have no timeout or cancellation (daemon memory blow-up / permanently hung step)
- **Category:** reliability / resource-leak
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/agents/src/hosts/local-host.ts:23` (`readFile(p, "utf8")`); `packages/agents/src/hosts/ssh-host.ts:84-87,98-106` (`cat` with no `timeoutMs`); `packages/agents/src/host.ts:185-216` (`stdout += d` unbounded, no `AbortSignal`); `packages/agents/src/acp-session.ts:199-213` (`fs/read_text_file` reads the whole file before applying `line`/`limit`); callers `packages/engine/src/executors/agent-step.ts:130-132,269` pass no timeout.
- **Issue:** (a) Neither `HostFileSystem.readFile` implementation has a size cap; the ACP `fs/read_text_file` handler and artifact pickup read whole files into the daemon heap. `withinRoots` is lexical, so a symlink inside the workspace to `/dev/zero` (or a multi-GB log named as a deliverable) is followed. (b) `SshHost.exec` — used for `readFile/writeFile/exists/existsMany/mkdirp` and `git worktree add` — passes no timeout, does not set `ServerAliveInterval`, and `collectChildProcess` accepts no abort signal, so a half-open SSH connection (laptop sleep, NAT drop) blocks forever and `orchestrator.cancel()` cannot interrupt it.
- **Scenario / evidence:** Agent runs `ln -s /dev/zero report.md` (auto-allowed edit) for a planned deliverable; local pickup allocates up to 2 GiB before `ERR_FS_FILE_TOO_LARGE`; over SSH `cat` streams forever, `stdout += d` eventually throws `RangeError: Invalid string length` inside the `data` listener (uncaught → `orca run` exits 1; `orca serve` logs and keeps an unsettled promise and a running ssh child). Separately, `existsMany` in `watchForArtifacts` and the post-turn `collect()` hang indefinitely on a dropped connection; `Promise.all(planned.map(readFile))` also opens one ssh connection per deliverable at once, tripping sshd `MaxStartups` (10:30:100) for steps with many deliverables unless the user configured ControlMaster.
- **Recommendation:** Add `maxBytes` to `HostFileSystem.readFile` (stat + regular-file check locally with `O_NOFOLLOW`/`lstat` policy; `head -c N` + `test -f` remotely) and to the ACP read handler; add a default `timeoutMs` and an `AbortSignal` to `exec`/`collectChildProcess`, cap collected stdout, add `-o ServerAliveInterval=15 -o ServerAliveCountMax=3` to `baseArgs()`, and batch reads into one ssh process (as `existsMany` already does).

### C4-05 — `orca ping` silently falls back to a local in-process handshake when the daemon's `agents.ping` takes longer than 2 s or returns 5xx
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/cli/src/daemon-client.ts:84-92,110` (`AbortSignal.timeout(2000)`, `catch { return undefined }`, `!response.ok → undefined`); `packages/cli/src/commands/index.ts:203-206,442-460`; daemon side `packages/daemon/src/agent-model.ts:89-116` (spawn + initialize + session/new + close with 2 s+2 s exit grace).
- **Issue:** The code and tests (`cli/test/runtime-auth.test.ts:194-260`) state that once a daemon has answered, the CLI must never fall back to spawning locally. But every `daemonCall` uses a 2 s timeout, and a timeout, transport error, non-2xx (other than 401/403/3xx) or schema mismatch on the `agents.ping` call returns `undefined`, which `pingViaDaemon` treats as "no daemon".
- **Scenario / evidence:** Daemon running with a real `claude-code-acp` agent (cold start + handshake routinely 3–10 s; handshake timeout is 30 s). `orca ping claude` → hello succeeds, `agents.ping` aborts at 2 s → CLI bootstraps ephemerally and spawns a second agent locally, printing "recorded nothing: no daemon answered on http://127.0.0.1:6722" while the daemon concurrently records its own result. Two agents spawn; the message is false.
- **Recommendation:** Use a per-method timeout (≥ handshake timeout + cleanup grace for `agents.ping`), and once `hello` succeeded treat any later failure as an error (`AGENT_TRANSPORT`, "daemon did not answer agents.ping") rather than `undefined`. Add a test with a slow `agents.ping` responder.

### C4-06 — Config discovery walks to the filesystem root with no ownership check, and every bootstrap (including `orca validate`/`status`) imports the discovered config's plugins
- **Category:** security
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/cli/src/bootstrap.ts:146-163` (`findConfig` upward walk), `:170-189` (`loadConfig`), `:345`, `:585` (`await import(importUrl)`), `packages/cli/src/commands/index.ts:319` (`validate` loads plugins), `main.ts:21` ("nearest one upwards from cwd").
- **Issue:** Any `orca.config.yaml` in any ancestor directory is trusted: its `plugins:` are executed in-process, its `agents[].command` is spawned by `ping`/`run`, its `storeDir` is created and written (first-run fence, generation persistence). Unlike git's `safe.directory`, there is no check that the file/directory is owned by the current user or not group/world-writable.
- **Scenario / evidence:** On a shared host another user creates `/tmp/orca.config.yaml` with `plugins: ["./x.mjs"]` and `/tmp/x.mjs`. The victim runs `orca validate` (or `orca runs`, `orca status`) from `/tmp/work-123/` → `import("file:///tmp/x.mjs")` runs attacker code as the victim. Same effect for running `orca validate` on a checked-out untrusted PR that adds a plugin entry.
- **Recommendation:** During discovery, stop at (and refuse) config files/directories not owned by the current uid or writable by group/others (POSIX), and stop the walk at `$HOME`/filesystem boundaries; print which config was used. Make read-only commands (`validate` without `--plugins`, `status`, `events`, `runs`) not import plugins, or require an explicit opt-in for plugin execution on discovered configs.

### C4-07 — ACP facade rewrites the kinds of forwarded permission options (index 0 → `allow_once`, all others → `reject_once`)
- **Category:** security / design
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `packages/integrations/src/acp-facade/upstream-human-input.ts:76-82`; kind dropped upstream at `packages/engine/src/orchestrator.ts:1976` (`options: offered.map((o) => ({ id: o.optionId, label: o.name || o.optionId }))`).
- **Issue:** Downstream permission asks reach the facade as generic human questions with no option kind, and `UpstreamHumanInput.ask` assigns kinds positionally. Agents commonly order options `[allow_always "Always Allow", allow_once "Allow", reject_once "Reject"]`, so the upstream client receives "Always Allow" as a *one-time* allow and "Allow" as a *reject* variant.
- **Scenario / evidence:** Kepler/Zed render options by kind (icons/colours, keyboard shortcuts) and some clients auto-handle by kind (e.g. "reject when unattended" picks the first `reject_once`): such a client would select "Allow", approving the tool call. A user who clicks the one-time-styled first option actually grants the downstream agent a standing `allow_always`.
- **Recommendation:** Carry `kind` through `HumanInputOption` for `kind: "permission"` questions and forward the real ACP kinds; only use positional kinds for workflow gate decisions. Consider filtering `allow_always`/`reject_always` for upstream forwarding (as the live path already does) unless the facade can honour the standing grant.

### C4-08 — JEV evaluation silently drops inputs whose aliases collide while still recording them as judged
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/integrations/src/jev/executor.ts:80-82` (`inputAlias`), `:172-189` (`artifacts[alias] = a.content` overwrites; `inputs.push(...)` keeps both); `:311-322` (`onError: record` writes `inputs: []`).
- **Issue:** The alias defaults to the artifact name/kind. Two inputs resolving to artifacts with the same name (e.g. `fromNode: design, kind: spec` and `fromNode: review, kind: spec`, both named `spec`) share one key in `state.artifacts`; the second silently replaces the first, but the provenance (`inputs[]`, artifact `parents`, rendered "## Inputs" list) claims both were evaluated. The routing decision downstream is therefore based on an evaluation of different material than the durable record says. Not covered by `integrations/test/jev-eval.test.ts`.
- **Scenario / evidence:** A rubric comparing an implementation spec against a revised spec of the same name → only the revised one is sent to System One; the evaluation artifact lists both with hashes.
- **Recommendation:** Reject duplicate effective aliases in `parseNode` (validation time) and at execute time; require `as:` when names collide. In `onError: record`, keep the resolved `inputs`/`missingInputs` when the failure occurred after resolution.

### C4-09 — CLI prints agent/repository-controlled text to the terminal without stripping control characters (prompt spoofing in `humanInput.mode: cli`)
- **Category:** security
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `packages/cli/src/human-input-cli.ts:61-66` (question + option labels written raw); `packages/cli/src/format.ts:38-47,59` (agent message chunks, tool titles, permission titles); `packages/core/src/events/event-payload.ts:28-35` (`text()` does no sanitisation).
- **Issue:** Tool titles, agent message chunks, permission option names and human-question text originate from the agent, which often quotes repository content (file names, file contents). ESC/CSI/OSC sequences pass straight through to the operator's terminal.
- **Scenario / evidence:** A malicious repository contains a file whose name embeds `\x1b[2K\x1b[1A` sequences; the agent's permission request title "Edit <name>" is printed by `cliHumanInput` and can erase/rewrite the preceding lines so the operator sees a benign question and option list while answering the real one; OSC 52 can write the clipboard in terminals that allow it. `orca run`'s event stream (stderr) and `orca events` have the same exposure.
- **Recommendation:** Sanitise all untrusted strings before terminal output (replace C0/C1 controls except `\n`/`\t`, e.g. with `\u{2400}`-style escapes or `JSON.stringify` slices) in `formatEvent`, `formatRunState`, `formatPendingInput` and `cliHumanInput`.

### C4-10 — Agent process cleanup only signals the direct child; over SSH the remote agent keeps running after cancel/timeout
- **Category:** reliability / resource-leak
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/agents/src/process-cleanup.ts:226-272`; `packages/agents/src/hosts/ssh-host.ts:90-93` (`ssh -T`, no pty, no remote process-group handling); `packages/agents/src/hosts/local-host.ts:48-52` (no `detached`/process group).
- **Issue:** Killing the local `ssh` client closes the channel, but with `-T` the remote process gets no SIGHUP, only EOF on stdin/EPIPE on its next stdout write. An agent that is "wedged" (the reason `requestCancel` escalates to kill) or busy in a long tool call keeps running and keeps editing the remote worktree; local agents' descendants (shells, test runners, dev servers) are orphaned similarly. Documented as "outside the guarantee" in `docs/research/tool-call-safety/current-state.md`, but the consequence for retries is not.
- **Scenario / evidence:** A remote step hits `turnTimeoutMs`; ORCA kills ssh and the engine retries the step in the same `git-worktree` directory while the first agent is still writing files there → two agents interleave edits; the artifact recorded may be the stale agent's.
- **Recommendation:** Run the remote command under a small wrapper that puts the agent in its own process group and kills it when stdin closes (e.g. `setsid` + a watchdog loop on the stdin pipe, or `ssh -tt` with care for ACP framing); locally spawn with `detached: true` and signal `-pid`. Before retrying a step in the same workspace, require a confirmed exit or a fresh workspace.

### C4-11 — Windows: `LocalHost.exec` runs POSIX-quoted strings through `cmd.exe`
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/agents/src/hosts/local-host.ts:63-70` (`shell: true`); `packages/agents/src/host.ts:88-92` (`shellQuote` single-quote escaping, leaves `%` unquoted); caller `packages/engine/src/workspace/git-worktree.ts:41-48,64`.
- **Issue:** On win32 `shell: true` means `cmd.exe /d /s /c`, where single quotes are literal characters and `%NAME%` expands. Windows is a tested platform (`agents/test/hosts.test.ts:76`).
- **Scenario / evidence:** `workspace: {provider: git-worktree, repo: "C:\\Users\\Jane Doe\\proj"}` → `git worktree add 'C:\Users\Jane Doe\proj-worktrees\x' 'orca/x'` → git receives `'C:\Users\Jane` etc.; provisioning fails.
- **Recommendation:** Make `exec` take argv (`execFile` style) for local hosts, or use a host-specific quoter (`cmd`-aware quoting / PowerShell) and keep POSIX quoting for SSH only.

### C4-12 — `orca demo --dir <existing dir>` overwrites `README.md` and `orca.config.yaml` without checking
- **Category:** data-integrity
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/cli/src/commands/index.ts:759-763,902-907`
- **Issue:** `--dir` is documented as "retains the chosen workspace" and is accepted for an existing directory; the command unconditionally writes `README.md`, `orca.config.yaml` and `demo-playbook.yaml` there.
- **Scenario / evidence:** `orca demo --dir .` inside a real project replaces its README and its ORCA configuration with the demo's.
- **Recommendation:** Refuse a non-empty `--dir` (or one containing either file) unless `--force`, or write into `<dir>/orca-demo-<id>`.

### C4-13 — MCP operator reports an already-committed write as an error when re-discovery differs after the call
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/integrations/src/mcp/server.ts:205-219`
- **Issue:** For write tools (`submit_request`, `start_workflow`, `cancel_run`, `respond_to_approval`, `continue_run`, `revise_input`) the backend mutation has already been applied when the post-call `discover()` runs. If the scope changed (credential narrowed/revoked mid-call) the tool returns `AUTH_FORBIDDEN "Operator authority changed during the call"`; if the output fails schema parsing it returns `PROTOCOL_MESSAGE`. Neither tells the LLM operator that the effect may have committed (contrast the `AGENT_TRANSPORT` path, which says "Do not assume a write failed"). Only the read path is tested (`mcp-operator.test.ts:194-206`).
- **Scenario / evidence:** An approval is applied, the operator's credential is rotated concurrently → the model tells the user the approval was forbidden; for `submit_request` it may resubmit with a fresh idempotency key, creating duplicate work.
- **Recommendation:** For `write: true` operations, never convert a successful backend result into a plain failure: return the (possibly withheld) result with an explicit `committed: true, authorityChanged: true, inspect: <operationId>` marker, or an error whose text states the write may have committed and names the retained key/operation ID.

### C4-14 — Permission rule matching robustness: unvalidated `titlePattern`, empty `pathPrefix` wildcard
- **Category:** reliability / security
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/agents/src/permissions.ts:99` (`new RegExp(m.titlePattern)` per rule per ask), `:104-107`; schema `packages/core/src/model/agent.ts:63,72`.
- **Issue:** (a) `titlePattern` is never validated as a regex at config/sidecar load; an invalid pattern throws inside the `session/request_permission` handler for every ask that reaches it (the agent receives an internal error), and because sidecar *parsing* succeeds the "skip corrupt sidecar" logic never applies. A catastrophic pattern (hand-written) is evaluated against agent-controlled titles of unbounded length on the daemon's event loop, stalling every run. (b) `pathPrefix: "."`/`"./"` normalises to `""`, is filtered out, and the prefix constraint is then skipped entirely — the rule matches any request, including ones with no or outside-workspace locations (string `startsWith` semantics are otherwise documented).
- **Scenario / evidence:** `rules: [{match: {kind: execute, pathPrefix: "."}, decision: allow}]` intended as "commands in the workspace" allows every `execute`.
- **Recommendation:** Validate `titlePattern` with `new RegExp` in the schema (`refine`), compile once per policy load, cap the tested title length; reject `pathPrefix` values that normalise to empty (or treat them as "workspace" scope explicitly).

### C4-15 — JEV HTTP provider persists provider error bodies and has no transport hardening
- **Category:** security
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/integrations/src/jev/http-provider.ts:26-56`; `packages/integrations/src/jev/executor.ts:146-147,219-220,309-322`.
- **Issue:** On non-2xx the default (environment-configured) provider copies up to 400 characters of the response body into `JevProviderError.message`, which becomes the step failure message (event log) and, with `onError: record`, the evaluation artifact body. The restoration provider in the same package explicitly refuses this ("A proxy may echo authorization in an error body; never persist transport text", `restoration.ts:229-236`), but the shipped default plugin does not. `TYPESAFE_BASE_URL` is accepted with `http:`, and `res.json()`/`res.text()` are unbounded.
- **Scenario / evidence:** An egress proxy or API gateway returning a 400/407 page that echoes request headers stores `Authorization: Bearer <TYPESAFE_API_KEY>` in the run's public history.
- **Recommendation:** Apply the restoration path's sanitisation to the default provider (status code only, or a fixed-charset excerpt with the key literal redacted), require `https:` unless an explicit loopback override is set, and bound response size.

### C4-16 — T3 Code session adapter (exported groundwork) defaults to `full-access` and has lifecycle bugs
- **Category:** security / correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/integrations/src/t3code/session.ts:38` (`runtimeMode ?? "full-access"`), `:62-74`, `:104-125`, `:130-135`.
- **Issue:** The exported `openT3CodeSession` bypasses ORCA's permission policy entirely by default (T3 threads in `full-access` never ask). ### C4-17 — Read-only CLI commands run the full writer bootstrap

- **Severity:** Low

### C4-18 — SSH `host`/`user` not validated against option injection
- **Category:** security (hardening)
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/agents/src/hosts/ssh-host.ts:44-58`; schema `packages/core/src/model/agent.ts:12-28`.
- **Issue:** The destination is appended before `--`, so a `host` value beginning with `-` (e.g. `-oProxyCommand=…`) is parsed by `ssh` as an option and executed locally. Config is operator-controlled, but `config.set` makes it daemon-writable (`docs/daemon-security.md:109`) and the schema gives no protection; `user` is similarly unvalidated.
- **Recommendation:** Reject `host`/`user` starting with `-` or containing whitespace/`@` (user) in `SshHostSchema`; pass the destination after `--`, i.e. `[...options, "--", dest, ...remote]`.

### C4-20 — ACP facade session bookkeeping: concurrent prompts clobber `active`, sessions never released
- **Category:** concurrency / resource-leak
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `packages/integrations/src/acp-facade/orca-acp-agent.ts:154-165,377-379,404-409`
- **Issue:** A second `session/prompt` on the same session overwrites `session.active`; when the first finishes, `finally { delete session.active }` removes the second's marker, so `session/cancel` can no longer cancel the still-running run. `sessions` (holding the client context and an ever-growing `runIds`) is never pruned, and `/status` re-reads every run's state.

### C4-22 — MCP Streamable HTTP handler maps any discovery failure to 401 and triples daemon round trips
- **Category:** reliability / performance
- **Severity:** Low
- **Confidence:** High
- **Location:** `packages/integrations/src/mcp/transport.ts:185-194`; `server.ts:183-212`
- **Issue:** Each HTTP request pre-flights `discover`, and `tools/call` then runs `discover` twice more (before and after), so one tool call costs four daemon RPCs. A daemon outage/timeout during the pre-flight returns `401 WWW-Authenticate: Bearer`, which MCP clients interpret as "credential invalid" and may discard or re-prompt for the token.
- **Recommendation:** Return 503 for `AGENT_TRANSPORT` failures and 401 only for `AUTH_*`; reuse the pre-flight discovery result as the first discovery of the request's server.

### C4-24 — CLI sends the workspace bearer token over plaintext loopback TCP to whoever owns port 6722
- **Category:** security (hardening)
- **Severity:** Info
- **Confidence:** Medium
- **Location:** `packages/cli/src/daemon-client.ts:46-60,84-92`; `commands/index.ts:163-169`.
- **Issue:** `ping`/`agents` auto-read `auth/local-client.token` and POST it to `http://127.0.0.1:6722/rpc` before verifying the responder. On a multi-user host another user who binds the port while the daemon is down receives the token (it remains valid until the next daemon start rotates it).

### C4-26 — ACP stdio framing relies entirely on the SDK for size limits
- **Category:** reliability (hardening)
- **Severity:** Info
- **Confidence:** Low
- **Location:** `packages/agents/src/host.ts:117-122` (`acp.ndJsonStream` over child stdio), `:94-107` (`StderrTail`).
- **Issue:** ORCA applies no maximum line/message size to agent stdout before JSON parsing; a misbehaving agent emitting a multi-hundred-MB line without newline is buffered by the SDK (not verifiable here — SDK source not vendored). `StderrTail` keeps 50 "lines" but a line is bounded only by chunk size and partial lines are split across chunks.

## Strengths

- **SSH defaults are sound:** `BatchMode=yes` (so unknown host keys fail closed rather than prompting/auto-accepting), `ConnectTimeout`, argv-based `spawn` of `ssh` (no local shell), and consistent single-quote escaping of every interpolated path/command for the remote shell.
- **Daemon clients are carefully hardened:** `revisions` and `DaemonOperatorBackend` refuse credentials in URLs, plaintext non-loopback HTTP, and redirects; bound request and response sizes; validate every response against strict schemas; and never echo backend diagnostics. `daemonCall` refuses to auto-send a discovered token to a non-loopback address and never follows redirects.
- **The ACP permission plumbing has real liveness/staleness protection:** asks are bound to the exact live turn and session, late answers are dropped via `AbortSignal`, cancel escalates to a bounded kill, and handshake failures always run bounded cleanup.
- **maintenance-mcp is a convincing read-only design:** a closed input schema, fixed aliases, fixed absolute binaries with `shell: false` and a scrubbed env, `O_NOFOLLOW` + root-owner checks on procfs, byte/record/deadline budgets enforced while reading, allow-listed output projection (no free-text log bodies), and an unconfigured-by-default adapter.
- **Standing-grant derivation is conservative:** kinds are always kept, `execute` is scoped to an escaped, anchored title, outside-workspace and whole-workspace paths and volatile identifiers are refused, and sidecar writes are serialised under a lock with revision-checked replacement.
