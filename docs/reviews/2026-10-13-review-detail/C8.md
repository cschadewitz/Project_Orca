## Findings

### C8-01 — Release workflow gives every job a `contents: write` token, including the one that runs dependency code on the self-hosted runner with stored credentials
- **Category:** security (ci-cd, supply-chain)
- **Severity:** High
- **Confidence:** High
- **Location:** `.github/workflows/release-publish.yml:42-43` (workflow-level `permissions: contents: write`), `:46-99` (`check` job), `:56-59` (checkout without `persist-credentials: false`), `:68` (third-party action), `:75-83` (`pnpm install`, lint, `pnpm test`, build)
- **Issue:**
  - `contents: write` is granted at workflow level, so the `check` job gets it too. That job runs on `[self-hosted, linux, x64, homelab]` and executes thousands of third-party packages: the esbuild and electron postinstalls, then vitest, eslint, typescript, happy-dom and Playwright during typecheck, lint, test and build.
  - `actions/checkout` keeps its default `persist-credentials: true`, so the write token sits in the git configuration for the rest of the job. Any process in the job can read it.
  - Only the `publish` job needs write access. The reusable `desktop.yml` and `app-smoke.yml` already downgrade themselves to `contents: read`.
- **Scenario / evidence:**
  - A compromised dependency already in the lockfile — for example one merged through a weekly Dependabot group bump — runs during `pnpm test` on a release run. This is the token-harvesting pattern of the 2025 npm worms.
  - It reads the token from the checkout credentials and, while the job is still running, can do any of the following through the REST API:
    - delete and re-upload assets on an *already published* release. For example, it can replace `ORCA-0.6.0-win-x64.exe` on `v0.6.0`, so later downloaders get a backdoored, unsigned installer.
    - create or move tags.
    - push commits to any unprotected branch, including `main`. `docs/RELEASING.md` implies `main` has no required checks: "only worth making if `main` ever gains required status checks".
  - The same job also runs the third-party action `pnpm/action-setup@v6` after checkout (see C8-02).
- **Recommendation:**
  - Set `permissions: contents: read` at workflow level and grant `contents: write` only on the `publish` job.
  - Add `persist-credentials: false` to the `check` checkout. Keep `fetch-depth: 0`; tags arrive with it.
  - In `publish`, run no dependency installs (true today) and put it behind a protected environment (see C8-04).

### C8-02 — The third-party action `pnpm/action-setup` and all other actions are pinned by mutable tag, including in jobs with a write token on the self-hosted runner
- **Category:** supply-chain
- **Severity:** High
- **Confidence:** High
- **Location:** `pnpm/action-setup@v6` at `release-publish.yml:68`, `ci.yml:59`, `ci-shadow.yml:120`, `app-smoke.yml:92,205` and `desktop.yml:74`. Also tag-pinned: `actions/checkout@v7`, `actions/setup-node@v7`, `actions/cache@v6`, `actions/upload-artifact@v7`, `actions/download-artifact@v8` and `github/codeql-action/*@v4`.
- **Issue:** Every action reference is a floating major tag. `pnpm/action-setup` is published outside GitHub. It runs after checkout in the release `check` job (write token in the checkout credentials, self-hosted host) and in the `ci-shadow` `workflow_run` job (`actions: read`).
- **Scenario / evidence:**
  - Someone gains push access to `pnpm/action-setup` (compromised maintainer or CI) and repoints `v6`. This is the tj-actions/changed-files incident pattern of March 2025.
  - The next merged release PR runs the attacker's code on the homelab runner. It reads the persisted `contents: write` token, and anything else on the host, then tampers with releases or tags as described in C8-01.
  - Dependabot's grouped `github-actions` updates (`dependabot.yml:41-47`) keep tags current but give no integrity guarantee.
- **Recommendation:**
  - Pin every action to a full commit SHA with a `# vX.Y.Z` comment. Dependabot updates SHA pins.
  - At minimum, SHA-pin `pnpm/action-setup`. Alternatively, drop it from write-token jobs and use the `packageManagerDependencies` pnpm pin through `corepack` or `npx pnpm@12.4.2`.

### C8-03 — The release verification job runs `pnpm test` before `pnpm run build`, so compiled-MCP acceptance tests will fail on the clean checkout and block the next release after it merges
- **Category:** ci-cd (correctness)
- **Severity:** High
- **Confidence:** High
- **Location:** `.github/workflows/release-publish.yml:82-83`; `packages/integrations/test/mcp-operator-production-fixture.ts:239-248`; `tools/test/m10-owned-plugin.test.js:23`; compare `ci.yml:156-159`
- **Issue:**
  - `ProductionFixture.create()` throws `"Acceptance requires a fresh compiled build"` when `packages/cli/dist/main.js`, `packages/integrations/dist/mcp/transport.js` or `packages/testing/dist/scripted-agent/main.js` is missing. Ten integration test files call it from `beforeEach`/`sharedFixture` with no skip condition.
  - `ci.yml` builds first on purpose ("Production MCP acceptance launches the emitted daemon and MCP entry points").
  - `release-publish.yml` keeps the older order: `pnpm test` (82), then `pnpm run build` (83). `actions/checkout` defaults to `clean: true` (`git clean -ffdx`), so no `dist/` survives from earlier runs on the self-hosted runner.
- **Scenario / evidence:**
  - The production fixture landed in `9720e7d` on 2026-10-03. The last release, 0.6.0, is dated 2026-09-29, so no release has run through this ordering since then.
  - The next `release: vX.Y.Z` merge will fail in `check`. `main` is then left with the version bump and no tag, which is exactly the fix-forward situation `RELEASING.md` describes.
  - Release verification has also drifted from CI in three other ways:
    - It does not run `design:check`.
    - It does not set `ORCA_MCP_REQUIRE_PRODUCTION=1`, so `requireProduction()` calls `ctx.skip()` instead of failing.
    - It does not run the `ORCA_RETRY_INTEGRATION` no-skip retry acceptance, so those tests skip silently.
  - So reordering the steps alone would let the release gate pass with production acceptance skipped. The release PR itself never runs CI (it is opened with `GITHUB_TOKEN`), so this job is the only verification the tagged tree gets.
- **Recommendation:**
  - Make the release `check` job match the CI code lane: build before test, plus `design:check`, `ORCA_MCP_REQUIRE_PRODUCTION: "1"`, the retry-acceptance step and the compiled smoke.
  - Better, factor the CI steps into a reusable workflow or composite that both CI and release call, so they cannot drift again.
  - Add a test in `tools/test` that asserts the release job's step order and environment, like the existing `ci-shadow-evidence.test.js` assertions on `ci.yml`.

### C8-04 — Release publication can be dispatched from any ref, with no environment approval and no check that the commit is on `main`
- **Category:** security (ci-cd)
- **Severity:** Medium
- **Confidence:** High
- **Location:** `.github/workflows/release-publish.yml:30-36,47-58,116-208`
- **Issue:**
  - `workflow_dispatch.inputs.ref` accepts any branch or SHA, and the `release`-label requirement only applies to the PR-close path.
  - Nothing checks `git merge-base --is-ancestor $sha origin/main`.
  - No job uses an `environment:` with required reviewers or deployment-branch rules. The feed secret is therefore available to any dispatcher (see C8-05).
- **Scenario / evidence:**
  - Any account with write access pushes an unreviewed branch whose `package.json` says `9.9.9`, then dispatches "Release (publish)" with `ref=that-branch`.
  - The workflow tags it, publishes an official GitHub release marked latest, and — if `ORCA_FEED_HOST` is set — activates it on the private `stable` feed. The forward-only check passes, and Windows clients auto-update to it unsigned (see C8-06).
  - This bypasses whatever review protects `main`. `RELEASING.md` documents dispatch as the fix-forward path for `main` "or the fixed commit".
- **Recommendation:**
  - In `check`, require `git merge-base --is-ancestor "$sha" origin/main` unless an explicit, logged override is given.
  - Run `publish` in a `release` environment with required reviewers and a deployment-branch rule.
  - Move `ORCA_FEED_SSH_KEY` and `ORCA_FEED_KNOWN_HOSTS` into that environment.

### C8-05 — The feed deploy key is a repository-wide secret with unrestricted shell on the feed host, and the job overwrites the self-hosted runner's `known_hosts`
- **Category:** security (secrets)
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `.github/workflows/release-publish.yml:186-208`; `tools/deploy/publish-feed.py`; `docs/UPDATING.md:99-108`
- **Issue:**
  - **Repository scope.** `secrets.ORCA_FEED_SSH_KEY` is a repository secret, so any workflow on any branch can reference it. Writers can add one that prints or uses it.
  - **Interactive shell.** The job uses the key as `ssh host python3 - …` with the script on stdin. That only works without a forced command, so the key is a general shell on the "trusted distribution host" that serves code to every Windows client. `UPDATING.md` claims the account "needs write access only to the feed root".
  - **Runner-wide files.** The step writes the key to `~/.ssh/orca-feed` in the persistent homelab runner's home, and replaces `~/.ssh/known_hosts` wholesale (`:204`), clobbering host keys other jobs or tools on that runner rely on.
  - **Late cleanup.** The `trap` that removes the key is registered after the key and `known_hosts` writes (`:202-205`). A failure in between leaves the private key on disk.
- **Scenario / evidence:** One leaked key gives a shell on the feed host. From there an attacker can replace `stable/latest-x64.yml` and the installer, and both are trusted by clients with no publisher signature (C8-06).
- **Recommendation:**
  - Make the secret environment-scoped (see C8-04).
  - On the host, restrict the key with `restrict,command="/usr/bin/python3 /opt/orca/publish-feed.py …"` in `authorized_keys`, and send the archive on stdin rather than through `scp`.
  - On the runner:
    - `umask 077`.
    - Write the key and known-hosts file under `$RUNNER_TEMP`.
    - Pass `-o UserKnownHostsFile=$RUNNER_TEMP/kh -o StrictHostKeyChecking=yes -o IdentitiesOnly=yes -F /dev/null`.
    - Set the `trap` before writing anything.

### C8-06 — Desktop artifacts and Windows auto-updates are unsigned, so feed-host or pipeline compromise means code execution on every client (known, documented gap)
- **Category:** supply-chain (release signing)
- **Severity:** Medium
- **Confidence:** High
- **Location:** `packages/app/electron-builder.yml` (`mac.identity: null`, `notarize: false`, no `win` signing); `.github/workflows/desktop.yml:200-218`; `tools/deploy/release-assets.py:21-37`; `docs/RELEASING.md` "Signing and notarisation are not done"; `docs/UPDATING.md:110-117`
- **Issue:**
  - Every installer is unsigned. `electron-updater` on Windows then has only the `sha512` in `latest-ARCH.yml`, served by the same feed host.
  - `release-assets.py` and `publish-feed.py` check consistency inside the pipeline, not authenticity: no signature and no signed manifest.
- **Scenario / evidence:** Any of three paths delivers code to all clients at their next update check:
  - a write-token compromise in the release run (C8-01, C8-02);
  - a leaked feed key (C8-05);
  - an unauthorised dispatch (C8-04).

  The project documents this and says "HTTPS/checksums protect distribution but do not substitute for publisher identity".
- **Recommendation:**
  - Before wider rollout, add Windows Authenticode signing (Azure Trusted Signing) and set `publisherName` so `electron-updater` verifies signatures.
  - Until then, consider a detached signature over the feed manifest (minisign or ed25519) that the app verifies with a key built into the app.
  - Keep the release notes saying the builds are unsigned.

### C8-07 — One self-hosted `homelab` runner serves release builds and publishing as well as jobs that can run arbitrary refs; it is exposed if the repository goes public
- **Category:** security (ci-cd)
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - Release jobs on the runner: `release-publish.yml:51,119` (`check` and `publish`, the latter holding the feed key), `release-prepare.yml:32`, `desktop.yml:51` (Linux packaging)
  - Dispatch jobs on the same label: `app-smoke.yml:15-27,39,84,184` (free-form `ref` input), `changelog.yml:32,51-56` (checks out a PR head), `selfhosted_runner_smoketest.yml` (no `permissions:` block, so it gets the default token), `codeql.yml:174`
  - `codeql.yml:150-155` suggests making the repository public.
- **Issue:**
  - Release publication shares the same label, and possibly the same host, with workflows a writer can point at any ref.
  - `app-smoke` documents "a manual run can verify a branch". With `ref=refs/pull/N/head` of a contributor's PR it runs that PR's `pnpm install`, build and Playwright on the homelab runner.
  - None of these self-hosted checkouts set `persist-credentials: false`.
  - If the runner is not ephemeral, these all persist between jobs and can be poisoned by an earlier job, then reused by the next release's Linux AppImage and `tar.gz` packaging:
    - the pnpm store (`setup-node cache: pnpm` restores into the runner home);
    - `~/.cache/electron` and `~/.cache/electron-builder` (they hold downloaded `appimagetool` and Electron zips);
    - `~/.ssh` (C8-05).
  - `codeql.yml` suggests "make the repository public". Then any fork PR could add a workflow with `runs-on: [self-hosted, homelab]`, because `pull_request` workflows come from the PR's merge commit.
- **Scenario / evidence:**
  1. A maintainer dispatches App smoke with a contributor's PR ref to get screenshots.
  2. The PR's `postinstall` or test code writes a modified tool binary into `~/.cache/electron-builder`.
  3. The next release's Linux leg packages with it.
- **Recommendation:**
  - Make the homelab runner ephemeral (JIT or `--ephemeral`, fresh VM or container per job).
  - Put release jobs on a separate runner group restricted to selected workflows and refs (`release-publish.yml` on `main` only).
  - Restrict dispatch `ref` inputs to branches of this repository, or use hosted runners for arbitrary-ref verification.
  - Add `permissions: contents: read` and `persist-credentials: false` to the smoke-test, changelog and app-smoke checkouts.
  - Before going public, move every self-hosted job behind runner-group workflow restrictions.

### C8-09 — Version math skips the final release after a prerelease, and accepts pinned versions that go backwards or come from unintended text
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `tools/release.js:46-74,170-174`; `.github/workflows/release-prepare.yml:78-79`
- **Issue:**
  - `nextVersion()` ignores the prerelease part. From `0.7.0-rc.1`, a `release:patch` milestone gives `0.7.1` and a minor gives `0.8.0`, so `0.7.0` is never produced unless someone pins it.
  - `--pin` is only checked for syntax, not for being greater than the current version.
  - The milestone pin regex is a case-insensitive substring search for `release:[[:space:]]*v?X.Y.Z`, so text like "pre-release: 0.9.0" or "Follows release: v0.5.0" in a description is taken as the pin.
- **Scenario / evidence:**
  - After publishing `0.7.0-rc.1`, closing the next label-driven milestone proposes `v0.7.1`.
  - A typo'd or quoted older version in a milestone description produces a PR that bumps `package.json` backwards. Only human review of the bot PR catches it, and there are no `release.js` tests.
- **Recommendation:**
  - If the current version has a prerelease part, a bump to the same base should give the base: `0.7.0-rc.1` with patch becomes `0.7.0`.
  - Refuse a `pin` that is not greater than the current version.
  - Anchor the pin regex to a whole line, `^Release:\s*v?…$`.
  - Add unit tests for `nextVersion` and the pin handling.

### C8-10 — An unvalidated version string is spliced into shell scripts in `desktop.yml`
- **Category:** security (script injection, hardening)
- **Severity:** Low
- **Confidence:** High
- **Location:** `.github/workflows/desktop.yml:105` (`version="${{ inputs.version }}"`), `:261` (`cp … "orca-daemon-${{ steps.version.outputs.version }}.mjs"`); source `release-publish.yml:90-99` (no semver check)
- **Issue:** `inputs.version` is `package.json`'s `version` from the released ref and is never format-checked. Expression interpolation puts it in the script verbatim.
- **Scenario / evidence:**
  - On the dispatch path (C8-04), a branch whose `package.json` has `"version": "1.0.0\"; curl … | sh; \""` runs the injected command on all three desktop runners, including the self-hosted one.
  - Exploiting it needs write access, so this is hardening rather than escalation. The feed step already validates the same value (`release-publish.yml:200`).
- **Recommendation:**
  - Validate `^\d+\.\d+\.\d+(-[0-9A-Za-z.-]+)?$` in the `check` job's "The version being released" step.
  - In `desktop.yml`, pass `inputs.version` and `steps.version.outputs.version` through `env:` and reference `"$VERSION"`.

### C8-11 — Predictable temp paths on shared hosts, and the feed host never verifies installer hashes
- **Category:** security
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `release-publish.yml:155` (`/tmp/notes.md`), `:206-208` (`/tmp/orca-feed.tgz`, remote `/tmp/orca-feed-$VERSION.tgz`); `tools/deploy/publish-feed.py:63-75`
- **Issue:**
  - The self-hosted publish job writes fixed names in the shared `/tmp` instead of `$RUNNER_TEMP`.
  - The upload goes to a predictable world-writable path on the feed host.
  - `publish-feed.py` checks member names and that both channel YAMLs exist, but not that each installer's `sha512` matches its YAML. Integrity was verified only on the runner (`release-assets.py`).
- **Scenario / evidence:** On a feed host with other local users and no `fs.protected_regular`, an attacker pre-creates `/tmp/orca-feed-0.7.0.tgz` as a world-writable file. `scp` writes into it, and the attacker swaps the content before the `ssh` step extracts it into the immutable snapshot. With `protected_regular=1`, the same pre-creation instead makes the upload fail, which is a denial of service.
- **Recommendation:**
  - Use `$RUNNER_TEMP` on the runner.
  - Stream the archive over `ssh` stdin into `mkdtemp(dir=root)`, or upload to a 0700 directory inside `FEED_ROOT`.
  - Re-verify each `latest|prerelease-ARCH.yml` `sha512` against its installer in `publish-feed.py` before `os.rename`.

### C8-12 — A feed activation failure after the GitHub release is published cannot be retried through the workflow
- **Category:** reliability
- **Severity:** Low
- **Confidence:** High
- **Location:** `release-publish.yml:139-208`
- **Issue:**
  - The release becomes public (`gh release edit --draft=false`) before the feed step runs.
  - Re-running the failed `publish` job, or dispatching again, stops at the "tag already exists" guard (`:147-150`) before reaching the feed step.
- **Scenario / evidence:** The feed host is temporarily unreachable during publication, so the GitHub release exists but `stable` still points at the old version. Recovery is the documented manual procedure (`UPDATING.md:106-108`), done by hand on the host.
- **Recommendation:** Split feed activation into its own idempotent job or workflow keyed on an existing published release, which downloads its assets and re-verifies them. Alternatively, make the tag guard skip release creation when the release already exists with identical assets.

### C8-13 — Concurrency settings contradict their comments and can drop queued runs
- **Category:** ci-cd
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `release-publish.yml:27-40`, `desktop.yml:35-39`, `ci.yml:14-16`
- **Issue:**
  - **Release publication.** Every closed PR, including no-op ones, joins the workflow-level `release-publication` group. GitHub keeps one running and one pending run per group, so a newer pending run cancels an older pending one — which could be a queued fix-forward dispatch.
  - **Desktop.** `desktop.yml` says a release's run should not be cancelled, but in a reusable call `github.event_name` is the caller's. For a release started by merging a PR it is `pull_request`, so `cancel-in-progress` evaluates to `true`.
  - **CI.** `ci.yml` cancels in-progress `main` push runs. The selected-PR design relies on "main catches regressions" and on per-commit full-suite evidence (ci-shadow), and that evidence is lost for intermediate commits.
- **Scenario / evidence:** While a 30–60 minute release run is in progress, a maintainer queues a dispatch and then two unrelated PRs are closed. The dispatch is cancelled as superseded.
- **Recommendation:**
  - Move release concurrency to job level on `check` and `publish`, or compute the group as `release-publication` only for qualifying events and `noop-${{ github.run_id }}` otherwise.
  - In `desktop.yml`, test `github.workflow == 'Desktop' && github.event_name == 'pull_request'`, or take a `cancel` input.
  - In `ci.yml`, use `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`.

### C8-14 — Long jobs have no `timeout-minutes`, so a hang holds the single homelab runner for up to 6 hours
- **Category:** performance (CI time, reliability)
- **Severity:** Low
- **Confidence:** High
- **Location:** `ci.yml` `check` job (only the retry step has a 3-minute bound); every job in `release-publish.yml`, `desktop.yml`, `app-smoke.yml` (`smoke`, `changes`, `type-proof` jobs), `release-prepare.yml` and `changelog.yml`
- **Issue:** The default limit is 360 minutes. A hung Electron, xvfb, Playwright or vitest worker can occupy the runner, and the release-publication concurrency group, for six hours. `DEVELOPMENT.md` says the owner requires capacity checks before homelab jobs.

### C8-15 — The design-token lint has easy false negatives that contradict the "no literal sizes or radii" rule
- **Category:** maintainability (lint correctness)
- **Severity:** Low
- **Confidence:** High
- **Location:** `tools/eslint-config/rules/design-tokens-only.js:24-42,88-93`; `tools/eslint-config/css-tokens.js:18,23-24,37,43,146-151`
- **Issue:**
  - **TSX rule.**
    - Bare numbers are flagged only for width, height and padding properties. React renders other numbers as px, yet these all pass: `style={{ margin: 8, gap: 12, fontSize: 13, borderRadius: 4, top: 10, inset: 2, zIndex: 1000 }}`.
    - Values in a separately declared object (`style={s}`) are not checked.
  - **CSS scanner.**
    - Only `px`, `rem`, `ms` and `s` count as lengths, so `pt`, `pc`, `cm`, `mm`, `in` and `Q` pass, e.g. `padding: 12pt`.
    - `color(srgb 1 0 0)` is not caught.
    - Most CSS colour names pass, e.g. `tomato`, `whitesmoke`, `rebeccapurple`. The word-boundary guard also stops "white" from matching inside "whitesmoke".
  - **Escape hatches.**
    - `orca-allow-literal` matches anywhere on a line, including a selector name, and suppresses that line and the next.
    - `// eslint-disable-next-line orca/design-tokens-only` needs no justification; there is no `eslint-comments/require-description`.
- **Scenario / evidence:** `AGENTS.md` says "`pnpm run lint` enforces this now … in inline `style={{ … }}` objects", but `<div style={{ borderRadius: 4, margin: 8 }}>` and `.x { padding: 12pt; color: tomato }` both lint clean.
- **Recommendation:**
  - TSX: flag non-zero numbers on every CSS property React suffixes with px (React's `isUnitlessNumber` list, inverted), and handle `zIndex`.
  - CSS: add `pt|pc|cm|mm|in|q` and `color(`; compare against the full CSS named-colour list.
  - Recognise the allow marker only inside a comment.
  - Add `@eslint-community/eslint-comments/require-description`.
  - Add fixtures for each case to `packages/design/test/token-lint.test.ts`.

## Strengths

- **No privileged trigger misuse.** There is no `pull_request_target` anywhere. The one `workflow_run` consumer (`ci-shadow.yml`) is careful:
  - It checks out the default-branch SHA with `persist-credentials: false`, under `contents: read` / `actions: read`.
  - It authenticates the source run, PR, merge parents and artifact digest through the API.
  - It reads exactly one bounded `evidence.json` without extracting the archive (`read-artifact.py`).
  - It refuses evidence when producer files differ from the trusted checkout.
- **Untrusted expressions stay out of shell.** Event fields (milestone title, PR numbers, SHAs) are passed through `env:`; the only `${{ }}` spliced into a script is the version in `desktop.yml` (C8-10). Inputs are validated (`changelog.yml` PR number, the feed host, root and version regexes).
- **PR CI stays on hosted runners.** Fork-reachable CI (`ci.yml`) runs on GitHub-hosted `ubuntu-24.04` with `contents: read` and `persist-credentials: false`, and the docs-only fast path fails safe to the full checks.
- **Dependency installs are locked down.** `pnpm install --frozen-lockfile` is used everywhere. Lifecycle scripts are denied by default, with an explicit `allowBuilds` allowlist (esbuild and electron only; IBM Plex telemetry and electron-winstaller denied). The lockfile has only registry resolutions, and pnpm itself is integrity-pinned.
- **Release assembly checks its inputs.** It verifies `sha512` against the Windows update metadata and blockmap presence, refuses name collisions when flattening, uploads to a draft before publishing, and re-checks the tag before tagging. Native header downloads are size-, time- and checksum-bounded.
- **Deploy tooling is defensive.** `credential-policy.js` uses `O_NOFOLLOW` reads with inode, owner and mode checks, exact permission sets and `timingSafeEqual`. `orca-release.py` uses flock admission barriers, atomic symlink swaps, store-epoch gating, no-redirect RPC and HTTPS for remote tokens. The systemd templates use `env -i`, `UMask=0077`, `NoNewPrivileges` and `PrivateTmp`, and the renderer has no placeholder-injection surface.
