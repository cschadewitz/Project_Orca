# Architecture and maintainability assessment

This is an evidence-based design assessment, not a bug verdict or runtime certification. Facts come from the frozen [baseline](../baseline/index.md) and its explicit [corrections](../addenda/corrections.md). Judgments and priorities below are **inferred assessments**. Each proposed change is specified separately in [R01–R18](recommendations.md), including alternatives and acceptance criteria.

## Overall judgment

ORCA has recognizable ownership boundaries and useful test seams. Its largest maintenance risks arise where **different kinds of ownership meet**: a plan operation across document/journal writes, a process-local feed over a multi-process file store, a workspace shared by independently leased runs, and a Request projection above raw run controls. Extending these boundaries without naming their guarantees will cost more than adding another executor or screen. [System](../architecture/system.md), [lifecycles](../baseline/lifecycles.md), [uncertainties U01–U06](../baseline/uncertainties.md).

The repository does not need a speculative distributed rewrite. It needs explicit operation ownership, convergence and provenance, followed by narrow refactoring around those decisions. File storage, ports/adapters and the current desktop boundary can remain viable within declared scale and deployment limits. No throughput ceiling or production failure rate was measured.

## State, lifecycle and concurrency

Run event state, mutable Request/WorkItem projections and mutable plan collections are not one uniformly event-sourced aggregate. Their sources of truth and repair triggers differ. The engine's single-token-per-run interpreter can still drive multiple child runs, provider sessions and workspace effects concurrently. The source evidence for that cross-package flow is in [lifecycles](../baseline/lifecycles.md) and [data contracts](../baseline/data-contracts.md).

**Inferred maintenance cost:** operators and developers must currently combine several mechanisms to answer “who may write this now?” Local PlanService queues do not become shared locks because document storage is multi-process aware; a work-item claim does not own a cwd; a run sequence does not become a global reconnect cursor. The proposed ownership table and R04–R06 address those specific distinctions. No universal lock abstraction is proposed.

Recovery needs a defined unit at each level. Run replay/lease recovery is substantially explicit; plan operations cross separate persistence writes; Request settlement is above raw run controls; ACP session reuse ends when the interpreter closes its session pool. “Resume” therefore must not imply restoration of a provider conversation. [Sessions](../architecture/agents-session.md), [interpreter](../architecture/engine-interpreter.md), [program](../architecture/engine-program.md). R08/R09 preserve these distinctions while making provenance and terminal projection easier to reason about.

## Contracts, validation and extensibility

Zod schemas own most external data shapes. Workflow validation checks graph references and built-in fields; daemon dispatch validates parameters; client parsers validate results; adapters validate external responses. These are meaningful boundaries, though in-process TypeScript values are not necessarily reparsed. [Authoring](../architecture/core-authoring.md), [wire](../architecture/protocol.md), [JEV](../architecture/integration-jev.md).

The principal type/schema maintenance risk is **parallel contract representation**, not the absence of schemas. A method can require protocol declarations, daemon handlers, capability lists, bridge types, preload/main routing and hook changes. R10 reduces mechanical synchronization while retaining named privileged boundaries. Plugin-specific schemas and operational prompt claims need separate owners; permissive `CustomNodeSchema` does not provide plugin preflight. R14 addresses that concrete seam.

The expression interpreter evaluates its own AST, whereas a configured plugin executes trusted JavaScript. ACP permission decisions govern cooperative agent tool requests; host file/exec ports and plugins possess direct process privileges. These are different extension/trust mechanisms. None is an implicit untrusted-code sandbox. [Inputs/extensions](../baseline/inputs-extensions.md), [agents](../architecture/agents.md), [bootstrap](../architecture/cli-bootstrap.md).

## Error handling, diagnostics and testability

[OrcaError](../../packages/core/src/errors.ts#L54) provides stable codes and structured details; [dispatch](../../packages/daemon/src/server.ts#L66) preserves protocol faults while serializing other errors. This is a useful shared error vocabulary. Recovery-sensitive failures still need domain decisions: policy fallback, provider timeouts, lost leases, stale config and failed update admission should not be flattened into one retry rule. Their current ownership is described in [lifecycles](../baseline/lifecycles.md) and [inputs](../baseline/inputs-extensions.md).

[Logger](../../packages/core/src/util/logger.ts#L4) supports structured fields and child contexts, while durable run events and plan journals carry distinct IDs and sequence domains. There is no traced general metrics/tracing exporter. R17 recommends joinable diagnostic context and targeted counters, not an unsolicited telemetry service. Retention/redaction must apply to diagnostic exports as well as artifacts.

Test source spans pure algorithms, scripted ACP subprocesses, real filesystem stores, IPC/renderer fixtures and browser smoke assertions. Architectural import/token checks and UI sweep tests encode useful intended invariants. The [test catalog](../baseline/test-catalog.md) maps declarations; [engineering](../baseline/engineering.md) records command/CI organization. No test result, branch coverage percentage, platform installation or browser layout was verified. R16 focuses on independent-process and interruption boundaries rather than demanding more tests everywhere.

## Repository, build and documentation governance

Workspace package direction is understandable; TypeScript references, pnpm manifests/lockfile and release scripts expose the build graph. Runtime, build-only and development dependencies are distinguished in the [dependency inventory](../baseline/dependencies.md). The app's build-time daemon bundle does not contradict its renderer runtime import rule. Separate lint TypeScript dependencies may be a tool-compatibility choice; this review does not infer an upgrade defect from differing versions.

CI, packaging, release preparation, publication and managed deployment are distinct stages with different environments and secrets. Their source/configuration is inspectable, but deployment credentials, branch protection and actual service state are external. Unsigned platform configuration and conditional Windows in-app updates require a distribution policy, not an assumption that packaging equals shipping assurance. R15 is conditional on the intended distribution boundary.

The documentation contains valuable detailed implementation notes but several competing current-status summaries. Historical issue-number narratives and later correction paragraphs accumulate without retiring earlier present-tense claims. The [17 differences](../comparison/differences.md) demonstrate that maintenance cost concretely. R01–R03 introduce a small current-state ledger and clearer supersession; preserving ADR rationale and release history is preferable to deleting them.

Repository ownership here means code responsibility, not inferred team staffing. No human owner, on-call arrangement or actual PR-review practice can be established from source alone. The proposed task owners are subsystem roles, not assignments to people.

## Decisions deliberately not made

This review does not recommend a wholesale rewrite, mandatory database migration, provider expansion, workflow-editor implementation or a universal reactive-state framework. It does not invent cost, ETA, run-completion percentages, global capacity scheduling or multi-tenant support. These are either explicitly absent in the baseline or future product choices. Prioritize the guarantees and maintenance seams exposed by the existing implementation before growing those features.
