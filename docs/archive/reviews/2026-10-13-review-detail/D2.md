## Findings

### D2-01 — Earlier finished `parallel` / `plan-dispatch` siblings are visible as artifact inputs, but WORKFLOWS.md says parallel branches "never see each other"
- **Doc:** docs/WORKFLOWS.md:95-100. Only loop iterations see earlier siblings; "`parallel` branches run concurrently and so never see each other."
- **Code:**
  - `packages/engine/src/run-context.ts:199-258`: `visibleArtifacts()` adds every *earlier sibling*, meaning any child of the same container step that was spawned earlier and has `completedAt <= run.createdAt`, plus its descendants. Nothing restricts this to `loop`.
  - Fan-outs start children lazily:
    - `packages/engine/src/executors/containers.ts:216-268` (`runBranches` launches a branch only when a slot frees or its `dependsOn` is met). The parallel default is `concurrency: 4` (`core/src/model/workflow.ts:306`).
    - `custom:plan-dispatch` uses the same `FanOut`, default plan concurrency 2 (`core/src/model/plan.ts:313`).
  - `orchestrator.ts:1715-1748` emits `child.finished` before the next branch is created. A later branch therefore satisfies the "earlier sibling" test.
  - `orchestrator.ts:1785-1806`: `resolveInputs` resolves `{ name: … }` and `{ kind: … }` refs against that merged map.
  - Concrete effect: under `custom:plan-dispatch`, item B's first `build` declares `{ name: review, required: false }` and `{ name: testReport, required: false }` (`workflows/ai-sdlc.yaml:69-72`). B has no review or test report of its own yet, so it receives item A's if A finished before B was spawned. The code comment at run-context.ts:205-207 makes the same "parallel branches do not precede each other" assumption.
- **Variance type:** contradicts-design
- **Severity:** High (one work item's review/test report can be fed to another item's builder, which the authoring doc says cannot happen)
- **Confidence:** Medium (traced through code, not executed)
- **Suggested resolution:** fix code. Limit earlier-sibling visibility to `loop` steps, or scope it by branch or work item. If cross-branch visibility is intended, at least document it in WORKFLOWS.md.

### D2-04 — Reloadability table implies roles/program/workflows/templates apply live, but any configured plugin makes every `config.apply` return `restart-required`
