## Findings

### C7-01 — Permission-sidecar draft is a whole-file copy, saved against the *latest* revision, so it silently reverts other writers' grants
- **Category:** data-integrity / security
- **Severity:** Critical
- **Confidence:** High
- **Location:** `config/use-config.ts:153-162` (every `config.changed` re-reads), `config/use-config.ts:191-210` (`expectedRevision: view.revision`); `config/policy-editor.tsx:117-135` (`write()` → `feed.setText(DOCUMENT, serializeSidecar(withRules(held, …)))`)
- **Issue:** The policy panel turns every grant edit into `{kind:"raw", text}`. That text is the entire sidecar, serialised from the version that was on screen when the edit was made. `useConfigFeed` re-reads both documents on every foreign `config.changed` but keeps the draft. `write()` then sends `expectedRevision: view.revision`, where `view` is the freshly re-read document, not the revision the draft was built on. The `CONFIG_STALE` guard can therefore never fire once the push has been processed. Saving writes the old copy over the new file.
  - The header comment in `use-config.ts` says the opposite ("`expectedRevision` is the revision this draft was made against").
  - AGENTS.md says a draft "is the edits and never a copy of the file".
- **Scenario / evidence:**
  1. Agents → Permissions for agent A. The user removes grant 2, so the draft holds the full r1 text minus that grant.
  2. Meanwhile one of the following happens:
     - (a) A run in Attention is answered "allow always" for agent B, and the daemon writes r2.
     - (b) In a second window, someone removes a dangerous grant and saves r2.
  3. The push re-reads r2 into `state.data`. The draft still holds r1-based text.
  4. The user presses Save. `config.set({document:"permissions", expectedRevision:"r2", text:<r1 minus grant 2>})` succeeds.
  5. Result: B's new grant is deleted, or the revoked dangerous grant is re-instated. Neither is mentioned anywhere. The only signal is that the bar's count rises from "1 change" to "2 changes", because `ruleChanges(onDisk_r2, held_r1)` counts the reverted row.
  6. No test covers draft + push + Save (`policy-editor.test.tsx:480` only checks that a push re-reads when there is no draft).
- **Recommendation:**
  - Record `baseRevision` on the `DocumentDraft` when it is first created and send that as `expectedRevision`, so the daemon answers `CONFIG_STALE`.
  - Better still for the sidecar, keep the draft as per-agent rule operations and rebase them onto the re-read document.
  - Whenever `state.data.permissions.revision !== draft.baseRevision`, show the conflict state with Reload or Rebase, never a silent Save.
  - Add a test: draft → `config.changed` → Save must send the draft's base revision.

### C7-02 — Structured Config form records one edit per keystroke; past 1000 edits the draft can never be validated or saved
- **Category:** correctness / data-integrity
- **Severity:** High
- **Confidence:** High
- **Location:** `config/structured-form/structured-form.tsx:369-373` (`change(text)` on every `onChange`); `config/structured-form/editor-session.ts:80` (`this.edits = [...this.edits, ...edits]`, no coalescing); `config/configuration-adapter.ts:190-195` (`ConfigSetParamsSchema.parse({… edits: candidate.edits …})`); `packages/protocol/src/config.ts:358` (`edits: z.array(...).max(1000)`)
- **Issue:** Every character typed or deleted in a text or number field appends a new `{kind:"set"}` intent, and the full list is sent on every Validate. Once the list passes 1000 entries, `ConfigSetParamsSchema.parse` throws inside `lowering.lower`. `refused(error,false)` does not classify it, and `session.validate` ends in `block("Validation unavailable. Draft retained.")` every time. Save needs a review, and switching to Raw needs "Discard draft and switch". The draft is stuck and discarding it is the only way out.
- **Scenario / evidence:** Typing a 600-character agent command, then fixing a few typos and editing a couple of other fields, adds up to more than 1000 intents. Every Validate then returns "Validation unavailable"; no field error explains why. The tests use `fireEvent.change` with whole values (for example `configuration-studio-route.test.tsx:27`), so they never accumulate per-keystroke intents.
- **Recommendation:**
  - In `StructuredEditorSession.edit`, coalesce a `set` whose path equals the previous intent's path, and drop a `set` that restores the original base value.
  - Alternatively, commit text fields on blur or Enter, as the workflow inspector already does.
  - Guard the 1000 limit explicitly with a readable message.
  - Add a test that types character by character.

### C7-03 — Workflow inspector shows the previous node's uncommitted text on the newly selected node and can write it there
- **Category:** data-integrity / correctness (React state reuse)
- **Severity:** High
- **Confidence:** High
- **Location:** `workflow/editor/editor-inspector.tsx:178-186` (`<NodeInspector …/>` and `<EdgeInspector …/>` have no `key`); `:310` (`FieldEditor key={spec.key}`); `:818` (`CommitInput`: `useEffect(() => setText(value), [value])`)
- **Issue:** Moving the selection between two nodes of the same type reuses the same `FieldEditor` and `CommitInput` instances, because the keys are equal. Local `text` is only reset when the `value` string changes. When the old and new node have the same committed value for a field, the field keeps the text typed for the old node. Edges behave the same way in the "Only when" and "Label" fields.
- **Scenario / evidence:**
  1. Add two Agent steps from the palette. Both get `prompt: "Describe what this step should do."` (`draft-model.ts:223`).
  2. Select `agent-1` and type a new prompt.
  3. Click `agent-2` on the canvas. Blur correctly commits `agent-1`'s prompt, but `agent-2`'s Prompt box now shows `agent-1`'s text even though its value prop is still the placeholder, which did not change.
  4. Tab through, or click into the box and out again. `commit()` sees `text !== value` and sends `updateNode agent-2 set prompt=<agent-1's text>`.
  5. The same happens with two edges that have no `when`.
  6. The data is silently wrong and only Undo recovers it. There is no test that switches selection after typing.
- **Recommendation:** Key the inspector bodies by identity: `<NodeInspector key={`${path key}:${node.id}`}>` and `<EdgeInspector key={edge.index + from + to}>`. Alternatively key `CommitInput` by its YAML `path`.

### C7-04 — Guided launch wedges permanently after a launch is refused before main retains it
- **Category:** reliability
- **Severity:** High
- **Confidence:** Medium
- **Location:** `guided-launch/controller.ts:311-326` (`unresolvedReview: review` set before `launch()`, cleared only on success); `:343-371` (recover: `if (!intent) throw new LaunchPortFailure("unavailable")`); `:579-584` (`newWork` refuses while `unresolvedReview` is set); `src/main/guided-launch.ts:53-56` (`verifyReview` runs before `retainGuided`)
- **Issue:** Main re-verifies the review and throws if it no longer matches: checkout evidence, workflow revision, generation, provenance or validation have moved. That happens before anything is retained. The renderer maps the throw to `LaunchPortFailure("unavailable")` and keeps `unresolvedReview`.
  - **Recover:** `resolveIntent` correctly finds no intent, which the controller treats as a failure. `unresolvedReview` is still set.
  - **Start explicit new work:** blocked ("…unresolved. Recover or inspect…").
  - **Edit:** refused.
  - **Restore:** refused.
  - **Close:** keeps the session.
  - The only way out is restarting the app or a daemon-target remount.
- **Scenario / evidence:** Preview a launch, commit to the prepared checkout (so `evidenceId` changes and nothing is pushed), then press Launch. Main's `verifyReview` → `refuse()`. The session can no longer launch anything. The controller tests use the `retain`/`submit` ports; no test covers the production `launch` + `resolveIntent` path.
- **Recommendation:**
  - Treat `resolveIntent` returning `undefined`, under the same scope with current authority, as "confirmed nothing retained": clear `unresolvedReview` and return to editing with the draft intact.
  - Or have main return a distinct "refused before retention" code so the controller never sets `unresolvedReview` for that case.

### C7-05 — Config form checks access with synchronous IPC and full-document re-projection, many times per field per render, on every keystroke
- **Category:** performance
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `config/configuration-studio.ts:163-193, 315-327` (`value` getter and `reason()` → `currentEditorTarget(this.bridge)` and `bridge.connection.read()`); preload `src/preload/index.cts:177, 314` (both reads are `ipcRenderer.sendSync`); `config/structured-form/structured-form.tsx:304-311, 368, 437` (`form.access` ×2–3 per scalar, plus `allowed()` per enum choice, plus Actions); `configuration-studio-surface.tsx:197-199` (`referenceChoices` → `studio.value` per scalar)
- **Issue:** Each `studio.editAccess()` costs:
  - two blocking renderer→main `sendSync` round trips;
  - `session.snapshot()`, which `structuredClone`s every recorded edit;
  - a deep `jsonValue` copy of the whole parsed config with all N edits replayed;
  - a second projection.

  A scalar field runs this 2–4 times per render, enums once per choice, and `referenceChoices` adds another full projection per scalar. Every keystroke emits, so the whole form re-renders.
- **Scenario / evidence:**
  - A config with about 100 leaf fields means several hundred synchronous IPCs and several hundred projections per keystroke.
  - Because of C7-02 the edit count grows with typing, so the cost per keystroke grows linearly and the total grows quadratically.
  - `sendSync` also stalls the main process's event loop each time.
- **Recommendation:**
  - Compute the target and connection snapshot once per render, from `useConnection` or the existing subscriptions, and pass them in.
  - Cache `studio.value` per session `sequence` and derive `editAccess` from the cached projection. Most per-field checks need only the cached `reason`, not a re-projection.
  - Coalesce edits (C7-02).

### C7-06 — Workflow draft queue sends index-addressed operations against a newer revision than they were composed for; a held or doubled Delete removes the wrong edges and then cascades into nodes
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:** `workflow/editor/use-workflow-draft.ts:100-113, 115-124, 142-160` (each queued call reads `latest.current.revision` when it runs; a `CONFIG_STALE` reloads and the queue continues); `workflow/editor/workflow-editor.tsx:180-205`; `workflow/editor/editor-canvas.tsx:209-217` (Delete and Backspace with no repeat or busy guard); `packages/protocol/src/workflow-drafts.ts:67` ("Edges are addressed by their index … as of the revision the batch names")
- **Issue:** `removeEdge`, `updateEdge` and `insertNode` take the edge index as rendered at revision N. If another op is queued ahead, or the queue reloads after `CONFIG_STALE`, they are sent with `expectedRevision` set to the newer revision. The daemon's revision check then passes and the op hits whatever edge now has that index. After an edge delete succeeds, selection moves to the edge's source node (`landAfterDelete(from)`), so further Delete presses remove nodes.
- **Scenario / evidence:**
  1. Select edge #2 and hold Delete, or press it twice quickly.
  2. The second `removeEdge index:2` is queued and runs after the first, deleting the edge that slid into slot 2.
  3. Auto-repeat after that deletes the source node, then its neighbour, and so on, one undo step each.
  4. Separately, if op 1 is refused `CONFIG_STALE` because another window edited the draft, the queued op 2 still runs against the reloaded revision.
- **Recommendation:**
  - Capture `draft.revision` when the gesture is composed and send that for index-addressed ops (or for all ops). Let the daemon refuse with `CONFIG_STALE` instead of chaining.
  - Flush the queue after a refusal.
  - Ignore `KeyboardEvent.repeat` for destructive shortcuts, and do not accept a Delete while a delete for the same selection is in flight.

### C7-07 — Inspector shows a bare-string agent selector (an agent id) as "role" and rewrites it to `{role: …}` on edit
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High
- **Location:** `workflow/editor/editor-inspector.tsx:729` (`kind = record && typeof record.id === "string" ? "id" : "role"`), `:751` (`onCommit({ [kind]: text })`); semantics in `packages/agents/src/hosts/registry.ts:329-331` and `packages/daemon/src/workflow-model.ts:46` (a bare string is an agent id)
- **Issue:** `agent: codex` means agent id `codex`. The inspector labels it "role", and any text edit commits `{ role: "<text>" }`. Editing `codex` to `claude` turns an id selector into a role lookup. That either fails validation ("no agent fills role") or, worse, resolves to whichever agent fills a role that happens to have the same name.
- **Scenario / evidence:** A workflow written by hand with `agent: codex`: change one character and the node now resolves by role. `workflow-editor-inspector.test.tsx:248-262` only checks the value; it never checks that the kind shown for a bare string is "agent id".
- **Recommendation:** Treat `typeof value === "string"` as `kind = "id"`. Preserve the bare-string form on a text edit (commit a string), and only switch shape when the user explicitly chooses "Agent by".

### C7-08 — Sidecar edits typed while a Save is in flight are silently discarded; Discard during a Save does not stop the write
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** `config/use-config.ts:257-264` (`setDrafts(... [document]: undefined)` unconditionally on success), `:181-184` (discard resets `busy`); `config/policy-editor.tsx:191` (`editable = canSet && held !== undefined`, with no `save.busy`); `config/draft-bar.tsx:131-133` (Discard is not disabled while busy)
- **Issue:**
  - Grant inputs and menus stay live during `config.set`. A keystroke during the round trip updates the draft. When the write succeeds, the hook clears the draft wholesale, so the newer edit vanishes and "Saved." is announced.
  - Discard pressed mid-save hides the bar and resets `busy`, but the original write still lands.
- **Scenario / evidence:** Edit a grant's Path prefix, press Save, keep typing in the same field: the trailing characters are gone after the save. A daemon under load makes the window wider.
- **Recommendation:** Snapshot the draft (or its sequence) that was sent. On success, clear the draft only if it is unchanged; otherwise keep the newer draft, rebased on the new revision. Disable the editors and Discard while `busy`.

### C7-09 — Config studio: an edit made while Save is in flight becomes an unreconcilable "retained" draft
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** `config/configuration-studio.ts:226-238` (save port: `if (sequence changed) this.stale = true` and no `acceptSaved`); `config/structured-form/editor-session.ts:253-256` ("Reviewed changes saved. Newer edits are retained; reconcile them with the saved revision."); `config/configuration-studio.ts:506-541` + `config/reconciliation.ts:12-23`
- **Issue:**
  - Form inputs stay editable while the session is `saving`: `editAccess` → `reason("validate")` ignores busy.
  - If the user edits during the save, the session freezes with the full edit list, the saved prefix included. `this.data` stays at the old base.
  - "Read current configuration" then runs `reconcileConfigurationEdits(oldBase, savedRevision, allEdits)`. The first saved edit's path differs between the two by definition, so reconciliation always reports a conflict and the studio stays stale.
  - The message promises a reconcile, but the only working action is "Discard draft and load current revision", which throws away the newer edits.
- **Scenario / evidence:** Validate → Save → type one more character in any field before the acknowledgement arrives → the screen says "Newer edits are retained; reconcile them"; Read current → still stale; the newer edit has to be discarded.
- **Recommendation:** When the save is acknowledged with newer edits, rebase in place: set the session revision to the saved one, drop the saved prefix (`edits.slice(review.editCount)`) and update `this.data`. Or simply make inputs read-only while busy.

### C7-10 — Plan journal forward reads never follow `hasMore`; bursts or an early push leave missing or unloadable entries
- **Category:** correctness
- **Severity:** Medium
- **Confidence:** High (bursts) / Medium (initial-load race)
- **Location:** `plan/use-plan.ts:301-319` (single page of `JOURNAL_PAGE=50` after the held tail); `:261-295` (initial load); `:321-337` (`loadEarlier` uses `earliestSeq`)
- **Issue and scenarios:**
  - **Bursts:** A `journal` push triggers one read of 50 entries after the newest held entry. A burst of more than 50 entries (a re-plan, bulk decisions) leaves the newest entries unread until further pushes arrive. Each push re-runs the effect, cancelling the previous read (`live=false`), so 100 rapid pushes still fetch only one page.
  - **Initial-load race:** If a push arrives while the initial two-call load is in flight, `heldRef` is empty, so the forward read fetches the oldest 50. When the newest page lands first, folding the oldest 50 into it leaves a gap. `loadEarlier` then asks for entries before seq 1, gets nothing, and sets `hasEarlier=false`, so the gap can never be filled.
- **Recommendation:** Loop the forward read while `result.hasMore`. Do not run the forward read until the initial load has resolved, or have the initial load supersede it. Make `loadEarlier` page backwards from the lowest seq of the newest contiguous run, not from the global minimum.

### C7-11 — Guided launch resets the review on every `config.changed` and `workflows.changed`, including sidecar writes, and fences away in-flight acknowledgements
- **Category:** reliability / correctness
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `guided-launch/launch-context.tsx:51-62, 82, 115-120` (each push → `refresh()` → `contextChanged()` twice; clears `retained` and `selection`); `guided-launch/controller.ts:107-119` (`fence += 1`, review dropped, phase `blocked`), `:433` (`receive` drops the result when the fence moved)
- **Issue:** Any `config.changed` resets the launch: a permission-sidecar write from a running agent's "allow always", an unrelated config save, or a generation event.
  - An in-progress Preview result is discarded.
  - A displayed review is cleared, along with the permission-acknowledgement checkbox.
  - The user's choice of retained launch is wiped.
  - If it lands during Launch, the `launch()` call has already set `intent`, but `receive` returns early. The accepted receipt is never shown, and the UI reads "Configuration or connection changed. Review the draft again." over a launch that was actually admitted. Only "Recover original launch" reveals it.
- **Recommendation:**
  - Only invalidate when the snapshot actually differs in fields the review depends on: generation, workflow revision, target or roots. A permissions-document change does not qualify.
  - Never fence a result whose intent was already recorded; route it through `receive` with the original fence.
  - Preserve `selection` across refreshes when the handle is still present.

### C7-12 — Workflow viewer: nested graphs share node-id space with the outer graph (DOM ids, selection, overlay)
- **Category:** correctness / accessibility
- **Severity:** Medium
- **Confidence:** High
- **Location:** `workflow/workflow-canvas.tsx:293-319` (nested `Graph` with the same `selected`/`overlay`), `:343-414`, `:417` (`nodeDomId = orca-wfnode-${nodeId}`); `workflow/layout.ts` `findNode` (first match); `workflow/editor/draft-model.ts:208-214` (every editor-created container contains `start` and `done`)
- **Issue:** The daemon sends nested node ids unqualified (`daemon/src/workflow-model.ts:181`). Expanding a container whose body has `start` (always the case for editor-created loops and parallels) renders a second `id="orca-wfnode-start"`, so the DOM ids are duplicated.
  - Selecting the nested `start` highlights both boxes.
  - The inspector shows the outer `start` (`findNode` takes the first match).
  - The outer listbox's `aria-activedescendant` may point at the wrong element.
  - `runStateOf` paints the outer node's visit status onto the nested node.
- **Scenario / evidence:** Create a loop in the editor, publish, open the viewer, expand the loop, click its `start`. The test fixtures use distinct ids (`ui-start`, `docs-start`), so the collision is never exercised.
- **Recommendation:** Qualify selection and DOM ids by graph (`${nested.id}::${node.id}`). Carry a graph id through `onSelect` and `findNode`. Only apply the overlay to the graph the traversal belongs to.

### C7-13 — A `workflows.changed` push for the workflow being edited unmounts the editor
- **Category:** reliability
- **Severity:** Medium
- **Confidence:** High
- **Location:** `workflow/use-workflow.ts:66-91` (definition push → `setState({phase:"loading"})`); `workflow/workflow-surface.tsx:146, 166-180` (the loading return comes before the `editing` branch)
- **Issue:** When the definition is re-read, the surface returns the loading `StateView`, which unmounts `WorkflowEditor`. When the read finishes it remounts and reopens the draft. The following are lost:
  - uncommitted `CommitInput` text (commit happens on blur, which does not fire on unmount);
  - the open Review panel;
  - the nested-graph `path`;
  - the selection;
  - the canvas view.
- **Scenario / evidence:** While a prompt is half-typed, another window publishes the workflow, or a Config Apply lists it among changed workflows (`daemon/src/subscriptions.ts:229-233`). The text is lost.
- **Recommendation:** Keep the last `ready` state while re-reading (a stale-while-revalidate phase), and render the editor whenever `editing` is set, independently of the viewer's read.

### C7-14 — Decision rationale is cleared when the daemon refuses a decide
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** `plan/decision-mode.tsx:219-232` (`setPending(undefined); setRationale("")` regardless of `result.ok`), `:324` (Decide is disabled only on `busy`)
- **Issue:** A refused `decisions.decide` (connection lost after choosing an option, a concurrent decide, a validation error) clears the typed rationale and the chosen option, and the refusal is only announced. This contradicts the rule that a refused write keeps the draft. The Decide button also ignores writability, so a decide sent after the connection drops is refused and the text is wiped.
- **Recommendation:** Clear `pending` and `rationale` only when `result.ok`. Disable Decide with `disabledReason` while not writable.

### C7-15 — Run overlay re-reads the whole run, traversal included, on every `run.changed` and `step.changed`, without coalescing
- **Category:** performance
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `workflow/use-workflow.ts:103-136`
- **Issue:** Every push for the overlaid run bumps `revision`, which issues a `runs.get` carrying the full traversal. A `parallel`/`forEach` run emitting dozens of step changes per second produces a matching stream of reads. Earlier responses are dropped through `live`, but the IPC and daemon work still happen.
- **Recommendation:** Coalesce: throttle the bump (for example `requestAnimationFrame` or 250 ms trailing), or skip a new read while one is in flight and re-read once afterwards.

### C7-16 — `setWire` updater has a side effect; StrictMode double-invocation adds duplicate edges in dev
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `workflow/editor/editor-canvas.tsx:349-356`; `main.tsx:47` (`<StrictMode>`)
- **Issue:** `onConnect` is called inside a state updater. React calls updaters twice under StrictMode in development, so dragging a connection sends two `addEdge` ops. This affects the demo/dev app (`orca-demo-dev`), not production.

### C7-17 — Structured form number input cannot be cleared

- **Confidence:** High

- **Issue:** The controlled `<input type="number" value={readable}>` only commits when the text is non-empty and finite. Backspacing to empty does not change state, so React restores the old value. The user cannot clear the field and retype; they have to select and overwrite.

### C7-18 — Union variant review card disappears on any re-render
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `config/structured-form/structured-form.tsx:486` (`pending.value === form.value`); `config/configuration-studio.ts:163-165` (`value` is a fresh projection on every render)
- **Issue:** The guard compares object identity, but the projected value is a new object on every parent render: connection pushes, studio emits, feed reloads. The "Review variant change" card can vanish while it is being read.
- **Recommendation:** Compare by `pathLabel(form.path)` plus a stable sequence (`studio.state.sequence`), or deep-equal the current value.

### C7-19 — Focus drops to the page body when arming Waive and Reopen confirmations

### C7-21 — Workflow draft change count double-counts nested edits
- **Category:** correctness
- **Severity:** Low
- **Confidence:** High
- **Location:** `workflow/editor/draft-model.ts:101-153`

### C7-22 — Graph layout and model have quadratic hot spots, re-run on every plan push
- **Category:** performance
- **Severity:** Low
- **Confidence:** High
- **Location:** `workflow/layout.ts:198-200` (`nodes.some` per DFS root → O(N²)), `:252`; `plan/graph-model.ts:106-131` (`dependencies.filter` per item and per target → O(I·D)); `plan/plan-surface.tsx:225-231` (recomputed on every `held` change)
- **Issue:** Workflows are tiny, but the plan dependency canvas runs on every `plan.changed`. With about 1000 items and 3000 dependencies that is several million operations per push, plus O(N²) in `backEdges`.
- **Recommendation:** Use `Set` and `Map` lookups (`ids.has(root)`) and pre-index dependencies by `from` and by target.

### C7-23 — Workflows list re-reads list and per-workflow draft facts once per `workflows.changed`

## Strengths

- No unsafe rendering sinks anywhere in scope: no `dangerouslySetInnerHTML`, `innerHTML`, `eval` or URL `href` from data. Workflow, template, YAML and diff content is always rendered as React text.
- The Config studio saves exactly the reviewed candidate bytes (`ConfigurationAdapter.save` checks the reviewed text, revision and acknowledgement), and keeps Save separate from a guarded Apply. Its target, epoch and sequence fencing is thorough.
- Guided launch freezes the reviewed command and re-verifies it in main before retention. Sensitive inputs stay withheld monotonically, and an accepted receipt is checked against the launch mode.
- `layout.ts` is iterative, so deep or cyclic workflows cannot overflow the stack. Edge keys include the index, so parallel edges are distinct.
- The Agents claims list is a model implementation of release confirmed on the row, with careful focus handling, `focusAfterLeaving`, and Escape through the layer stack.
- The template adapter verifies the target, revisions and the exact saved text on every acknowledgement, and allows only one source per Save.
