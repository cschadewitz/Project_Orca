# V3 — Adversarial verification of C7-01..04 and D7-01..05

Repo the repository at HEAD `0c75d01`. Static, read-only. Paths are under `packages/app/renderer/src/` unless they say otherwise.

### C7-01
- **Verdict:** CONFIRMED
- **Adjusted severity:** High, down from Critical. The trigger that is easy to hit is a daemon "allow always" grant being dropped. That fails safe: the agent simply asks again. The variant that weakens security, where a grant someone revoked comes back, needs a second ORCA client to write the sidecar at the same time. It is still High because it silently defeats a compare-and-swap check the daemon was built for this exact race.
- **Evidence:**
  - **The daemon's check is correct.** `packages/daemon/src/config-model.ts:28-38,374-395,543-551` compares `expectedRevision` against a content hash, inside the sidecar's `link()` lock (`replacePermissionPolicyFile`).
  - **The renderer sends the wrong revision.** `config/use-config.ts:194,207` sends `expectedRevision: view.revision`, where `view` is the current `state.data`, not the revision the draft was built from.
  - **A push moves that revision without touching the draft.** Every foreign `config.changed` calls `reload()` (`use-config.ts:156-161`), and the re-read replaces `state.data` (`:133-137`). `drafts` is not touched.
  - **The daemon does push for "always" grants.** `packages/daemon/src/control.ts:340,391` call `config.announce("permissions")` after a grant is recorded.
  - **The draft is a whole-file copy.** `config/policy-editor.tsx:118,132` builds it from `held`, which is the draft's own parse once a draft exists, so it never picks up the newer file.
  - **Result.** Draft at r1 → push → re-read to r2 → Save sends r1-based text with `expectedRevision=r2` → the compare-and-swap passes and the newer grant is overwritten. The only visible sign is the change count going up (`policy-model.ts:262-277` counts across all agents).
  - **This needs only one user and one window.** The draft is held above navigation (`config-context.tsx`). A person can edit grants in Agents, answer "allow always" in Attention, return, and press Save.
  - **No test covers it.** `test/policy-editor.test.tsx:480` covers a push without a draft. `:455-478` covers a scripted `CONFIG_STALE` with no push.
  - **Refutation attempts failed.** There is no base-revision field on `DocumentDraft` (`use-config.ts:56`), no conflict detection on push, and no guard in `DraftBar` wiring (`policy-editor.tsx:372-387`).
- **Fix note:** Sending the base revision is not enough. The designed path "`CONFIG_STALE` → Reload → Save" (`use-config.ts:21-25`: "the same draft can then be sent against it") would still write the stale whole-file copy against the new revision. Keep the draft as this agent's rule list and compose it at save time with `withRules(onDisk, agentId, rules)`. Flag a conflict only when that agent's own rules moved since the draft's base.

### C7-02
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium, down from High. Nothing on disk is harmed, and the counter resets on every successful Save (`editor-session.ts:261`). The cost is the unsaved draft: it has to be discarded and re-entered, and a paste counts as one edit.
- **Evidence:**
  - **Every keystroke records an edit.** Text and number inputs call `change()` on every `onChange` (`config/structured-form/structured-form.tsx:297-300,363-372`).
  - **Nothing in the path coalesces.** `onEdit` goes to `studio.edit` → `session.edit`, which appends (`structured-form/editor-session.ts:78-88`; `configuration-studio.ts:329-341`). No coalescing or debounce exists anywhere on that path.
  - **Over 1000 entries, the parse throws.** `ConfigSetParamsSchema.parse({… edits })` in `configuration-adapter.ts:190-195` hits `edits.max(1000)` (`packages/protocol/src/config.ts:358`) and throws a ZodError.
  - **The failure is unclassified and repeats.** `refused(error,false)` does not classify a ZodError (`configuration-studio.ts:258-264`). The error is rethrown, and `session.validate` ends in `block("Validation unavailable. Draft retained.")` (`editor-session.ts:203-204`) on every attempt.
  - **There is no way out except discarding.** Save needs a review. Raw needs "Discard draft and switch" (`configuration-studio-surface.tsx:172-178`).
  - **Refutation attempts failed.** I looked for an explicit limit check and for edit squashing on Validate, and found neither.

### C7-03
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium, down from High. The edit lands only in the draft. Publishing goes through Review, which shows the exact diff (`workflow-editor.tsx:386-394`, `ReviewPanel`), and `⌘Z` restores. The wrong text on screen is still a real defect.
- **Evidence:**
  - **Nothing forces a remount between nodes.** `<NodeInspector>` and `<EdgeInspector>` have no key (`workflow/editor/editor-inspector.tsx:177-186`), and `FieldEditor` is keyed only by `spec.key` (`:302-304`). Two nodes of the same type therefore reuse the same `CommitInput` instances.
  - **Local text only resets when `value` changes.** `CommitInput` does that in `useEffect(() => setText(value), [value])` (`:817`).
  - **Two default Agent steps share a value.** Both get the same prompt (`draft-model.ts:223`), and any two nodes with the same field unset render `""`.
  - **The sequence.**
    1. The old node's blur commits its own edit through the closure (`:226-231`).
    2. The new node's field keeps the typed text, because `value` did not change.
    3. A later blur on that field sees `text !== value` and commits it to the new node (`:818-826`).
  - **Refutation attempts failed.** No wrapper key on `<EditorInspector>` (`workflow-editor.tsx:438-452`), and no reset on `node.id`.
- **Fix note:** Do not key `NodeInspector` by `node.id`. Renaming with Enter commits `renameNode` and then reselects the new id (`editor-inspector.tsx:262-266`), so remounting the whole inspector would drop focus out of the focused Id input (RULES 10). Key each `FieldEditor` by `${node.id}:${spec.key}`, or key `CommitInput` by its YAML path, and key `EdgeInspector` by `index+from+to`.

### C7-04
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium, down from High. It fails closed: no wrong or duplicate launch is sent and no data is lost. "Permanently" overstates it, because an app restart builds a fresh controller and main's journal holds nothing. Until that restart, guided launch, including the first-run sample button (`launch-route.tsx:55-58`), is unusable. The Recover button the UI points to always fails, and `useUpdateDraft` stays held (`launch-context.tsx:131-139`).
- **Evidence:**
  - **The renderer marks the review unresolved before launching.** `submit()` sets `unresolvedReview` before `launch()` and clears it only on success (`guided-launch/controller.ts:311-318`).
  - **Main can refuse before anything is retained.** Main runs `verifyReview` → `refuse()` before `retainGuided` (`packages/app/src/main/guided-launch.ts:54-58`; `main/guided-launch-adapter.ts:298-361`). Any `connect`/`preflight` throw also lands there.
  - **Every failure keeps the flag.** The error becomes `LaunchPortFailure("unavailable")` (`production-bindings.ts:21-24`), or a plain Error that `receive` routes to "recovering" (`controller.ts:450-457`). Both keep `unresolvedReview`.
  - **Recover cannot find anything to recover.** `resolve` returns `undefined` when nothing matches (`guided-launch-adapter.ts:403-413`). The controller then throws `"unavailable"` (`controller.ts:366`) and still keeps the flag.
  - **Every other way out refuses.** `edit` (`:121`), `preview` (`:179`), `restore` (`:530-533`), `newWork` (`:580-585`), `saveDraft` and `loadDraft` (`:474,496`) all refuse. `contextChanged` and `reviewTarget` never clear the flag (`:107-160`).
  - **The controller outlives navigation and refreshes.** It lives in `owned.current` (`launch-context.tsx:42,79-91`).
  - **Tests miss this case.** The only test of the `launch` port asserts that the flag is retained (`test/guided-launch-restore-safety.test.tsx:106-134`), and no test exercises `resolveIntent` returning `undefined`.

### D7-01
- **Verdict:** CONFIRMED, with a doc tension on the shape of the confirmation.
- **Adjusted severity:** Medium, down from High. Discard does ask once. The real hazard is that a second Enter, a held key or a double-click lands on the same button and discards irreversibly. Missing `✕` is the one point no document disputes.
- **Evidence:**
  - **The control is one toggling button.** At `workflow/editor/workflow-editor.tsx:255-264,331-338` the label changes to "Discard every change" and the tone to `danger`. There is no Keep and no `✕` (`Button` adds no glyph; `ui/button.tsx`), it is not on the layer stack, and it disarms only `onBlur`.
  - **The rules it breaks are binding.** `docs/design/RULES.md:71-76` (rule 17: Keep first and focused, `✕ Confirm`, `Esc` through the layer stack) and `60-implementation.md:379-380` (names "discard a draft") both apply. `70-workflow-editing.md:56-58,104` says Discard is the one act here that confirms.
  - **Partial refutation.** `docs/design/README.md:128-130` describes "an armed **Discard every change**" as a single armed control and only requires "the tone and the `✕` together". The prior review (`docs/reviews/2026-10-10-design-conformance.md:614-616`) recorded only the missing `✕`. So the Keep/`Esc` part rests on rule 17 against README wording that tolerates a single armed button. The missing `✕` is unambiguous.
- **Fix note:** Either reuse the armed-row pattern (Keep first and focused, `✕ Confirm`, layer-stack `Esc`), or amend README/70 to bless a single armed button. In both cases add the `✕` and ignore a key-repeat second press.

### D7-04
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium, down from High. The unreachable control is a copy-id/sequence menu, a minor function. However, every rendered row adds a tab stop, which breaks the one-tab-stop list model.
- **Evidence:**
  - **The list is a listbox.** `runs/timeline/timeline.tsx:183-204` uses `VirtualList` without `role`, so the default is `listbox`, with rows as `option`s (`list/virtual-list.tsx:147,165,184,299`).
  - **Each row holds a button.** `TimelineEntryRow` renders `EntryMenu` (`timeline.tsx:298,330-361`), whose trigger is a native `<button aria-haspopup="menu">` with no `tabIndex` override (`ui/menu.tsx:428-439`).
  - **The rule is binding.** `50:161-165` says a list whose rows hold controls is a `grid`, and names exactly two such lists.
  - **Tests do not cover it.** The smoke axe run audits Runs, but its ready selector waits only for the run tree (`packages/app/test/smoke/app-shell.spec.ts:139`), so a timeline may never be in the audited DOM.
  - **Clipping is unverified.** The claim that the popover is clipped by `.orca-list__scroller` is supported only by the file's own comment (`timeline.tsx:150-152`). It needs layout to confirm.

### D7-05
- **Verdict:** CONFIRMED
- **Adjusted severity:** Medium, down from High. The focus loss is real and violates RULES 10, but it costs a keyboard user their place rather than any data.
- **Evidence:**
  - **Closing or publishing unmounts the editor.** `workflow/workflow-surface.tsx:166-180`: `onClose` and `onPublished` call `setEditing(false)`, which unmounts `WorkflowEditor` along with the focused button: Close (`workflow-editor.tsx:349-351`), Discard (`:261-262`, through `onClose`) or Publish (`:251`).
  - **The new Edit button is not focused.** It is re-rendered in the chrome header (`workflow-surface.tsx:115-121`) with no `focus()` call. `grep -a focus workflow-surface.tsx` finds nothing.
  - **Back to editing also drops focus.** It calls `setReview(undefined)` (`workflow-editor.tsx:392,491-493`), which swaps out the focused panel.
  - **Refutation attempt failed.** I searched for global recovery and found none: no `focusout`, `focusin` or `activeElement === document.body` handler, and no `MutationObserver` except in unrelated preferences and list code. The editor's own focus handling covers only deletes (`workflow-editor.tsx:169-203`).
