### C2-01 (C2.md), D2-01 (D2.md): later fan-out siblings see the artifacts of earlier finished siblings
- **Verdict:** CONFIRMED. This is a code bug, not intended behaviour.
- **Adjusted severity:** High (unchanged).
- **Evidence:**
  - `packages/engine/src/run-context.ts:242-258` (`earlierSiblings`) has no container-type or `workItemId` filter. `visibleArtifacts` (`:209-233`) then pulls the whole sibling subtree via `collect(sibling,"down")`.
  - `plan-dispatch` launches every item as a child of the same step (`plan/executors.ts:632-641`, `ctx.runChild(..., {workItemId, branch: slug})`).
  - `runChild` calls `startRun`, which writes `run.created`, only when a FanOut slot frees. That happens after the previous child's `child.finished` (`orchestrator.ts:1686-1742`).
  - The shipped `workflows/program.yaml:13,102` sets `concurrency: 2` with `itemWorkflow: ai-sdlc`. From the third item on, B's first `build` therefore resolves `{name: testReport}` and `{name: review}` to item A's artifacts. `resolveInputs` (`orchestrator.ts:1798-1799`) picks by name, highest version. `templates/sdlc/build.md` then renders A's report under "Fix the failures below" and "Address every 'changes requested' item".
  - The comment at `run-context.ts:203-207` and the docs (`docs/WORKFLOWS.md:95-100`, "`parallel` branches ... never see each other", and `docs/DATA-MODEL.md:189-194`) all assume parallel siblings never precede one another. That is false under any concurrency limit or `dependsOn`. Cross-item context has its own explicit channel, `vars.upstream` (`plan/executors.ts:632`), which shows that leaking it through sibling visibility was not the design.
- **Refutation attempts (all failed):**
  - No guard on `workItemId` or container type.
  - No plan or parallel test asserts prompt inputs.
  - B's own spec still wins (its version is A's + 1), but the optional `testReport`/`review` refs resolve to A's because B has none of its own yet.
- **Counter-evidence that changes the fix:**
  - `packages/engine/test/protected-execution-boundaries.test.ts:224-268` deliberately asserts that a *custom* container's second sequential child sees its first child's artifact (`expect(visible).toEqual([["prior"]])`). Generic sibling visibility for sequential children is therefore intended. Only the cross-work-item and fan-out case is a bug.
- **Fix note:** "restrict to `loop` only" (C2's first option) would break that test. Prefer excluding earlier siblings whose `workItemId` differs from this run's, or whose link was spawned by a FanOut (`parallel` / `plan-dispatch`). Update WORKFLOWS.md and DATA-MODEL.md to match whichever rule is chosen.

### C2-02 (C2.md): malformed YAML front matter throws out of `collect()`
- **Verdict:** CONFIRMED.
- **Adjusted severity:** Medium (down from High). The run fails loudly with the parser message and can be resumed. Nothing is corrupted. The real cost is losing the follow-up attempt the contract promises, plus duplicate artifacts on retry.
- **Evidence:**
  - `packages/engine/src/executors/agent-step.ts:139-140` calls `extractStructuredData` and `parseFrontMatter` with no try/catch.
  - `packages/core/src/util/frontmatter.ts:21` calls yaml@2.9.1 `parse`, which throws the first document error, such as nested compact mappings or duplicate keys.
  - The throw escapes the follow-up loop at `agent-step.ts:387`. It is not turned into `problems`, so no follow-up prompt is sent.
  - `orchestrator.ts:1604-1620` turns the throw into a retryable `failed` outcome. With `retryBudget` (`core/src/model/workflow.ts:384-388`) and `completion.maxAttempts` defaulting to 1 (`:64,78`), every ai-sdlc agent node except `build` (`maxAttempts: 2`) fails the run outright.
  - Deliverables recorded earlier in the same `collect` loop are recorded again on retry.
  - No test covers a deliverable with invalid YAML front matter (grep found none).
- **Fix note:** C2's recommendation is correct as written.

### C2-03 (C2.md): `void self.cancel(child)` races child lease attachment, causing an unhandled `RUN_LEASED`
- **Verdict:** CONFIRMED (the timing window is real but narrow).
- **Adjusted severity:** Medium (down from High). It needs a fail-fast halt or operator cancel to land inside a child's attach window. The consequences are wasted agent work, a misleading step failure, or a one-shot CLI exiting mid-run (recoverable with `resume`), not corruption.
- **Evidence:**
  - `orchestrator.ts:1725-1732`: both abort listeners `void` the `cancel()` promise.
  - `cancel` (`:517-563`) takes the non-live path whenever `this.live` has no entry. `this.live` is filled only in `loadContext` (`:1302`), after `getSummary` and `takeRunLease` (`:1315-1324`), which acquires with `this.leaseHolder`.
  - The non-live path acquires with a fresh holder (`:531-538`). `FileLeaseStore.acquireUnlocked` (`store/src/lease-store.ts:359-396`) returns the incumbent, so `cancel` throws `RUN_LEASED`, and nothing observes the rejection.
  - The child's `own` listener was `{once:true}` and has already fired, so nothing re-aborts it. The parent's `fan.settled()` loop waits for the child to finish its whole workflow.
  - The window is widened by `runBranches`, which has no `signal.aborted` check before `b.run(signal)` (`executors/containers.ts:229-241`). A branch halted while it is claiming or provisioning (git worktree) reaches `runChild` already aborted. It then hits the immediate path at `:1732`, where `cancel` and `run` race for the lease. If `cancel` wins, `takeRunLease` throws `RUN_LEASED` into the FanOut. That becomes the step error, with the misleading "take the lease with `orca leases break`" message.
  - `cli/src/main.ts:139-152`: `orca run`/`resume` run the orchestrator in-process (`commands/index.ts:501,508,655`), so an unhandled rejection there means `exit(1)`.
- **Fix note:** C2's recommendation is correct. Also check `signal.aborted` before `b.run`/`runChild` so an already-halted branch never spawns a child.

### C3-01 (C3.md): `private-execution/` is rescanned on every append and read
- **Verdict:** CONFIRMED.
- **Adjusted severity:** High (unchanged). The onset depends on store size (it is noticeable only at tens of thousands of records). However there is no retention, deleting payload files breaks replay, and the per-operation cost is O(directory), so a long-lived daemon degrades steadily.
- **Evidence:**
  - `ProtectedEventStore.append` calls `getInputs` unconditionally (`store/src/protected-event-store.ts:213-214`), for public-only runs too.
  - `FileExecutionStore.getInputs` (`execution-store.ts:229-238`) always calls `overlays()`, which calls `privateJsonNames`, which does a full `readdir(dir)` (`protected-file.ts:220-229`).
  - A protected append adds three more full scans:
    1. `getPayload` for the previous event (via `getPayloads`, which re-validates with `getInputs`).
    2. `putPayload`, which calls `getInputs` again (`execution-store.ts:255-265`).
    3. `writePrivateJson`, which calls `keyFor(dir, true)`, which does another `readdir` and decrypts one record (`protected-file.ts:393-418, 548-551`).
  - `read`/`readTypes`/`readRange` reach `getInputs`/`getPayload` through `requireSafeLegacy`/`requireIntegrity` (`:34-80, 355-369`).
  - Protected inputs are stored for every run with an actor, a parent or a generation (`engine/src/orchestrator.ts:436-445`). That covers every child run, so every event of every ai-sdlc item run writes one flat `<uuid>.payload.json`.
  - No cache, sharding or pruning exists anywhere. `docs/protected-execution-storage.md:51` says "There is no automated deletion".
- **Fix note:** C3's recommendation is correct as written.

### C3-02 (C3.md) / C1-08 (C1.md): `__proto__` prototype pollution via `config.set` patch paths
- **Verdict:** CONFIRMED (the pollution is real). C3's exploit framing is REFUTED as a privilege escalation.
- **Adjusted severity:** Low. C1 is right and C3's High is overstated.
- **Evidence (the sink is real):**
  - `ConfigPatchEntrySchema.path` is `z.string().min(1)` (`protocol/src/config.ts:325-328`). Only the newer `edits` form refuses `__proto__`/`prototype`/`constructor` (`:286-292`).
  - `splitPath` (`daemon/src/config-model.ts:572-580`) and `setInPlain` (`:583-595`) walk `node["__proto__"]`, which is `Object.prototype`, and assign to it.
  - This always happens for the sidecar (`:467`), and for the config document when the file is absent or blank (`:444-447`). An existing YAML file uses `doc.setIn`, which is safe.
  - The `validateOnly` branch runs `nextText` (`:274-280`), so a no-write validation call still pollutes the process.
  - Only a two-segment `__proto__.x` path pollutes. `constructor.prototype.x` just creates own keys, because `typeof Object === "function"`.
- **Evidence (who can reach it):**
  - `config.set` requires `config.write` and `config.read` (`daemon/src/auth/operations.ts:197-202`). Both are `WORKSPACE_PERMISSIONS`, which `holds()` grants only to unrestricted principals (`auth/principal.ts:66-75, 114-117`).
  - Of the presets, only `owner` has `config.write`. `operator`, `viewer` and `client` do not (`principal.ts:130-166`).
  - The other routes are a custom credential that an owner explicitly issues with those grants, and the opt-in `--unauthenticated-loopback` `LOCAL_PRINCIPAL`, which is owner-equivalent.
  - `--read-only` daemons do not register the method (`methods.ts:660-678`).
  - The MCP operator calls only `operator.*` methods, and `operator.config` is read-only.
- **What an attacker gains:**
  - Pollution can change authorization-relevant fallbacks. For example, `Object.prototype.default = "allow"` flows into `configured.default ?? …` in `layerPermissionPolicies` (`core/src/model/agent.ts:265`) and into any zod-parsed optional field.
  - Every principal that can do this can already write the sidecar (`{match:{}, decision:"allow"}`, live on the next ask) or `orca.config.yaml` (agent commands, plugins) directly. The only extra is an in-memory change with no file trace, plus DoS of the daemon.
  - No lower-privileged principal benefits.
  - In practice the owner token sits on disk in an agent-reachable directory (see C4-01). That is the real exposure, and it is C4-01's problem, not this sink's.
- **Fix note:** apply the `ConfigEditPathSchema` refinement to each patch segment, and walk own properties only in `setInPlain`. Treat it as hardening, not an escalation fix.

### C4-01 (C4.md): default config puts the sidecar, config, owner token and store inside the agent workspace, and default policy auto-allows edits
- **Verdict:** CONFIRMED.
- **Adjusted severity:** High (unchanged).
- **Evidence (the default workspace contains ORCA's own files):**
  - The schema default is `workspace: {provider: "local"}` (`core/src/config.ts:90`).
  - `makeWorkspaceProvider` uses `resolve(configDir, ws.root ?? ".")` (`cli/src/bootstrap.ts:204`). The same bootstrap serves `orca run` and `orca serve`.
  - That directory contains:
    - the sidecar `permissionPolicyPath(configDir)` (`agents/src/permissions.ts:187-189`)
    - `orca.config.yaml`
    - the default `storeDir: ".orca"` (`core/src/config.ts:56`), including `private-execution/` and its AES key
    - `<configDir>/auth/local-client.token` (`cli/src/commands/index.ts:1048-1050`), which is an **owner**-preset credential (`daemon/src/auth/bootstrap.ts:59-63`)
- **Evidence (the agent can grant itself allow-all):**
  - `DEFAULT_PERMISSION_POLICY` allows read, search, edit, delete and move with `scope: workspace` (`core/src/model/agent.ts:128-139`) whenever `default:` is unset.
  - `decidePermission` has no protected-path concept (`agents/src/permissions.ts:80-111`). Grep finds no exclusion of `orca.permissions.json`, `auth/` or `storeDir` anywhere.
  - The sidecar is re-read on every ask (`acp-session.ts:120,162`, using `bootstrap.ts:240`). Its rules are layered before the default rules, and an empty `match` is schema-valid (`core/src/model/agent.ts:59-75, 218-221`).
  - `fs/write_text_file` (`acp-session.ts:214-219`) writes anything inside the session roots with no policy check at all.
  - Result: in the default config, an injected agent's edit of the sidecar is auto-allowed, and every later `execute` ask becomes `allow`. Under the default `humanInput: pause`, those asks would otherwise have been cancelled.
- **Refutation attempts:**
  - The git-worktree provider puts *work-item* runs in `<repo>-worktrees/<slug>`, outside `configDir`, so the sidecar is outside-workspace and goes to `ask` (`engine/src/workspace/git-worktree.ts:27-36`).
  - However, runs with no work item still get `cwd: repo` unless `isolateRoots` is set, and it is optional and off by default (`core/src/config.ts:23`). That covers the program's `decompose`, `assess-risks` and `summarize` agent steps and a plain `orca run <workflow>`.
  - With the usual `repo: .` (as in `examples/orca.config.yaml:75-77`), the sidecar stays inside those runs' workspace.
  - `orca demo` uses scripted agents only.
- **Fix note:** a policy-level protected-path check is necessary but not sufficient. ACP agents' native tools act with the user's OS permissions and may not ask at all. The durable fix is to keep the sidecar, `auth/` and `storeDir` out of any agent root, for example by defaulting the local provider and root runs to a sub-directory or `isolateRoots: true`, and to refuse to start when a root contains them.
