## Findings

### C3-01: Every event append and read rescans the flat `private-execution/` directory, which grows by one file per protected event
- **Category:** performance (unbounded resource growth)
- **Severity:** High
- **Confidence:** High
- **Location:**
  - packages/store/src/protected-event-store.ts:214-215 (`append` → `getInputs` unconditionally), :241-243, :355-369 (`read*` → `requireSafeLegacy`/`requireIntegrity`)
  - packages/store/src/execution-store.ts:212-238 (`overlays` → `privateJsonNames`), :255-265 (`putPayload` → `getInputs`), :283-291
  - packages/store/src/protected-file.ts:221-229 (`readdir(dir)` of the whole directory), :393-419 (`keyFor(create)` runs `readdir` again and decrypts an arbitrary record on every write)
- **Issue:** `FileExecutionStore` keeps every protected record in one flat directory: inputs, overlays, one `<uuid>.payload.json` per protected event, generations, retry and continuation records. `getInputs(runId)` always lists that whole directory to find `<runId>.sensitivity.*` overlays. `ProtectedEventStore.append` calls `getInputs` first for every event, public runs included.
  - A protected append also calls `getPayload` for the previous event, which calls `getInputs` again.
  - It then calls `putPayload`, which calls `getInputs` a third time, then `writePrivateJson`, which calls `keyFor(dir, true)`. That runs another `readdir` and decrypts whatever `.json` sorts first.
  - Every `read`, `readTypes` and `readRange` also reaches `getInputs` through `requireSafeLegacy`/`requireIntegrity`.
  - docs/protected-execution-storage.md says "There is no automated deletion".
- **Scenario / evidence:**
  - `orchestrator.startRun` stores protected inputs whenever an actor, parent run or config generation is present (engine/src/orchestrator.ts:436-445). That covers every daemon-launched run and every child run.
  - In those runs every `agent.update` becomes its own payload file. 100 runs × 5 steps × ~500 updates is about 250k files.
  - From then on each streamed update costs about four full `readdir`s of 250k names plus a decrypt, and the cost keeps rising as the store ages.
  - `runs.list` → `listRunSummaries` → `readTypes` per run, which multiplies that cost by the number of runs. `inputs.list` with no run filter replays every run.
  - The result is quadratic slowdown of a long-lived daemon that eventually blocks its event loop.
- **Recommendation:**
  - Shard the directory per run (`private-execution/<encoded runId>/…`) so overlays are found with a per-run listing or a manifest record.
  - Cache the key per directory under the same stat or identity checks already used for ciphertext.
  - Skip `getInputs` for runs already known to be public-only, before the call rather than after it.
  - Add a retention or compaction story for payloads of finished runs.

### C3-02: A `config.set` patch path of `__proto__` pollutes `Object.prototype` in the daemon
- **Category:** security
- **Severity:** High
- **Confidence:** High (the pollution itself); Medium (downstream exploit impact)
- **Location:**
  - packages/protocol/src/config.ts:325-328 (`ConfigPatchEntrySchema.path: z.string().min(1)`), :356 (`patch` has no `.max()`)
  - Sink (daemon): packages/daemon/src/config-model.ts:572-580 (`splitPath`), :583-594 (`setInPlain`), :443-447 and :463-469 (callers)
- **Issue:** The structured `edits` path schema (`ConfigEditPathSchema`, config.ts:286-292) explicitly refuses `__proto__`, `prototype` and `constructor`. The older `patch` form accepts any dotted string. The daemon applies it with a hand-written `setInPlain`:
  - `node[key]` for `key === "__proto__"` returns `Object.prototype`.
  - The final assignment then writes onto it.
- **Scenario / evidence:**
  - A principal with `config.write` and `config.read` sends `config.set({document:"permissions", expectedRevision:<from config.get>, patch:[{path:"__proto__.default", value:"allow"}], validateOnly:true})`.
  - `nextSidecarText` always uses `setInPlain` (:467), and the `validateOnly` branch runs it before any write (:274-280). So `Object.prototype.default === "allow"` for the rest of the daemon's life, and no file changes.
  - Any optional field read off a plain object then inherits attacker values. For example, `configured.default ?? …` in `layerPermissionPolicies` (core/src/model/agent.ts:268) would turn the fallthrough for agents with no explicit `default` into `allow`.
  - Authorization or grant lookups on plain objects are equally exposed.
  - The same happens for the `config` document when the file does not exist yet (:444-447).
- **Recommendation:**
  - Apply the `ConfigEditPathSchema` unsafe-key refinement to each segment of `ConfigPatchEntrySchema.path`, and bound `patch` with `.max(…)` and a path length limit.
  - In `setInPlain`, reject `__proto__`, `constructor` and `prototype` segments, walk only own properties (`Object.hasOwn`), and build containers with `Object.create(null)` or a `Map`.
  - Add a regression test.

### C3-03: A stale lock is never broken while its owner's PID is "alive", including the current process's own PID after a container restart
- **Category:** reliability
- **Severity:** Medium
- **Confidence:** Medium-High
- **Location:** packages/store/src/file-lock.ts:74-97 (`removeDeadOwner`), :173-180 (`processAlive`)
- **Issue:** A lock owner is broken only if its host matches, its PID is a positive integer and `process.kill(pid,0)` fails. Age never breaks a lock (by design). There is no check that a "live" PID is the same process that wrote the token: no start time or boot id, and no in-process registry of held tokens. The comment on `processAlive` says every caller pairs it with an age or heartbeat rule (#103); `withFileLock` does not.
- **Scenario / evidence:**
  - The daemon runs as PID 1 in a container (Docker/Kubernetes; the hostname persists across `docker restart` or a pod container restart).
  - It is OOM-killed while holding `runs/<id>.jsonl.lock`, `plans/<id>.jsonl.lock`, `requests.json.lock` or `work-items.json.lock`. Appends hold these constantly while an agent streams, so this is likely.
  - On restart the new process is PID 1 again, so `processAlive(1)` returns true. Every later append or write on that key waits 60 s and fails with `STORE_LOCK_TIMEOUT`, indefinitely, until someone deletes the directory by hand.
  - If the stuck lock is `requests.json.lock`, every Request or WorkItem write fails.
  - The documented fail-closed case of an empty lock directory left by a crash between `mkdir` and token publication has the same outcome.
- **Recommendation:**
  - Keep a process-local `Set` of tokens this process holds. A token naming `process.pid` that is not in the set is provably stale.
  - Record the process start time (`/proc/<pid>/stat` field 22; `ps -o lstart` or sysctl on macOS) and the boot id in the token, and treat a mismatch as dead.
  - Consider a startup sweep for lock directories owned by this host's previous boot or PID incarnation.

### C3-04: `JsonFileDocumentStore` keeps mutations whose write failed before the lock; readers see them and a later write persists them
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** packages/store/src/document-store.ts:147-195 (`enqueue`). The `queue.splice` sits in a `finally` inside the `withFileLock` callback (:181-185).
- **Issue:** The batch is removed from `queue` only inside the locked callback. If `withFileLock` throws before running it (`STORE_LOCK_TIMEOUT`, `mkdir` EACCES/ENOSPC at :156), the caller's `put`/`delete` rejects, but the mutations stay queued.
  - `view()` (:134-140) applies the queue on top of the file, so `get`/`list` report the "failed" document as present.
  - The next unrelated `put` snapshots the whole queue and writes it.
- **Scenario / evidence:** A lock held more than 60 s (for example C3-03) makes `workItems.put(item{status:"failed"})` reject. The engine treats the write as not done. Readers in the same process still see `failed`, and the next item update silently persists it. During a long outage the queue also grows without bound. No test covers the failure path (document-store-batching.test.ts tests only the success paths).
- **Recommendation:** On any failure of the scheduled write, remove that batch from the queue (wrap the whole `p` body, not just the callback). Alternatively, keep failed mutations out of `view()` and reject them explicitly. Add a test for a write that hits `STORE_LOCK_TIMEOUT`.

### C3-05: Content-addressed blobs are overwritten in place, with no fsync and no hash check on read
- **Category:** data-integrity
- **Severity:** Medium
- **Confidence:** High
- **Location:** packages/store/src/artifact-store.ts:104-108 (`put`), :123-127 (`blob`)
- **Issue:** `put` calls `writeFile(blobs/<hash>, bytes)` unconditionally: open with O_TRUNC, then write. There is no temp file, no rename or link, no fsync, and no "already exists, skip".
  - Identical bodies share one blob, so every re-put of the same content truncates and rewrites a file other artifacts already reference.
  - Reads never verify `sha256(bytes) === contentHash`.
- **Scenario / evidence:**
  - Retries and loops often re-produce identical artifacts (an unchanged spec, an "approve" review), so `put` rewrites an existing blob in normal use.
  - A crash or power loss between truncate and write leaves the earlier artifact's blob empty or partial.
  - A concurrent reader (the daemon serving `artifacts.get`, or `RunContext.content` in another process) can read a truncated body.
  - Neither case raises `ARTIFACT_MISSING`: a prompt is rendered from partial content, which is the failure #270 aimed to prevent.
- **Recommendation:**
  - Write to a temp file in `blobs/`, fsync it, then `link()` into place, treating EEXIST as success. If the target exists, skip the write.
  - Fsync the directory before appending the index entry.
  - Verify the hash (or at least the size) when reading.

### C3-06: Replay opens every private payload at once and reports resource exhaustion as "record unreadable"
- **Category:** reliability (resource exhaustion)
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - packages/store/src/protected-file.ts:501-517 (`Promise.all(names.map(privateBytes…))`), :354-357 (any error → `unreadable()`)
  - packages/store/src/execution-store.ts:299
  - packages/store/src/protected-event-store.ts:382-389
  - Callers in engine/src/orchestrator.ts:548, 587, 715 pass the entire log.
- **Issue:** `executionEvents(await events.read(runId))` hydrates every protected event in a single `readPrivateJsonBatch`, which starts N `privateBytes` concurrently. libuv processes the stages breadth-first: all lstats, then all opens, then all stats and reads. So close to N file descriptors are open at the same moment. Any failure, including EMFILE or ENOMEM, becomes the generic integrity error "protected execution record or key is missing, invalid or unreadable".
- **Scenario / evidence:** Take a protected run with more payload records than the process's fd limit: thousands of `agent.update` events against a hard `nofile` of 4096 on some Linux hosts, or about 10k on macOS. `getState`, resume and inspection fail with what reads as corruption, and retrying fails the same way. Tests use `count = 2` (protected-replay-batch.test.ts:82).
- **Recommendation:** Bound the concurrency (for example 32-64 in flight) or read sequentially in chunks. Let transient OS errors (EMFILE, ENFILE, EAGAIN, ENOMEM) propagate as retryable rather than as `RUN_STATE` "invalid record". Consider replaying a page at a time.

### C3-07: Closed enums in hello and event schemas break the protocol's own rule that minor versions are compatible
- **Category:** design/architecture (version negotiation)
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - packages/protocol/src/handshake.ts:178,189 (`capabilities: z.array(z.enum(DAEMON_CAPABILITIES))`)
  - packages/protocol/src/runs.ts:253 (`events: z.array(OrcaEventSchema)`)
  - packages/protocol/src/subscriptions.ts:230 (`event.appended`)
  - packages/protocol/src/version.ts:1-5, :122-125
  - Consumer: app/src/client/daemon-client.ts:356 (parses with `HelloResultSchema`) before the `isCompatible` check at :599
- **Issue:** version.ts says a minor bump adds messages or fields and that `isCompatible` accepts any daemon with the same major and an equal or higher minor. But:
  - `HelloResultSchema` rejects any capability it does not know (protocol.test.ts:86-89 asserts this).
  - `runs.events` and `event.appended` validate events against core's closed discriminated union.
  - The version.ts note for 2.0 admits that 1.10 clients broke for exactly this reason.
  - Elsewhere the package is deliberately forward-tolerant (workflow-inputs.test.ts:52 "read a newer daemon's declaration instead of failing").
- **Scenario / evidence:** A 2.1 daemon adds a capability or a new event type (for example `foo.recorded`). A 2.0 app's `hello()` fails schema validation before `isCompatible` runs, so the user sees a parse error and the documented compatible pairing cannot connect. A 2.0 client's `runs.events` page fails entirely if any event in it has the new type, and `parseNotification` silently drops the frame.
- **Recommendation:**
  - Parse `capabilities` as `z.array(z.string())` and filter to known names.
  - For event pages, accept unknown types as an opaque `{type, seq, runId, at, payload: unknown}` variant.
  - Otherwise, state plainly in version.ts that capability and event additions are major bumps, and drop the "ignores the rest" wording carried over from 1.7.

### C3-08: Unbounded `runs.events` filters allow CPU denial of service, and forward pages re-parse the log from the start
- **Category:** performance / security (DoS)
- **Severity:** Medium
- **Confidence:** Medium-High
- **Location:**
  - packages/protocol/src/runs.ts:236 (`types: z.array(z.string().min(1))`, no `.max`)
  - packages/store/src/jsonl-event-store.ts:169-193 (per line: `needles.some(n => line.includes(n))`, then a full zod parse before the `seq` check)
  - packages/daemon/src/read-model.ts:518-530 (passes `types` straight through)
- **Issue:**
  1. A `runs.read` principal can send a ~1 MB body containing ~250k entries in `types`. The store checks every log line against every entry, roughly 250k × 50k lines, which blocks the daemon's event loop for minutes.
  2. `after` pages scan forward from byte 0 and zod-parse every preceding line (no `types` filter means no needle pre-filter), so tailing a long log with `after: lastSeq` re-parses the whole log on every call. A `stepRunId` that matches nothing does the same.
- **Recommendation:**
  - Bound `types` (for example `.max(64)`, string `.max(128)`) and make it a `Set`.
  - Cheaply pre-filter on `seq` before the zod parse (a regex on the `"seq":N` field), or keep a small sparse offset index per log, so `after` near the tail is cheap.
  - Audit the other older params schemas for missing `.max()`: `config.set` `text`/`patch`, `runs.start` `vars`, `idempotencyKey` in `RequestsSubmitParamsSchema`.

### C3-09: The "workspace" permission scope compares paths as text, so Windows relative or rooted paths and symlinks escape it
- **Category:** security
- **Severity:** Medium
- **Confidence:** Medium
- **Location:**
  - packages/core/src/model/agent.ts:313-352 (`normalizePermissionPath`, `workspaceRelativePath`)
  - Consumer: packages/agents/src/permissions.ts:80-110
  - Default rules: agent.ts:131-143
- **Issue:**
  - `normalizePermissionPath` converts backslashes only when a path starts with a drive letter or `\\`. `workspaceRelativePath` then treats any path that is not absolute and does not start with `..` as already inside the workspace.
  - On a Windows workspace (`C:\work`), both of these pass as in-workspace:
    - `\Users\me\.ssh\id_rsa`, which is rooted on the current drive.
    - `src\..\..\..\Users\me\secrets`.
  - `DEFAULT_PERMISSION_POLICY` therefore auto-allows read, edit, delete and move on them.
  - On every platform the check ignores symlinks, so a repository symlink such as `vendor -> /home/me` makes `vendor/.aws/credentials` look in-workspace.
- **Scenario / evidence:** A prompt-injected agent on a Windows host reads a file outside the workspace that was supposed to require `ask`. #140 introduced this default for exactly that case. The tests (core/test/permission-paths.test.ts) cover drive and UNC forms but not backslash-relative or drive-rooted (no drive letter) paths.
- **Recommendation:**
  - When the workspace is a Windows path, normalise backslashes in every location and treat a leading `\` or `/` as absolute.
  - Treat any `..` segment remaining after normalisation as outside the workspace.
  - Resolve symlinks (`realpath` of the longest existing prefix) on the agent host before scoping, or document `scope: workspace` as lexical and exclude symlinked paths.
  - Add tests for these cases.

### C3-10: Every artifact `get`, `content` or `list` re-reads and zod-parses the entire `artifacts/index.jsonl`
- **Category:** performance
- **Severity:** Medium
- **Confidence:** High
- **Location:** packages/store/src/artifact-store.ts:98-103 (`load`), :109-130
- **Issue:** There is no cache, fingerprint or id index. `blob(id)` → `get(id)` → `load()`, which calls `readCommitted("index", ArtifactSchema)` over the whole store's index and parses every line, including each artifact's front-matter `data`. It also runs `mkdir` on every call.
- **Scenario / evidence:** `RunContext.content` (engine/run-context.ts:270) calls this once per input artifact per prompt render. The daemon's `artifacts.get` and `artifacts.list` (with no `runId`) do the same work on every request. A store with tens of thousands of artifacts, each carrying a decomposition or risk register, pays tens of MB of parsing per body read.
- **Recommendation:** Cache the parsed index under a size, inode and mtime fingerprint (as `JsonlLogDir` and `JsonFileDocumentStore` already do), append newly put artifacts in memory, and keep `id`→entry and `runId`→ids maps.

### C3-11: The admission-retry quota counts every admission ever made and never resets; the recovery poll fsyncs every 5 s even when idle
- **Category:** reliability
- **Severity:** Medium
- **Confidence:** High
- **Location:**
  - packages/store/src/admission-retry-store.ts:151-155, :168-170 (counters only increase), :259-271 (`batch` republishes `cursor.json` on every call)
  - Callers: packages/store/src/continuation-admission-store.ts:83; cli/src/commands/index.ts:1260 (`setInterval(recoverContinuations, 5_000)`)
- **Issue:**
  1. `maxClaimsPerPrincipal` (10,000 by default) caps how many admissions a principal can ever make. Keyed and unkeyed `request.submit`/`run.admit` calls both increment it, and nothing decrements it. docs/admission-retry.md acknowledges this ("No claim expires", compaction is tracked as #399).
  2. Each `batch()` call fsyncs a tmp file and two directories even when `total === 0`, which happens every 5 s for the life of a token-auth daemon.
- **Scenario / evidence:** A single-operator daemon, or automation submitting ~50 runs a day, starts getting `RETRY_LIMIT` on every new admission after about 200 days. The only fix is editing the config and restarting. Meanwhile, idle laptops perform an fsync'd write every 5 s.
- **Recommendation:** Until #399 ships, make the quota a sliding window or release counts when operations settle. Skip the `cursor.json` publish when the cursor value is unchanged.

### C3-12: Collection files are rewritten in full through each process's own schema, so mixed versions drop fields
- **Category:** data-integrity
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - packages/store/src/document-store.ts:113-131, :160-178
  - Schemas: core/src/model/request.ts:205-264, model/plan.ts (all `z.object`, which strips unknown keys)
- **Issue:** Every `put` re-serialises all documents in `requests.json`, `work-items.json`, `plans.json` and so on, from objects parsed by the writing process's own schema.
  - An older CLI or engine on the same store strips fields it does not know from every document whenever it writes any one of them.
  - A newer enum value (for example a new `WorkItemStatus`) makes `load()` throw, so the older process can neither read nor write the collection.
  - Each `put` also pretty-prints and fsyncs the whole, never-pruned collection, an O(N) cost per status projection.
- **Recommendation:** Use `looseObject`/passthrough for persisted documents, or write a per-document file. Record a collection schema version and refuse writes from older versions. Consider one file per document or an append log for status projections.

### C3-13: Gaps in the expression sandbox
- **Category:** security (hardening)
- **Severity:** Low
- **Confidence:** High (mechanics); Low (exploitability, which depends on how workflows are written)
- **Location:** packages/core/src/expr/evaluate.ts:224, :238, :245-252, :269-271, :312-319
- **Issue:**
  - `fns[e.fn]` is looked up on an ordinary object, so `constructor(x)`, `toString()` and `hasOwnProperty(x)` pass the "unknown function" check. They return `Object(x)` or throw a non-`OrcaError` TypeError at run time, while `checkExpression` accepts them at validation.
  - `get()` blocks only `__proto__`, `constructor` and `prototype`. Inherited members such as `toString`, `valueOf` and `hasOwnProperty` resolve to (truthy) functions.
  - The `in` operator uses JavaScript `in` on objects, so `'toString' in vars.approved` is true.
  - The README claims "no prototype access".
  - `range(n)` has no upper bound: `range(2e9)` allocates until the process hits a fatal OOM.
- **Scenario / evidence:**
  - `when: exists(vars.approvals[artifacts.review.data.reviewer])`: an agent writes `reviewer: hasOwnProperty`, and the condition is true.
  - `items: range(artifacts.plan.data.count)`: an agent writes `count: 2000000000`, and the daemon blocks, then aborts.
- **Recommendation:**
  - Use `Object.hasOwn(fns, name)` and `Object.hasOwn(obj, key)` for member and `in` lookups, or build the function table and contexts with null prototypes.
  - Cap `range` (and `pluck`/`join` inputs) at, say, 10k.
  - Return an `OrcaError` for non-callable values.

### C3-14: The launch-input `pattern` regex still runs on values that already failed `maxLength`
- **Category:** security (DoS)
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/core/src/workflow/inputs.ts:314-322
- **Issue:** The `minLength`/`maxLength` failures do not return before the regex runs, so a megabyte-sized value is matched against an author-supplied `u`-flag pattern on every admission or preflight. `runs.start` `vars` are unbounded apart from the 1 MB HTTP body limit.
- **Scenario / evidence:** A workflow declares `pattern: "^(\\w+\\s?)*$"` with `maxLength: 64`. Any `runs.admit` or `workflows.validateInputs` caller sends 100 KB of `a` followed by `!`, causing catastrophic backtracking on the daemon thread.
- **Recommendation:** Return after a length failure, cap string inputs before testing the regex, and consider a linear-time engine (RE2) or a pattern-complexity lint at load.

### C3-15: `JsonlLogDir` puts keys into file paths without encoding or validating them
- **Category:** security (hardening)
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/store/src/jsonl-log.ts:98-100 (`join(dir, \`${key}.jsonl\`)`), :303-305 (lock directory `…jsonl.lock` created via `mkdir`)
- **Issue:** Claims, leases, execution and workflow stores all `encodeURIComponent` their ids. Run and plan logs do not. Wire `runId`s are `z.string().min(1)` (protocol/src/runs.ts:183, control.ts:120/137), so `runs.get({runId:"../../x"})` reads `<store>/../x.jsonl`. `readObservation` would `mkdir` and `rmdir` `<anywhere>.jsonl.lock`.
- **Scenario / evidence:** No write path is reachable, because new run ids are generated by the engine. Reads leak only existence and parse-error differences, since zod messages do not echo values.
- **Recommendation:** Validate keys (for example `/^[A-Za-z0-9_:-]{1,128}$/`) in `JsonlLogDir.file` and constrain run, plan and request id formats in protocol params.

### C3-16: `scanLinesBackward` ignores `bytesRead` on a `Buffer.allocUnsafe` buffer
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/store/src/jsonl-log.ts:534-549 (also `lastSeq`, the `before` pages of `readRange`, and every `requireIntegrity`)
- **Issue:** The size comes from `stat` and the read uses `allocUnsafe(len)`. If another process truncates a torn tail in between (`tail()` at :407-414), `read` returns fewer bytes and the rest of the buffer holds uninitialised heap memory. That memory is split into lines and parsed. A stale fragment of another run's event JSON could parse and appear in this run's page.
- **Recommendation:** Use `bytesRead`: slice the buffer or stop when it is short. The forward scan already does this correctly at :495-498.

### C3-17: Durability helpers fsync every ancestor directory up to `/` on each call
- **Category:** reliability / performance
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/store/src/jsonl-log.ts:267-283 (`syncDirectories`, called by each `appendDurableUnique`, `synchronizeExisting` and `readObservation`)
- **Issue:** Each call opens every ancestor with `O_RDONLY` and fsyncs it. An ancestor without read permission (an execute-only home or shared parent, mode 0711) makes the open fail with EACCES after the record is already written and fsynced. Every retry then finds the marker and fails again at the same step, so durable journal publication stays blocked. It also costs depth × (open + fsync) per call. `privateDirectory` (protected-file.ts:296-310) does this once per process; this function does it every time.
- **Recommendation:** Fsync only the directories this process created, once per process (as `privateDirectory` does), and tolerate EACCES on ancestors above the store root.

### C3-18: CLI-created stores are world-readable under the default umask
- **Category:** security / configuration
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - packages/store/src/jsonl-log.ts:103, document-store.ts:156,171, artifact-store.ts:99-106, claim-store.ts:110-114, lease-store.ts:344,460,475 (default modes)
  - cli/src/bootstrap.ts:299
- **Issue:** Only the private and identity directories are 0700. Run logs (agent text, tool `args`/`result` up to 2,000 characters, which can include file contents), artifact bodies, `requests.json` request text and lease host/PID data are created 0755/0644 under `.orca/` in the repository. The first-run path does create `.orca` as 0700 (protocol/src/first-run-fence.ts:315); plain `orca serve`/`run` does not. docs/protected-execution-storage.md notes the event projection is "not an artifact-body access boundary".
- **Recommendation:** Create the store root 0700 (and files 0600) from `fileStores`, or warn when the store root is group- or world-readable.

### C3-19: Workflow validation does not detect recursive subworkflow references, and the engine has no depth limit
- **Category:** correctness
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/core/src/workflow/validate.ts:142-147, :259-262 (`checkRef` checks only that a reference exists)
- **Issue:** Workflow `a` with an unconditional `subworkflow: a` (or `a → b → a`, or `program.itemWorkflow: program`) passes validation. At run time each child immediately spawns another child run, each with its own log, lease, workspace provisioning and nested await.
- **Recommendation:** Detect cycles over workflow references at load or registry time (warn on conditional cycles, error on unconditional ones), and enforce a maximum run-ancestry depth when spawning children.

### C3-20: Node-only lifetime fences live in the wire-contract package and use guessable loopback TCP ports
- **Category:** design/architecture
- **Severity:** Low
- **Confidence:** Medium
- **Location:**
  - packages/protocol/src/first-run-fence.ts:142-200
  - packages/protocol/src/update-window.ts:163-191 (8 slots, `port()` re-runs `fenceBoot()`, which spawns `ioreg`/`sysctl` synchronously on macOS for every slot attempt)
  - packages/protocol/package.json (`./update-window`, `./first-run-fence` exports)
- **Issue:** ARCHITECTURE.md describes `protocol` as "Zod schemas, depends on core only", but these modules do synchronous filesystem, `child_process` and `net` work.
  - The fences are 127.0.0.1 listeners on hash-derived ports in 20000–59999. The first-run and update-window schemes share that range, so they can collide with each other and with any unrelated listener. There is no fallback, so first-run for that workspace is refused permanently.
  - Any local user can squat the port, or connect and get a liveness answer.
  - Only 8 concurrent writer processes are allowed per enrolled root.
  - `assertFenceVolume` accepts only ext4, XFS, btrfs and overlay on Linux, so ZFS-root installs cannot complete first-run.
- **Recommendation:** Move these modules to an app/cli-side package. Use per-user `flock`/advisory locks or Unix domain sockets inside an owner-only directory instead of global TCP ports. Document or extend the supported filesystem list.

### C3-21: Ordinary appends are not fsynced, contrary to the `EventStore` contract
- **Category:** data-integrity (crash consistency)
- **Severity:** Low
- **Confidence:** Medium
- **Location:** packages/store/src/event-store.ts:4-6 (contract: "fan out … *after* the event is durable"), :162-171; jsonl-log.ts:374-389 (`appendJsonl` with no fsync)
- **Issue:** After power loss the tail of a log can disappear even though subscribers and clients already saw those `seq` values. The next append reuses those numbers for different events, so a client resuming with `subscribe({since: lastSeenSeq})` silently skips the new events in the reused range.
- **Recommendation:** Either fsync (perhaps group-committed per tick) before `publish`, or correct the contract wording and add a log incarnation id (for example the inode plus a creation nonce) to cursors so clients can detect a rewind.

### C3-23: Per-key in-memory maps grow for the life of a long-running daemon
- **Category:** resource-leak
- **Severity:** Info
- **Confidence:** High
- **Location:** packages/store/src/jsonl-log.ts:77-79 (`tails`, `chains`), lease-store.ts:258 (`InMemoryLeaseStore.chains`)

## Strengths
- **Locking:** the mutex protocol in `file-lock.ts` is careful. Only the process that unlinks the exact token may `rmdir`, so a delayed contender cannot remove a successor's lock, and a deterministic race test covers this. Leases fence obsolete writers with `withOwnership`.
- **Log appends:** `JsonlLogDir` numbers records on disk under a lock, repairs torn tails, and caches the tail by inode and size. The opt-in `appendDurableUnique` handles lost acknowledgements, duplicate correlations and sequence compare-and-set carefully, with fsync.
- **Protected records:** records are authenticated (AES-GCM with associated data bound to the record name), published write-once via link, kept in 0700/0600 files, opened with `O_NOFOLLOW`, and checked against stat identity before use. Failure messages carry no source bytes.
- **Wire validation:** inbound messages are validated with zod at runtime. Every `ParamsSchema` exists and the daemon uses them (117 references). The newer operator, drafts and templates schemas are consistently bounded (`.max` on ids, arrays, bytes and page sizes) and use `strictObject`.
- **Core purity:** core logic is pure and well documented. Reducers are exhaustive (a `never` check in `applyEvent`), id generation uses CSPRNG bytes without modulo bias (256 % 32 = 0), and launch-input validation never echoes values for sensitive inputs.
