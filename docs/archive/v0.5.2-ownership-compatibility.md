# v0.5.2 ownership compatibility

The event log remains the execution record. Work-item claims decide which dispatcher
owns an item; run leases decide which interpreter may currently advance its event log.
These are different guarantees and neither substitutes for the other.

## Upgraded writers

A lease ownership check and its protected append share the same cross-process
critical section as acquisition, renewal, release and takeover. A renewal suspended
inside that section cannot overwrite a successor: the successor must wait for the
section to finish, then make its own ownership decision. The mutation lock is never
stolen merely because a live process is slow or suspended.

The heartbeat's last successful renewal defines the real deadline. Repeated renewal
errors do not extend it. At expiry the local keeper reports loss once and aborts local
execution. A subsequent attempt to append must still pass the durable ownership check;
local cancellation by itself is not a fence.

## Existing logs and lease records

Existing event logs remain readable and resumable. No old events need migration,
and historical events do not gain invented ownership provenance.

New lease records retain the existing fields and add `guardedTtlMs` (actual TTL),
`guardedHost` (actual host), and `guardedId` (unique acquisition identity). Refresh
retains the identity; release or expiry followed by reacquisition creates a new one,
even at the same timestamp. Disk `ttlMs` is `Number.MAX_SAFE_INTEGER`, and disk `host`
is a sentinel containing a NUL character, which cannot be a real hostname. New readers
restore the actual host and TTL. Older readers see a non-expiring, nonlocal lease:
neither heartbeat expiry nor local dead-PID recovery can bypass the new mutex.
This also prevents an old recovery contender from moving a successor's lease record.
Older diagnostics display these sentinel values; use upgraded tools for actual status.

Records missing any guarded field, and unreadable records, are refused for acquisition,
renewal, protected writes and force-release. Even a demonstrably dead local legacy PID
does not prove that no older recovery contender remains paused. Recovery therefore
requires quiescing every writer and administrator that can access the store, then
explicitly removing the abandoned legacy lease record. Preserve the event log; the
upgraded runtime can resume it once the old coordination record is safely removed.
The refusal itself never changes the legacy lease or events.

## Mutex compatibility and crash recovery

New mutexes use directories at the existing `.lock` paths, containing a unique owner
token with local host and PID. Only a process that successfully unlinks the exact dead
owner token may remove that directory. A delayed competing remover cannot delete a
successor's differently named token or directory. Live, remote and unknown owners are
never stolen merely because a timeout elapsed; `staleMs` remains accepted but no longer
permits age-only takeover. Waits still fail with `STORE_LOCK_TIMEOUT` at their deadline.

Older writers encounter the existing path and then fail reading the directory; they
cannot treat it as a stale file. New writers wait for legacy lock files to be released,
but never automatically break them. Empty directories (including a crash between mkdir
and owner publication), malformed tokens and abandoned legacy files fail closed. After
quiescing all store users, an operator may explicitly remove only the abandoned mutex
path and retry. Successful ordinary operations remove their directory automatically;
proven-dead local directory owners recover automatically using the token protocol.
Durable event, claim and artifact record formats remain unchanged.

## Operator actions and limits

Stop older ORCA processes before administering ownership, and use the upgraded CLI
for lease breaks and claim release. An older explicit force-break command or direct
filesystem deletion can remove a fence despite the protocol; it cannot be made safe
by code in a binary it does not execute. Force is an administrative act, not automatic
recovery. The upgraded force path must refuse unsafe legacy holders as well.

Custom holder IDs must be unique per attachment; do not share one with an older binary,
whose same-holder refresh path predates fencing. Upgraded participants also reject an
active matching holder ID from a different process or host.

The same-host/process-namespace and atomic-filesystem assumptions of the existing
store still apply. A remote legacy holder cannot be declared dead from a local PID.
Do not work around that refusal by treating elapsed time as proof of death.

Claim records keep their existing shape. New claim creation and release serialize
through a mutation lock, and abandoned work-item projection repair completes before
the claim is exposed to a successor. Older claim-release commands do not participate
in that lock; claim administration likewise requires upgraded tools.
