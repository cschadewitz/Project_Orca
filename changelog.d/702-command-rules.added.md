- **core, agents, daemon, app:** Permission rules can match a shell command by its words: `command: "git push"` denies or asks for `git push` however it is written (`git -C repo push`, `sudo git push`, `bash -c "git push"`, or as one part of a compound command), and a final `*` covers a family (`npm *`). A command rule can deny or ask, never allow, because a command's words do not prove what it runs. For the same reason ORCA no longer offers, writes or honours a standing "Always allow" for a shell command: each command is answered once, and earlier title-based allows for commands in the permission sidecar are ignored. The "Always deny" review offers wider command rules (`npm run *`, `npm *`) alongside the exact command, and the Config surface shows and edits the new **Command** field. A config holding a command rule must declare `version: 2`, and a permission sidecar holding one is written as version 3, so ORCA 0.7.x refuses them. Once an agent's policy holds a command rule (in the config or saved by "Always deny"), no shell command is allowed automatically for that agent: commands not denied are asked, even if an older title rule or `default: allow` would have allowed them. A config that pairs command rules with `default: allow` or an allow for `kind: execute` (or no kind) is refused; set `default: ask` (or leave it unset) and give each allow rule a kind other than `execute`. The same holds for a call the agent did not classify or whose input carries a command whatever kind it claims, and for every agent whose permission sidecar cannot be read until it is repaired. Policies without command rules behave as before.
